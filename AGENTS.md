# Repository Guidelines

## Project Overview

`omp-channel-octo` is a private, resident TypeScript/Bun service that connects one Octo User Bot to a local OMP assistant. It accepts authenticated private messages and explicitly authorized group or CommunityTopic messages, keeps per-chat OMP sessions and durable task state, and returns assistant text, files, and optional execution progress cards. OMP runs as a child process over stdio RPC; it is not exposed through a network listener.

The design and behavioral contract are recorded in `docs/specs/2026-09-12-octo-channel-design.md`. Read it before changing permissions, commands, session movement, output delivery, persistence, or lifecycle behavior.

## Architecture & Data Flow

The main runtime path is:

```text
Octo HTTP/WebSocket
  -> OctoTransport (`src/octo/index.ts`)
  -> CoreService (`src/service.ts`)
  -> ChannelStore (`src/store.ts`): authorization, deduplication, bindings, tasks, outbox
  -> OMP worker (`src/omp/index.ts`): child process and stdio RPC
  -> WorkerEvent / ExecutionEvent
  -> durable outbox + ExecutionTracker
  -> Octo text, file, typing, and progress-card operations

Octo Bot event queue (`POST /v1/bot/events`, long poll + ack)
  -> CoreService (`src/service.ts`): card clicks answer the pending question
```

- `src/cli.ts` owns command dispatch and process lifecycle. `main` handles `start`, `run`, `check`, `restart`, `status`, `logs`, `test --card`, and `launchd`; the two entries installed by `bun link` are `oco` and `omp-channel-octo` (same program). `start` is the supervisor-hosted service process (it detects the daemon that runs it and exposes the restart port); `run` is the debugging entry point that stays out of the daemon's way. `runService` constructs the transport, worker factory, and service, then owns SIGINT/SIGTERM shutdown. Signal handlers must be removed only by the code that installed them; preserve unrelated host-process listeners.
- `src/supervisor.ts` detects which local supervisor hosts this checkout and under what program name — nothing about it is configured. It parses `super export --format json` / `super info` / `super list`, matches by live PID (service side) or by checkout directory and CLI command line (CLI side), and returns every candidate so an ambiguous machine is refused instead of guessed. `SupervisorTarget.kind` is where additional supervisor types (for example launchd) slot in.
- `src/logs.ts` owns the service's own log files under `~/.oco/logs` (`channel-YYYY-MM-DD.log`, 14-day retention): the console tee that mirrors output into the day's file with a `[YYYY-MM-DD HH:MM:SS]` prefix, the tail reader, and the follow loop that rolls over to the next day's file. Only `console` is wrapped — `process.stdout` also carries the OMP worker's protocol traffic.
- `OctoTransport` performs Bot registration, encrypted WebSocket communication, HTTP operations, inbound normalization, reconnection, message/file delivery, and AdaptiveCard capability checks. `ChatTarget` is keyed by the real `channelType` and `channelId`, not a display name.
- `CoreService` validates owner, group allowlist, thread identity, and structured bot mentions before handling commands or starting OMP. A group whose server-side 免@ decision (`GET /v1/bot/groups/{group_no}/mention_pref`, the server's AND of the bot owner's intent and the group's `allow_no_mention` switch) is effective lets the owner talk without an @mention; the decision is cached per group for 60 seconds (threads use the parent group), and a failed or unparsable lookup keeps the mention requirement. An allowlist rejection stays silent for everyone but the owner: an owner's @Bot mention in an unlisted group or thread gets one short notice per chat per 10 minutes carrying the exact passphrase `开通本群`, and that reply enables the chat — the durable `allowed_chats` row (state store, consulted as a union with the config's `allowedGroupIds`) is the permission, so no restart or config reload is needed, and `src/config-writeback.ts` then appends the id to the config file as the operator-visible mirror (a failed mirror keeps the grant and is reported). Non-owners, unmentioned messages, bot echoes, and DMs keep the old reply-less, task-less rejection path. Built-ins are `/new`, `/reset`, `/move`, `/thread`, `/queue`, `/mode`, `/interrupt`, `/cancel` (`/stop`), `/status`, `/help`, and `/restart`; `/thread <任务>` turns the message into a hand-over body for the assistant itself, which names the sub-thread and its `worktree_name`, drives `octo_management` (create-thread, then thread-dispatch), and dispatches the work directly when the requirement is clear or a request for the owner to clarify inside the thread when it is not; that body follows the chat's append mode like any other message the assistant reads — a running turn that accepts steering takes it as an append, `queue` mode or a refused steer leaves it a durable task — while a dispatched hand-over is delivered the way the target thread handles any arrival (its append mode and a steerable running turn take it as an append, otherwise it becomes that thread's own task, and the tool reports which happened), never as the answer to a question the target thread left open; while a chat has a pending `ask` question, the owner's next non-command text in that chat is its answer rather than a new task — with one question open it answers that question, and with several questions of one `ask` call open it answers the whole set at once (the same text into every open question, each read under its own rule) and the call returns immediately. When the deployment announces `octo/v2` with interaction enabled the questions are delivered as interactive cards instead: a single question keeps a frame of its own (one button per option for a single choice, a choice list for a multiple choice, a free-form field otherwise — every option question also carries a free-form field that wins over the selection when filled), while several questions share one card with per-question inputs and a single submit that records one compare-and-set per filled question inside one transaction and re-renders the rest behind fresh action ids; the text path and the card path share one answer compare-and-set and neither one replaces the other, and a set frame the deployment cannot carry (no interactive profile, over its limits, a failed send) falls back to asking its questions one at a time (`src/ask-card.ts`, Bot event queue below). With no persisted owner, the first valid private message claims ownership, is durably deduplicated, and only receives confirmation; it does not execute that message. Host tools are assembled per task: `ask` and `octo_send_file` everywhere, `octo_management` only in groups and threads, and `channel_control` everywhere — its `restart` asks the detected supervisor to restart this process once the channel is idle (so the asking turn still delivers its reply, which is what makes self-iteration possible), and its `status` reports the channel PID, running targets, queued tasks, blocked directories, and whether a restart is pending. `octo_management`'s `create-thread` accepts `worktree_name`: the host materializes a git worktree beside the calling chat's repository (directory and branch named after it, so the name must contain ASCII letters or digits) and pins the new thread's binding cwd to it (`chats.cwd_pinned`), so the thread runs in its own workspace; a workspace that cannot be created is reported as `worktree_error` while the thread stays usable, and only an explicit `/new <dir>` or `/move <dir>` replaces that directory. `octo_management`'s `thread-delete` retries once on a connection of its own when the server answers with a transient storage failure (any 5xx, or the `store_failed` internal error the bot API wraps as HTTP 400) — the server's delete is idempotent, so the retry cannot delete twice — and a final failure surfaces as one single-line, ≤200-character error; other failures, such as an authorization rejection, are not retried.
- `ChannelStore` opens `channel.sqlite` under `stateDir` with SQLite WAL/foreign keys. It persists owners, the runtime-enabled chat set (`allowed_chats`), bindings, inbound claims, tasks, outbox records, questions, progress-card rows, the worker ledger, and the Bot event-queue cursor. Durable acceptance precedes side effects; after a task crosses the `started` boundary, restart or reconnect must not automatically rerun it.
- `src/omp/index.ts` launches the installed OMP executable with an explicit RPC mode, yolo approval mode, cwd, and session directory. Keep the RPC decoder and OMP process lifecycle isolated from the host service. Worker cancellation uses bounded process/group shutdown and watchdog bookkeeping.
- `src/project-session.ts` validates session headers, canonical cwd, session IDs, and `previousSessionFiles` breadcrumbs. Native `/move` preserves session identity; external recovery accepts only an exact, uniquely verified session rather than a recent or fuzzy file match.
- Assistant output is cumulative per assistant message: stable local/remote IDs, immediate first nonempty create, serialized edits throttled to one second, authoritative final snapshots, and stable 3,000-UTF-8-byte segments. Do not merge separate assistant messages or let an older snapshot overwrite a newer one.
- `src/group-history.ts` holds the pure group/thread history accounting: live coverage buffer, `POST /v1/bot/messages/sync` fetch planner, window selector, and prompt-block renderer. `CoreService` records every group/thread inbound sequence before the permission gate, pages the server only when the live buffer cannot prove coverage of `(watermark, S)`, stamps one `message_seq` per accepted task, and keeps a per-session `group_history_ledger` watermark in SQLite so already-injected messages are never sent twice. A failed page leaves the turn without history and holds the watermark. Enabled by default via `groupHistory`.
- `src/attachments.ts` holds the pure inbound-attachment helpers: `attachmentDirectory`, `safeAttachmentName`, `composePromptText`, `formatBytes`, `AttachmentError`, and `sweepAttachments`. The transport maps each inbound `payload.type` to text plus attachment references; `CoreService` downloads them under `<stateDir>/attachments/<channelType>-<channelId>/<messageId>/` at one assembly point (after the permission gate and any pending-question answer, before steering and task acceptance) and folds absolute paths into the task text; a command path takes resources exactly when it consumes the message body: `/thread <任务>` and `/queue <文本>` assemble their command argument, a registered handler assembles the whole message (an intercepting one sees the assembled body, an observing one accepts the assembled body as its task text), while control commands that never hand a body to the agent (`/status`, `/new`, `/mode`, `/cancel`, …) and the pending-question answer path download nothing. `supported` is `true` for text-shaped payloads (types 1, 14, 17) even when the text is empty — a bare `@bot` still runs an ordinary turn — and otherwise only when text or a usable attachment was extracted, so unusable media and out-of-table types keep the explicit "unsupported message type" refusal. A reply also runs the same type table over the payload the client inlined in `payload.reply.payload`: the quoted text becomes an `[引用 <sender>]` block and the quoted media joins this message's attachments (deduped by absolute URL), while `supported` still follows only the message's own payload. Attachments are only ever reached behind the owner/allow-list/mention gate, bounded by `attachments.maxBytes` (25 MiB default) with a per-message count and time budget, and swept after 14 days at startup. Voice messages are transcribed through the Octo bot voice endpoint, best-effort.
- `src/worktree.ts` creates isolated thread workspaces through the resolved OMP executable (`omp worktree add`, so OMP's clone-first behavior carries ignored files like `node_modules`). Directory and branch come from the caller's `worktree_name` slug, stepping aside to `<slug>-<shortId>` when taken; names without ASCII letters or digits are rejected, commands are bounded, and failures are reported as single-line, 200-character-bounded errors. `runService` wires the port; the test harness injects a fake.
- `src/config-writeback.ts` keeps the config file's `allowedGroupIds` in step with a runtime grant: it re-reads the file at write time, appends only that array, and replaces the file by an atomic same-directory rename that preserves the original mode. `runService` wires the port from the resolved config path; a failure only costs the mirror, never the durable grant.
- `src/execution-card.ts` provides `ExecutionTracker`, safe execution snapshots, and AdaptiveCard construction. Real tool/turn/todo/run events feed one editable progress card per user round: a task and every message appended to it each open their own card at the first real tool progress, and an appended message closes the round it interrupted so the live card always sits below the newest message. The card's todo list is its contract and the execution trace is a rolling log, so the fit search sheds trace rows and the hidden-row budget first and only then shrinks the visible todo band; a trimmed band stays centred on the handoff (pinned `in_progress`/`blocked` tasks, growing outward from the first open task, completed side first), its expandable hidden rows are the omitted tasks nearest that band, and a phase renders only when it has a rendered child row. Rich trace rows carry the step's local `HH:mm:ss` start time; the compact history rows are single text lines. Capability and payload limits are checked against the wire envelope (card plus frame fields) before sending a card, and card failures must not block text delivery. `encodeExecutionSnapshot`/`restoreExecutionSnapshot` own the durable card payload: each card keeps its own row (bot, task, message id) with its message id, sequence, and last snapshot, deleted once that card's terminal edit lands, so every card a restart left open gets one terminal edit from the next process instead of leaving the client on the last running state.
- `src/ask-card.ts` builds the interactive `ask` frame (question text plus one `Action.Submit` button per option, a multi-select `Input.ChoiceSet`, or a free-form `Input.Text`), decodes the action id of a click back into an option index, and turns card inputs into the same answer strings a text reply produces. The card is one answer path, never the only one: `CoreService` falls back to the plain text question when the frame cannot be sent, and a text reply answers the same question. `CoreService` consumes the Bot event queue for clicks — `POST /v1/bot/events` long poll with a persisted monotonic cursor, ack only after the answer is durable, unknown event types acknowledged and skipped, and a missing endpoint stopping the poll loop.
- `src/execution-card.ts` provides `ExecutionTracker`, safe execution snapshots, and AdaptiveCard construction. Real tool/turn/todo/run events feed one editable progress card per user round: a task and every message appended to it each open their own card at the first real tool progress, and an appended message closes the round it interrupted so the live card always sits below the newest message. Capability and payload limits are checked before sending a card, and card failures must not block text delivery. `encodeExecutionSnapshot`/`restoreExecutionSnapshot` own the durable card payload: each card keeps its own row (bot, task, message id) with its message id, sequence, and last snapshot, deleted once that card's terminal edit lands, so every card a restart left open gets one terminal edit from the next process instead of leaving the client on the last running state.
- `src/ask-card.ts` builds the interactive `ask` frames — one question (option buttons and/or a free-form `Input.Text`, plus a submit) or a whole set on one card with per-question inputs (`ask_choices_<n>`/`ask_text_<n>`) and a single submit — decodes the action id of a click back into options or a set submission, and turns card inputs into the same answer strings a text reply produces. The card is one answer path, never the only one: `CoreService` falls back to plain text questions when a frame cannot be sent, and a text reply answers the same questions. `CoreService` consumes the Bot event queue for clicks — `POST /v1/bot/events` long poll with a persisted monotonic cursor, ack only after the answer is durable, unknown event types acknowledged and skipped, and a missing endpoint stopping the poll loop.
- `src/octo-cli.ts` gives each bot its own `octo-cli` credential: after the Bot registers, `provision` writes the token through stdin into `~/.oco/octo-cli/<botUid>` (0700) and publishes `OCTO_CONFIG_DIR`/`OCTO_API_BASE_URL`/`OCTO_BOT_ID`, which `workerEnv` passes to OMP children through an allowlist while the host's own `OCTO_*` stay stripped. A missing or failing CLI only costs the agent that identity; tasks then fall back to the host tools alone. Every task can therefore call `octo-cli` as this bot, including endpoints no host tool wraps.

## Development Commands

Install and run the standard checks:

```sh
bun install
bun run typecheck
bun test
```

Create a local configuration and exercise the service:

```sh
bun link   # installs both bin names (~/.bun/bin/oco → this checkout)
mkdir -p ~/.oco/config
cp config.example.json ~/.oco/config/config.json
chmod 600 ~/.oco/config/config.json
oco check --config ~/.oco/config/config.json
oco start --config ~/.oco/config/config.json
```

`check` validates configuration, Bot registration, and an OMP fresh-worker start/stop path; it deliberately does not call a model. `start` runs the service in the foreground — it is what a supervisor hosts — while `run` is the same process without supervisor participation (no detection, no restart port), for debugging. The default config path is `~/.oco/config/config.json`; service logs land in `~/.oco/logs/`. The package also keeps `bun run check` / `bun run start` / `bun run launchd` scripts as an install-free path.

Day-2 operations go through the same entry point, with the supervisor and program detected from the checkout:

```sh
oco restart            # super -y restart --wait-healthy + PID comparison
oco status             # supervisor state, PID, uptime, config and log paths
oco logs --tail 200    # service-owned log file; -f follows across midnight
oco test --card        # live preview card (applies ./.envrc first)
```

For macOS launchd:

```sh
oco launchd install --config ~/.oco/config/config.json
launchctl bootstrap "gui/$(id -u)" "$HOME/Library/LaunchAgents/com.omp.channel-octo.plist"
launchctl bootout "gui/$(id -u)/com.omp.channel-octo"
oco launchd uninstall --plist "$HOME/Library/LaunchAgents/com.omp.channel-octo.plist"
```

`launchd install` writes a private plist and does not call `launchctl`; loading and unloading are explicit operational steps. The generated plist runs `start` and writes its stdout/stderr into `~/.oco/logs/`.

The resident service on this host is managed by Super: the stack at `~/.super/conf/conf.d/omp-channel-octo.toml` runs `bun run src/cli.ts start --config ~/.oco/config/config.json` from the checkout, with `OCTO_BOT_TOKEN` sourced from `.envrc`. The private config holds the live values and `config.example.json` is only the template they are copied from. Apply stack edits with `super apply -f ~/.super/conf/conf.d/omp-channel-octo.toml`, then use `oco restart` to restart the service and wait for it to report healthy. Nothing about the supervisor or the program name lives in the channel config: both the CLI and the service detect it (`src/supervisor.ts`).

## Code Conventions & Common Patterns

- Use strict TypeScript contracts from `src/contracts.ts` and explicit dependency injection through `createChannelService`, `createOctoTransport`, `createWorkerFactory`, and option interfaces. Keep transport, persistence, worker, and presentation seams independently testable.
- Keep explicit `.ts` import extensions and follow the ESM/Bundler configuration in `tsconfig.json`.
- Validate untrusted config, protocol frames, message metadata, paths, and tool results at their boundaries. Use type guards and bounded body/frame sizes instead of assuming external shapes.
- Use `AbortSignal` and bounded deadlines for network activity, typing/card operations, worker cancellation, and shutdown. Pair resource ownership with `try`/`finally`; preserve the original error when rolling back a store transaction.
- Route state changes through `ChannelStore` transactions and persist durable acceptance, desired outbox versions, and stable client IDs before network operations. Reconnect recovery resumes delivery; it does not rerun an already-started task.
- Serialize by normalized realpath and chat target. A move holds both source and target directory leases, and a directory remains blocked until worker termination is confirmed.
- Treat command paths as data, not shell input. Apply the existing absolute/`~/` path rules and realpath normalization; do not add shell expansion or a second path parser.
- Keep user-visible errors and progress summaries safe and bounded. Never expose tokens, raw tool arguments/results, model thinking, or protocol payloads in logs, cards, or group output.
- Keep the OMP RPC compatibility decoder in `src/omp/index.ts` separate from host lifecycle/signal handling and retain its complete upstream MIT license. Do not clear global signal listeners to solve worker conflicts.

## Runtime/Tooling Preferences

- Use Bun as the runtime, package manager, and test runner. The package is ESM; `bun.lock`, `bun-types`, and the `#!/usr/bin/env bun` CLI establish this convention. Node-compatible APIs are imported from `node:*` while executing under Bun.
- TypeScript targets ES2022/ESNext with Bundler resolution, strict checking, `noUncheckedIndexedAccess`, and `exactOptionalPropertyTypes`. `tsconfig.json` includes both `src/**/*.ts` and `tests/**/*.ts` and emits no JavaScript.
- Use the installed `omp` executable, or pass `--omp-command` for a validated executable path. OMP stays in a child process over stdio RPC; do not load the full OMP runtime into the service host.
- Credentials come from a private config `botToken` or a `botTokenEnv`, never both. Environment credential names must use `OCTO_` or `OMP_CHANNEL_OCTO_` prefixes; keep `.envrc`, local config, state, SQLite, and logs out of version control and never echo token values.
- `stateDir` is created with private permissions and contains SQLite/outbox/runtime data. The sample defaults are in `config.example.json`; `src/config.ts` normalizes the API URL and local paths.
- `package.json` has no build or lint script. The supported compiler check is `bun run typecheck`; use the repository's existing scripts rather than introducing an unrecorded toolchain.

## Testing & QA

- Run `bun run typecheck` and `bun test` for a normal change. There is no coverage command in `package.json`.
- The suite intentionally separates layers: `tests/cli-lifecycle.test.ts` spawns the real CLI and Octo fixture; `tests/cli-ops.test.ts` spawns the real CLI against a fake `super` on `PATH`; `tests/omp-worker.test.ts` spawns the real Bun RPC fixture; core streaming, bindings, recovery, and boundary tests use deterministic fakes and temporary directories.
- For lifecycle changes, preserve real-process coverage for `/status`, clean SIGTERM exit, WebSocket closure, and absence of the bot token from captured output. `tests/cli-lifecycle.test.ts` is the reference test; it also covers a supervisor restart end to end (a fake `super` reports the CLI's own PID, so detection matches by PID rather than by name).
- For supervisor detection, the oco command surface, or service-owned logs, use `tests/supervisor.test.ts` (export/info parsing, PID and checkout matching, ambiguity, restart argv, failure and timeout paths), `tests/logs.test.ts` (day naming, tee prefixing and rollover, retention, tail, follow), and `tests/cli-ops.test.ts` (`restart`/`status`/`logs` through the real CLI with a recorded fake `super`).
- For host-tool changes, use `tests/core-host-tools.test.ts`: it asserts the per-chat tool set and exercises `octo_management`, `octo_send_file`, and `channel_control` against the fakes. Its `thread-delete` cases cover the retry after a transient `store_failed`/5xx answer (second attempt on a fresh connection, thread gone), the single bounded ≤200-character error when the retry fails too, and that a permanent rejection is sent exactly once. Its dispatch cases cover the landed task in an idle thread plus the two dispositions in a thread that is busy: a `steer`-mode thread's running turn takes the dispatched content as steering (`delivery=steered`, no second task, receipt names the running turn), and a `queue`-mode thread with an open question queues the dispatch as its own task while the question stays the owner's to answer (`delivery=queued`).
- For the `/thread` command, use `tests/core-thread-command.test.ts`: the command creates nothing itself — it hands over an instruction body (the agent names the thread and its workspace, and the requirement's clarity decides whether the dispatch is the work or a clarification request); a chat running a steerable turn takes that body as an append (`tests/core-steering.test.ts`, "/thread joins the running turn in steer mode instead of waiting behind it"), `queue` mode keeps it a queued task — and the test drives `octo_management` from the prompt callback to prove the composition.
- For the interactive ask card and the Bot event queue, use `tests/core-ask-card.test.ts`: a single-choice click answers the question and rewrites the card, a plain reply answers the same card, a multi-select submission answers with the selected indexes, a free-form submission answers a question that has no options, an empty submission redraws fresh action ids and keeps the question answerable, a non-owner click leaves the question pending, a click replay after the reply stays silent and updates nothing, and a failed card send falls back to the text question. The multi-question cases live in the same file: one submit answers every question of a set card (per-question inputs, the filled free-form field winning over the selection), a partial submission keeps the unfilled questions open behind a fresh submit id, one plain reply answers the whole set at once, a replayed submission answers nothing twice, and a set frame the deployment refuses falls back to one card per question or to text questions. `tests/octo-transport.test.ts`'s "Octo interactive cards and Bot events" block covers the `octo/v2` frame send and answered rewrite against the real HTTP fixture, the decline while interaction stays off, event-queue reads with cursor and ack, cursor hold clamping, a missing endpoint, and queue/ack failures.
- For RPC changes, use `tests/omp-worker.test.ts` and `tests/fixtures/omp-rpc-worker.ts`; cover ready negotiation, v1/v2 chunk reassembly, prompt acknowledgement versus completion, cumulative text events, late/repeated starts, cancellation, crashes, and process-group cleanup.
- For the append modes' consumption receipts, use `tests/core-steering.test.ts` (a steered message reports one `已并入当前回合` line once OMP confirms it joined the turn; only a message that actually waited behind the run reports `开始执行排队消息` at start) and the steer case in `tests/omp-worker.test.ts` (a `steering: true` user frame becomes a `steer_consumed` event, while an ordinary user frame stays unreported).
