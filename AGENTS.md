# Repository Guidelines

## Project Overview

`omp-channel-octo` is a private, resident TypeScript/Bun service that connects one Octo User Bot to a local OMP assistant. It accepts authenticated private messages and explicitly authorized group or CommunityTopic messages, keeps per-chat OMP sessions and durable task state, and returns assistant text, files, and optional execution progress cards. OMP runs as a child process over stdio RPC; it is not exposed through a network listener.

The design and behavioral contract are recorded in `docs/specs/2026-09-12-octo-channel-design.md`. Read it before changing permissions, commands, session movement, output delivery, persistence, or lifecycle behavior.

## Architecture & Data Flow

The main runtime path is:

```text
Octo HTTP/WebSocket
  -> OctoTransport (`src/octo/index.ts`)
  -> CoreService (`src/service.ts`)
  -> ChannelStore (`src/store.ts` + `src/store-*.ts`): authorization, deduplication, bindings, tasks, outbox
  -> OMP worker (`src/omp/index.ts` + `src/omp/*.ts`): child process, stdio RPC, process group
  -> WorkerEvent / ExecutionEvent
  -> durable outbox + ExecutionTracker
  -> Octo text, file, typing, and progress-card operations

Octo Bot event queue (`POST /v1/bot/events`, long poll + ack)
  -> CoreService (`src/service.ts`): card clicks answer the pending question
```

- `src/cli.ts` owns command dispatch and process lifecycle. `main` handles `start`, `run`, `check`, `restart`, `status`, `logs`, `test --card`, and `launchd`; the two entries installed by `bun link` are `oco` and `omp-channel-octo` (same program). `start` is the supervisor-hosted service process (it detects the daemon that runs it and exposes the restart port); `run` is the debugging entry point that stays out of the daemon's way. `runService` constructs the transport, worker factory, and service, then owns SIGINT/SIGTERM shutdown. Signal handlers must be removed only by the code that installed them; preserve unrelated host-process listeners.
- `src/supervisor.ts` detects which local supervisor hosts this checkout and under what program name — nothing about it is configured. It parses `super export --format json` / `super info` / `super list`, matches by live PID (service side) or by checkout directory and CLI command line (CLI side), and returns every candidate so an ambiguous machine is refused instead of guessed. `SupervisorTarget.kind` is where additional supervisor types (for example launchd) slot in.
- `src/logs.ts` owns the service's own log files under `~/.oco/logs` (`channel-YYYY-MM-DD.log`, 14-day retention): the console tee that mirrors output into the day's file with a `[YYYY-MM-DD HH:MM:SS]` prefix, the tail reader, and the follow loop that rolls over to the next day's file. Only `console` is wrapped — `process.stdout` also carries the OMP worker's protocol traffic.
- `OctoTransport` performs Bot registration, encrypted WebSocket communication, HTTP operations, inbound normalization, reconnection, message/file delivery, user lookups (`GET /v1/bot/user/info`), and AdaptiveCard capability checks. `ChatTarget` is keyed by the real `channelType` and `channelId`, not a display name. A dropped socket and a server-initiated `DISCONNECT` (a kick, reason 12 `ReasonConnectKick`, which the server sends when another login takes the session over, when it expires, or when the cluster moves it) both re-register and reconnect on an exponential backoff that doubles from 1s to a 30s cap and is jittered downward; only a failed registration or CONNACK authentication stops the transport for good.
- `CoreService` validates the chat, sender, and structured bot mentions before handling commands or starting OMP: DMs must come from the owner, and groups/threads must hit the allowlist (`allowedGroupIds` ∪ the state store's `allowed_chats`, with threads inheriting the parent group). There the owner runs a task with an @mention, or without one when the server-side 免@ decision (`GET /v1/bot/groups/{group_no}/mention_pref`, the server's AND of the bot owner's intent and the group's `allow_no_mention` switch) is effective — cached per group for 60 seconds (threads use the parent group), and a failed or unparsable lookup keeps the mention requirement; any other member runs a task when the message carries a structured @mention of the bot, and the 免@ exemption stays the owner's (a member's unmentioned message never runs and never triggers the lookup). Members never run commands either: a member's `/` message is consumed with one throttled notice per chat per 10 minutes (`命令仅 owner 可用；需要助手做事请直接 @<botName> 说明。`, deduplicated by the message's durable command claim) and never reaches a handler, the worker, or a task. An allowlist rejection stays silent for everyone but the owner: an owner's @Bot mention in an unlisted group or thread gets one short notice per chat per 10 minutes carrying the exact passphrase `开通本群`, and that reply enables the chat — the durable `allowed_chats` row (state store, consulted as a union with the config's `allowedGroupIds`) is the permission, so no restart or config reload is needed, and `src/config-writeback.ts` then appends the id to the config file as the operator-visible mirror (a failed mirror keeps the grant and is reported). Non-owners, unmentioned messages, bot echoes, and DMs keep the old reply-less, task-less rejection path. Built-ins are `/new`, `/reset`, `/move`, `/thread`, `/queue`, `/mode`, `/switch`, `/interrupt`, `/cancel` (`/stop`), `/status`, `/help`, and `/restart`; `/switch [模型]` reports or sets the chat's model — with no argument the running turn's live session answers from `get_state`/`get_available_models`, and an idle chat uses a one-off fresh worker (its own temporary session directory, stopped and removed afterwards, no chat session touched) that reports the current model and the provider-grouped available list (bounded at 80 models); with an argument the selector goes to OMP's own `/switch` (ACP builtin), which resolves `provider/id`, a model id or unique substring, `@role` (`settings.modelRoles`), and a `:level` suffix against its live catalog — a running turn's own session takes the dispatch in place (OMP consumes it locally with `agentInvoked:false`, so it works mid-turn and the turn keeps running), otherwise the throwaway probe worker resolves it, and the resolved `provider/id[:level]` is stored in `chat_models` for the chat; `default` clears it back to OMP's default; every worker created for that chat afterwards (task path and `/new`, `/reset`, `/move`) starts with `--model <value>`, which overrides the model recorded in a resumed session and survives a restart; `/status` carries a `model=` line; the `/new` and `/reset` success receipt (one shared creation path) carries the fresh session's actual model as well — `已创建会话 <session id>，cwd=<dir>，模型=<provider/id[:level]>`, read from that session's own candidate worker through the same `worker.models()` state query before it is stopped (no generation turn for display): the stored chat value when `--model` carried one, OMP's real default otherwise (never the literal `default`), and the receipt keeps its model-less form instead of inventing a value when OMP cannot or does not answer; `/move` migrates the existing session instead, so its receipt stays model-less — `/thread <任务>` turns the message into a hand-over body for the assistant itself, which names the sub-thread and its `worktree_name` and drives `octo_management` (create-thread, then thread-dispatch). In a sub-thread that is bound to an isolated workspace, whose deployment has isolation, and whose host has a compatible local `wt` (stable v0.76.x), `/thread merge` (the argument is matched by its first word: `merge` alone or followed by a separator, so `/thread merge, 已经完成的话` merges while a name like `merge-fix` does not, and anything after the keyword rides along as the owner's note) instead hands the assistant a merge instruction delivered under that chat's append mode — the host runs `wt merge` through `octo_management`'s `thread-merge`, the assistant never runs `wt` itself, and the command itself is the owner's confirmation to merge and clean up: unless a stated necessity says otherwise, the assistant runs the default pipeline, which removes the workspace and its merged branch after a successful merge, and keeping the workspace requires that reason plus an explicit `remove:false`; the instruction body likewise treats the sub-thread's cwd falling away with the removed workspace as a known result, not a caveat to repeat or a reason to keep it — while the main group, a DM, an unbound sub-thread, a deployment without isolation, and a host without a compatible `wt` are answered with a notice only, no task. The dispatch body always follows SDD shape (goal, scope, constraints, acceptance) — a requirement clear enough to generate the SDD from is dispatched as the work itself so the thread generates the SDD and starts at once, anything else is dispatched after at most the few answers it takes to hand it over, and the hand-over leaves the remaining clarification to the thread, settled in that same SDD shape (through the `spec-design` skill when the environment has it) before implementing; that body follows the chat's append mode like any other message the assistant reads — a running turn that accepts steering takes it as an append, `queue` mode or a refused steer leaves it a durable task — while a dispatched hand-over is delivered the way the target thread handles any arrival (its append mode and a steerable running turn take it as an append, otherwise it becomes that thread's own task, and the tool reports which happened), never as the answer to a question the target thread left open; while a chat has a pending `ask` question, the owner's or an enabled-group member's next non-command text in that chat is its answer rather than a new task — with one question open it answers that question, and with several questions of one `ask` call open it answers the whole set at once (the same text into every open question, each read under its own rule) and the call returns immediately; every recorded answer stores its submitter (`questions.answered_by`: the sender for a text reply, `operatorUid` for a click), which the `ask` result carries as `answeredBy` per answer and the card rewrite / timeout wake render as 「已由 <uid> 回复」. A card click answers through the same authorization split: the owner's click works in any chat, a member's only while the question's chat is an enabled group/thread, and every other click is acked and dropped with no effect. A wait longer than the configured `ask.timeoutMs` (default 6 hours; 30 minutes to 7 days per `src/config.ts`) never expires the question: the rows stay pending, their cards stay submittable, and the turn waiting on them is stopped the way a cancelled tool call stops it — the task settles `interrupted` and nothing is sent to the chat. The owner's later answer is recorded and delivered as new input for that chat (a running turn takes it as steering, otherwise it becomes a durable task), so the agent continues in the same session from where it halted. When the deployment announces `octo/v2` with interaction enabled the questions are delivered as interactive cards instead: a single question keeps a frame of its own (one button per option for a single choice, each button its own body `ActionSet` row so the client stacks the buttons vertically instead of clipping one shared row, its title bounded to the card width while the full label stays in the numbered lines, leaving only the free-form submit in the card's action area; a choice list for a multiple choice, a free-form field otherwise — every option question also carries a free-form field that wins over the selection when filled), while several questions share one card with per-question inputs and a single submit that records one compare-and-set per filled question inside one transaction and re-renders the rest behind fresh action ids; the text path and the card path share one answer compare-and-set and neither one replaces the other, and a set frame the deployment cannot carry (no interactive profile, over its limits, a failed send) falls back to asking its questions one at a time (`src/ask-card.ts`, Bot event queue below). With no persisted owner, the first valid private message claims ownership, is durably deduplicated, and only receives confirmation; it does not execute that message. Host tools are assembled per task: `ask` and `octo_send_file` everywhere, `octo_management` only in groups and threads, and `channel_control` everywhere — its `restart` asks the detected supervisor to restart this process once the channel is idle (so the asking turn still delivers its reply, which is what makes self-iteration possible), and its `status` reports the channel PID, running targets, queued tasks, blocked directories, and whether a restart is pending. `octo_management`'s `create-thread` accepts `worktree_name`: the host materializes a git worktree beside the calling chat's repository (directory and branch named after it, so the name must contain ASCII letters or digits) — through `wt switch --create` when a compatible local `wt` (stable v0.76.x) is available, otherwise through the resolved OMP executable's `omp worktree add` — and pins the new thread's binding cwd to it (`chats.cwd_pinned`), so the thread runs in its own workspace; a workspace that cannot be created is reported as `worktree_error` while the thread stays usable, and only an explicit `/new <dir>` or `/move <dir>` replaces that directory. `thread-dispatch` also accepts the boolean `notify` (default `false`): with `true`, a dispatch that becomes a task of its own registers a completion relay on that task row, and the task's terminal state while the channel is running (completed/failed/cancelled/interrupted) delivers one bounded notice (`notify:<thread task id>`, a synthetic inbound message sent as the persistent owner with `messageSeq = 0`) to the chat that dispatched it — the notice follows that chat's append mode (steering into a running turn that accepts it, otherwise a durable task, exactly one wake), never answers a pending question, and never crosses the permission gate; the dispatching assistant decides per hand-off whether to ask for the relay, a steered dispatch has no task row and reports `notify=skipped` in the tool result and receipt, a graceful stop or restart-driven interruption is never relayed so crash loops cannot fan out into dispatching-chat turns, and a failed delivery is logged without a retry. `octo_management`'s `thread-delete` retries once on a connection of its own when the server answers with a transient storage failure (any 5xx, or the `store_failed` internal error the bot API wraps as HTTP 400) — the server's delete is idempotent, so the retry cannot delete twice — and a final failure surfaces as one single-line, ≤200-character error; other failures, such as an authorization rejection, are not retried. Its optional `force` argument applies after the server delete succeeds: a `cwd_pinned` workspace is cleaned up through `wt remove --foreground` when `wt` is available and `git worktree remove` otherwise, a dirty workspace is kept with a `force=true` hint unless `force` is given (then the uncommitted changes are discarded), a workspace that is already gone is reported as such, and a cleanup failure lands only in the receipt. `octo_management`'s `thread-merge` is the action that runs a workspace merge: it accepts the current sub-thread only (bound `cwd_pinned` workspace, deployment isolation, compatible `wt`) and has the host run `wt merge --format json` with the workspace as cwd — `target` defaults to the repository default branch, `squash`/`commit`/`rebase`/`remove`/`ff` default true (`false` maps to `--no-*`), `stage` defaults `all` — returning wt's JSON result, rejecting anything but a linked worktree, and surfacing failures as one ≤200-character line (a rebase conflict leaves the workspace in the rebase state with the target untouched); a merge whose default pipeline removed the workspace also schedules that thread's archive (`archive: "scheduled"` beside the merge result; `remove: false` schedules nothing). `octo_management`'s `thread-archive` archives a thread on demand under the same `thread-*` addressing (a thread's own id when `short_id` is omitted), and both paths only schedule the work: any message sent into a thread reactivates it, so `CoreService` runs the archive after that chat's turn output — assistant text and the progress card's terminal edit — has drained, a new authorized inbound in that chat cancels the schedule, and the call retries five times five seconds apart on a transient failure (any 5xx, or `err.server.bot_api.store_failed`), ends at once on a permanent one, is abandoned when the channel stops, and surfaces a final failure as one ≤200-character `归档失败：…` line in the initiating chat (success leaves a service log line) — never a change to the merge result. A task that fails before its worker exists is reported by class rather than by one fixed sentence: `TaskStartupError` carries a bounded code (`cwd-missing`, `session-invalid`, `spawn-failed`, `identity-unverified`, `watchdog-unavailable`, `not-ready`, `exited`, `handshake-failed`, `session-dir-missing`), `src/task-failure.ts` maps it (bundled with the startup phase) to the class `context`/`binding`/`worker`/`generic`, and the failure lands as one `[task] 启动失败 …`/`[task] 执行失败 …` log line plus a task row of the form `<class>（<code>）：<bounded single-line reason>` while the chat gets the class sentence — `群说明读取失败，未启动任务。`, `任务未启动：绑定的工作目录或会话不可用（<code>）。`, `任务未启动：OMP 运行进程启动失败（<code>）。` or the unchanged `任务执行失败；未能可靠完成。` A freshly spawned worker gets 30 seconds to become ready (a cold OMP start on a loaded machine can take tens of seconds); `startupTimeoutMs` overrides that budget per deployment. The parent-death watchdog handshakes under that same startup budget: its ready marker must arrive within `startupTimeoutMs`, and a failed start is reported as `watchdog-unavailable` with a bounded detail line separating a spawn error, an early exit (carrying its exit code and a bounded stderr excerpt), an stdout read failure, and a ready timeout; the failed watchdog child is killed and awaited, and the freshly spawned OMP child it was guarding is then stopped before the error surfaces.
- `ChannelStore` opens `channel.sqlite` under `stateDir` with SQLite WAL/foreign keys. It persists owners, the runtime-enabled chat set (`allowed_chats`), bindings, inbound claims, tasks (including each dispatched task's completion-relay fields), outbox records, questions, progress-card rows, the worker ledger, and the Bot event-queue cursor. Durable acceptance precedes side effects; after a task crosses the `started` boundary, restart or reconnect must not automatically rerun it.
- The OMP worker is split by concern: `src/omp/index.ts` launches the installed executable with an explicit RPC mode, yolo approval mode, cwd, and session directory and owns the worker/factory seam, `src/omp/rpc.ts` decodes v1/v2 stdio frames, `src/omp/process.ts` owns process-group signals, bounded waits, and the parent-death watchdog, `src/omp/profile.ts` resolves the OMP profile, root env files, session roots, and the worker environment allowlist, and `src/omp/events.ts` folds RPC frames into `WorkerEvent`/`ExecutionEvent` including the bounded tool summaries. Keep those layers isolated from host lifecycle and signal handling. Worker cancellation uses bounded process/group shutdown and watchdog bookkeeping.
- `src/project-session.ts` validates session headers, canonical cwd, session IDs, and `previousSessionFiles` breadcrumbs. Native `/move` preserves session identity; external recovery accepts only an exact, uniquely verified session rather than a recent or fuzzy file match.
- Assistant output is cumulative per assistant message: stable local/remote IDs, immediate first nonempty create, serialized edits throttled to one second, authoritative final snapshots, and stable segments of at most 3,000 UTF-8 bytes that cut at the last natural boundary inside the segment's own window (paragraph/newline > sentence-end punctuation > comma > whitespace, hard cut only when that window has none), so an already-cut segment never moves as the stream grows. Do not merge separate assistant messages or let an older snapshot overwrite a newer one. Delivery failures stay bounded: an item is retried with the transport's own backoff shape (1s doubling to a 30s cap, jittered downward), a successful send or newer content resets its attempt count, and a permanent error or a spent attempt budget marks the row `dead` with the real bounded reason (one log line, `last_error`) so the queue head always moves on to later messages.
- `src/group-history.ts` holds the pure group/thread history accounting: live coverage buffer, `POST /v1/bot/messages/sync` fetch planner, window selector, prompt-block renderer, and the 「这个」 candidate query. `CoreService` records every group/thread inbound sequence before the permission gate, pages the server only when the live buffer cannot prove coverage of `(watermark, S)`, stamps one `message_seq` per accepted task, and keeps a per-session `group_history_ledger` watermark in SQLite so already-injected messages are never sent twice. Media-bearing messages are full history entries: live recording and server backfill both keep the attachment's kind, name, size, and absolute http(s) URL (unusable references stay out), they render as `[文件 名称 (大小)]`-style markers, and history itself never downloads. A failed page leaves the turn without history and holds the watermark. Enabled by default via `groupHistory`.
- `src/attachments.ts` holds the pure inbound-attachment helpers: `attachmentDirectory`, `safeAttachmentName`, `composePromptText`, `formatBytes`, `AttachmentError`, and `sweepAttachments`. The transport maps each inbound `payload.type` to text plus attachment references; `CoreService` downloads them under `<stateDir>/attachments/<channelType>-<channelId>/<messageId>/` at one assembly point (after the permission gate and any pending-question answer, before steering and task acceptance) and folds absolute paths into the task text; a command path takes resources exactly when it consumes the message body: `/thread <任务>` and `/queue <文本>` assemble their command argument, a registered handler assembles the whole message (an intercepting one sees the assembled body, an observing one accepts the assembled body as its task text), while control commands that never hand a body to the agent (`/status`, `/new`, `/mode`, `/cancel`, …) and the pending-question answer path download nothing. `supported` is `true` for text-shaped payloads (types 1, 14, 17) even when the text is empty — a bare `@bot` still runs an ordinary turn — and otherwise only when text or a usable attachment was extracted, so unusable media and out-of-table types keep the explicit "unsupported message type" refusal. A reply also runs the same type table over the payload the client inlined in `payload.reply.payload`: the quoted text becomes an `[引用 <sender>]` block and the quoted media joins this message's attachments (deduped by absolute URL), while `supported` still follows only the message's own payload; quoted media that carries no text of its own still renders the bare `[引用 <sender>]` heading so the assistant knows where the files came from. An authorized group/thread message that itself carries no attachment and no usable quote is matched against the history buffer (the 「这个」 contract): exactly one media-bearing message from the same sender within 10 minutes, with absolute-URL attachments only, is treated as the referenced file and run through the identical download path with a `[系统提示]` provenance line; zero candidates keeps the previous behavior, several candidates fetches nothing and instead lists the recent names asking for an explicit quote, a failed associated fetch degrades to a plain-text note instead of a refusal, and DMs, disabled `groupHistory`/`attachments`, other senders' files, and out-of-window files never associate. Attachments are only ever reached behind the owner/allow-list/mention gate, bounded by `attachments.maxBytes` (25 MiB default) with a per-message count and time budget, and swept after 14 days at startup. Voice messages are transcribed through the Octo bot voice endpoint, best-effort.
- `src/worktrunk.ts` is the Worktrunk seam: `probe` accepts only a stable v0.76.x `wt` (found on PATH or in the usual install locations, version output quoted and parsed), and the module builds the `wt switch --create`/`wt merge`/`wt remove` argv the port uses, parses wt's JSON results, and keeps every failure a single bounded line.
- `src/worktree.ts` creates and removes isolated thread workspaces and runs their merges: with a compatible `wt` it creates through `wt switch --create <branch> --no-cd --format json --config-set worktree-path=<candidate>` (project hooks from `.config/wt.toml` run the way wt runs them; the host never passes `-y`), falls back to the resolved OMP executable's `omp worktree add` (clone-first, so ignored files like `node_modules` come along) when `wt` is missing or reports an unsupported version (a `wt` create that fails or times out surfaces as the failure it is, never a silent switch to the OMP path), removes through `wt remove --foreground` or `git worktree remove`, and merges through `wt merge` (no fallback). Directory and branch come from the caller's `worktree_name` slug, stepping aside to `<slug>-<shortId>` when taken; names without ASCII letters or digits are rejected, commands are bounded, and failures are reported as single-line, 200-character-bounded errors. `runService` wires the port; the test harness injects a fake.
- `src/config-writeback.ts` keeps the config file's `allowedGroupIds` in step with a runtime grant: it re-reads the file at write time, appends only that array, and replaces the file by an atomic same-directory rename that preserves the original mode. `runService` wires the port from the resolved config path; a failure only costs the mirror, never the durable grant.
- Progress cards are split by role: `src/execution-tracker.ts` owns `ExecutionTracker`, the safe execution snapshots, and their durable encoding, `src/execution-render.ts` owns the card element factories and formatting, and `src/execution-card.ts` assembles them into an AdaptiveCard. Real tool/turn/todo/run events feed one editable progress card per user round: a task and every message appended to it each open their own card at the first real tool progress, and an appended message closes the round it interrupted so the live card always sits below the newest message. The subagent section is driven by OMP's own `subagent_lifecycle`/`subagent_progress` frames (`subagent_start`/`subagent_update`/`subagent_end` events), never by a tool name: the child's state comes from the lifecycle status, its id/agent/description from the payload, and a child the run ends without a terminal frame is settled by the run's own outcome; the card tracks the overall state and the child's current tool/tool count, so its rows carry no per-child clock or duration, and a deployment that cannot stream those frames simply renders no subagent section. The card's todo list is its contract and the execution trace is a rolling log, so the fit search sheds trace rows and the hidden-row budget first and only then shrinks the visible todo band; a trimmed band stays centred on the handoff (pinned `in_progress`/`blocked` tasks, growing outward from the first open task, completed side first), its expandable hidden rows are the omitted tasks nearest that band, and a phase renders only when it has a rendered child row. Rich trace rows carry the step's local `HH:mm:ss` start time; the compact history rows are single text lines, and both sections render them inside a grey emphasis band — the trace's omitted steps stay a sibling of `timeline_detail` (a filled Container directly under `#timeline_detail` is repainted by the web client as a failed-step red chip) and each finished subagent renders once, in the subagent band. Without `Action.ToggleVisibility` the band stays visible instead of folding away. Capability and payload limits are checked against the wire envelope (card plus frame fields) before sending a card, and card failures must not block text delivery: a body the deployment's edge refuses (`src/octo/http.ts` marks a 4xx whose response is not a bot API error envelope as `non-bot-API response body`, leaving `code` undefined) makes that round retry through `stripCardSummaries` — the same snapshot without the tool/subagent step summaries — and keeps that shape for the rest of the round, terminal edit included. `encodeExecutionSnapshot`/`restoreExecutionSnapshot` own the durable card payload: each card keeps its own row (bot, task, message id) with its message id, sequence, and last snapshot, deleted once that card's terminal edit lands, so every card a restart left open gets one terminal edit from the next process instead of leaving the client on the last running state.
- `src/ask-card.ts` builds the interactive `ask` frames — one question (option buttons — each its own body `ActionSet` row so the client stacks them vertically instead of clipping them in one row, titles width-bounded with the full labels in the numbered lines — and/or a free-form `Input.Text`, plus a submit) or a whole set on one card with per-question inputs (`ask_choices_<n>`/`ask_text_<n>`) and a single submit — decodes the action id of a click back into options or a set submission, turns card inputs into the same answer strings a text reply produces, and renders the answered line with its submitter — the uid resolved to a display name, rendered as a bold `TextRun` (`weight: Bolder`, so the emphasis is the run's own style; measured on the real client 2026-09-19), with the uid itself as the fallback when the name is unknown, and `已回复` for a row written before attribution. The card is one answer path, never the only one: `CoreService` falls back to plain text questions when a frame cannot be sent, and a text reply answers the same questions. `src/bot-events.ts` consumes the Bot event queue for clicks — `POST /v1/bot/events` long poll with a persisted monotonic cursor, ack only after the answer is durable, unknown event types acknowledged and skipped, and a missing endpoint stopping the poll loop.
- `src/octo-cli.ts` gives each bot its own `octo-cli` credential: after the Bot registers, `provision` writes the token through stdin into `~/.oco/octo-cli/<botUid>` (0700) and publishes `OCTO_CONFIG_DIR`/`OCTO_API_BASE_URL`/`OCTO_BOT_ID`, which `workerEnv` passes to OMP children through an allowlist while the host's own `OCTO_*` stay stripped. A missing or failing CLI only costs the agent that identity; tasks then fall back to the host tools alone. Every task can therefore call `octo-cli` as this bot, including endpoints no host tool wraps.

## Key Directories

| Path | Purpose |
| --- | --- |
| `src/` | Production CLI, service orchestration, contracts, configuration, persistence, session handling, and presentation. One file per concern: cross-cutting helpers at the top level (`target.ts`, `workdir.ts`, `errors.ts`, `abort.ts`, `bot-lock.ts`), one subsystem per module, and a facade where callers should not see the internals (`store.ts`, `execution-card.ts`). |
| `src/octo/` | Octo transport split by layer: `index.ts` (connection and outbound operations), `protocol.ts` (encrypted framing), `content.ts` (inbound normalization and uploads), `http.ts` (HTTP bodies, deadlines, media), `api.ts` (Bot management endpoints), `cards.ts` (card capability and Bot events), `error.ts`, `type-guards.ts`. |
| `src/omp/` | OMP worker split by layer: `index.ts` (worker and factory lifecycle), `rpc.ts` (v1/v2 frame decoding), `process.ts` (process groups and the parent-death watchdog), `profile.ts` (profile, env, session roots, worker environment), `events.ts` (event folding and tool summaries), `context-extension.ts` (the fixed OMP extension). |
| `tests/` | Behavioral, integration, lifecycle, transport, persistence, streaming, recovery, and boundary tests. |
| `tests/fixtures/` | Deterministic fakes plus HTTP/WebSocket and real-child-process protocol fixtures. |
| `docs/specs/` | Confirmed product and architecture specification. |

## Development Commands

Install and run the standard checks:

```sh
bun install
bun run typecheck
bun test
```

Create a local configuration and exercise the service:

```sh
bun link   # installs both bin names (~/.bun/bin/oco → this checkout)
mkdir -p ~/.oco/config
cp config.example.json ~/.oco/config/config.json
chmod 600 ~/.oco/config/config.json

```

`check` validates configuration, Bot registration, and an OMP fresh-worker start/stop path; it deliberately does not call a model. `start` runs the service in the foreground — it is what a supervisor hosts — while `run` is the same process without supervisor participation (no detection, no restart port), for debugging. The default config path is `~/.oco/config/config.json`; service logs land in `~/.oco/logs/`. The package also keeps `bun run check` / `bun run start` / `bun run launchd` scripts as an install-free path.

Day-2 operations go through the same entry point, with the supervisor and program detected from the checkout:

```sh
oco restart            # super -y restart --wait-healthy + PID comparison
oco status             # supervisor state, PID, uptime, config and log paths
oco logs --tail 200    # service-owned log file; -f follows across midnight
oco test --card        # live preview card (applies ./.envrc first)
```

For macOS launchd:

```sh
oco launchd install --config ~/.oco/config/config.json
launchctl bootstrap "gui/$(id -u)" "$HOME/Library/LaunchAgents/com.omp.channel-octo.plist"
```

`launchd install` writes a private plist and does not call `launchctl`; loading and unloading are explicit operational steps. The generated plist runs `start` and writes its stdout/stderr into `~/.oco/logs/`.

The resident service on this host is managed by Super: the stack at `~/.super/conf/conf.d/omp-channel-octo.toml` runs `bun run src/cli.ts start --config ~/.oco/config/config.json` from the checkout, with `OCTO_BOT_TOKEN` sourced from `.envrc`. The private config holds the live values and `config.example.json` is only the template they are copied from. Apply stack edits with `super apply -f ~/.super/conf/conf.d/omp-channel-octo.toml`, then use `oco restart` to restart the service and wait for it to report healthy. Nothing about the supervisor or the program name lives in the channel config: both the CLI and the service detect it (`src/supervisor.ts`).

## Code Conventions & Common Patterns

- Use strict TypeScript contracts from `src/contracts.ts` and explicit dependency injection through `createChannelService`, `createOctoTransport`, `createWorkerFactory`, and option interfaces. Keep transport, persistence, worker, and presentation seams independently testable.
- Keep explicit `.ts` import extensions and follow the ESM/Bundler configuration in `tsconfig.json`.
- Validate untrusted config, protocol frames, message metadata, paths, and tool results at their boundaries. Use type guards and bounded body/frame sizes instead of assuming external shapes.
- Use `AbortSignal` and bounded deadlines for network activity, typing/card operations, worker cancellation, and shutdown. Pair resource ownership with `try`/`finally`; preserve the original error when rolling back a store transaction.
- Route state changes through `ChannelStore` transactions and persist durable acceptance, desired outbox versions, and stable client IDs before network operations. Reconnect recovery resumes delivery; it does not rerun an already-started task.
- Serialize by normalized realpath and chat target. A move holds both source and target directory leases, and a directory remains blocked until worker termination is confirmed.
- Treat command paths as data, not shell input. Apply the existing absolute/`~/` path rules and realpath normalization; do not add shell expansion or a second path parser.
- Keep user-visible errors and progress summaries safe and bounded. Never expose tokens, raw tool arguments/results, model thinking, or protocol payloads in logs, cards, or group output.
- Keep the OMP RPC compatibility decoder in `src/omp/rpc.ts` separate from host lifecycle/signal handling and retain its complete upstream MIT license. Do not clear global signal listeners to solve worker conflicts.

## Runtime/Tooling Preferences

- Use Bun as the runtime, package manager, and test runner. The package is ESM; `bun.lock`, `bun-types`, and the `#!/usr/bin/env bun` CLI establish this convention. Node-compatible APIs are imported from `node:*` while executing under Bun.
- TypeScript targets ES2022/ESNext with Bundler resolution, strict checking, `noUncheckedIndexedAccess`, and `exactOptionalPropertyTypes`. `tsconfig.json` includes both `src/**/*.ts` and `tests/**/*.ts` and emits no JavaScript.
- Use the installed `omp` executable, or pass `--omp-command` for a validated executable path. OMP stays in a child process over stdio RPC; do not load the full OMP runtime into the service host.
- Credentials come from a private config `botToken` or a `botTokenEnv`, never both. Environment credential names must use `OCTO_` or `OMP_CHANNEL_OCTO_` prefixes; keep `.envrc`, local config, state, SQLite, and logs out of version control and never echo token values.
- `stateDir` is created with private permissions and contains SQLite/outbox/runtime data. The sample defaults are in `config.example.json`; `src/config.ts` normalizes the API URL and local paths. OMP sessions live under `sessionsDir` (default `~/.oco/sessions`), one directory per project — the task's canonical cwd, named `<basename>-<path digest>` — so different chats and isolated thread workspaces never share a session folder; a deployment that omits the key falls back to the pre-isolation `<stateDir>/sessions` root, which stays in the recovery roots either way.
- `package.json` has no build or lint script. The supported compiler check is `bun run typecheck`; use the repository's existing scripts rather than introducing an unrecorded toolchain.
