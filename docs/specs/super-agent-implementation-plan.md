# Super-agent 功能建设计划

关联路线图：[super-agent-roadmap.md](super-agent-roadmap.md)

## 用户原始需求

1. 「结合 @docs/specs/super-agent-roadmap.md 和 https://github.com/deepseek-ai/dsh-superagent-prototype (deepseek 刚发布的 super agent 构想/原型) 看下roadmap 有哪些需要调整的？以及对于我们有哪些启示、路线指引」
2. 「将以上的信息、建议、方向、待做事项、最新进度，等等都更新到 roadmap 中」
3. 「可以给我一个具体的推荐计划吗？单独文件，结合当前项目进行具体的实现路径规划(分阶段)」
4. 「跟 super-agent roadmao 同级目录不，不加时间前缀」
5. 「为啥我看着实现计划这么抽象呢？我要有清晰的待办和阶段目标，不是写个所谓的 P1/P2/P3 这个可以阶段内部做」
6. 「router 在里面有体现吗？decisions 在里面能起到什么作用？为啥还是这么抽象？每个阶段到底能解决 super agent 哪方面问题？达到了能实现什么效果？最终是一个什么效果和愿景？验收不验收的不重要，我需要一个 feature list 清单，不是让你写 spec，那是具体做的时候的事情」：本条明确计划以功能、用户效果和路线为中心，具体规格与验收留到实施时处理。
7. 「按你说的进行调整」：根据可行性审查收紧恢复、总览范围和证据归属，明确外部事件的生命周期及 Router、Decisions 的边界。

## 最终愿景：一个能持续协同的助手

用户在 Octo 群里提出目标，助手能够理解并拆分工作，在适合的子区持续推进；用户可以随时到子区讨论，也可以留在父群看全局。后续属于同一项工作的 Loop 变化、PR 评论和 CI 结果，能够回到正确的工作现场。需要用户决策时助手提出具体问题；工作完成时，它拿得出实际交付证据。

例如：

1. 用户说：“把登录问题修好，同时调查导出超时。”
2. 父群助手判断这是两项独立工作，创建两个子区并派发；各子区在自己的工作空间和会话里推进。
3. 登录修复需要确认兼容范围，子区向用户提问。用户在父群问“现在有什么需要我处理”，能看到这个问题并进入对应子区回答。
4. 登录修复产生 PR，后续经授权的 review 评论被送回原子区；执行者处理评论，父群不被每条评论打断。
5. 用户问“登录修复合了吗”，助手根据宿主或平台记录回答实际状态，并给出可追溯的 PR、提交或合并信息；无法证实时明确说不知道。
6. 用户问“导出调查是不是卡住了”，助手结合待答问题、执行状态和最近可用证据回答；仅仅长时间没有消息，不算卡住。

**最终体验：一个入口掌握全局，多项任务各自在合适的上下文中持续推进；助手只在用户需要决策或能使用结果时打扰。**

这是目标体验，不表示当前能力已经全部实现。默认不意味着助手可以读取所有群、自动处理所有外部事件或自行扩大权限。

## Router 和 Decisions 分别做什么

### Router：决定“这条信息交给谁、走哪条路”

Router 在本项目中首先是一种**协调职责**，不是先增加一个全局 agent 或服务。它分为宿主确定性路由和父群 agent 的语义协调：

| 信息 | 推荐去向 | 决定方式 |
| --- | --- | --- |
| 用户在父群提出新需求 | 父群 agent 理解、澄清、拆分和派发 | agent 结合用户意图和当前群上下文判断 |
| 用户直接在子区补充要求 | 当前子区和它的会话 | 已有聊天目标和授权直接确定 |
| 已有明确 Loop task—子区路由的变化 | 对应子区 | 宿主按持久路由确定，不经过父群模型再猜一遍 |
| 已授权订阅的 PR 评论 | 已绑定该 PR 的工作子区 | 未来由宿主按订阅和权限确定；引用本身不等于订阅 |
| 不明确属于哪个任务的输入 | 在授权范围内交给父群协调 | 父群 agent 判断是否需要澄清或派发 |
| 用户问全局进度 | 查询宿主已有记录，由父群 agent 组织回答 | 只读查询；不唤醒全部子区 |

**已具备的 Router 基础**：父群通过 `octo_management` 创建子区并派发；Loop 规格已有基于 task 路由和负责人身份的确定性分流；子区也可通过 `thread-send-parent` 显式向创建方输入。具体部署是否运行这些能力需另行核验。

**需要建设的 Router 能力**：先让父群看得到有可靠关联的任务，再逐步补齐工作身份、跨轮次关联和已授权的外部事件直达。只有明确身份或可靠关联才能直接路由；关系不明时由父群 agent 按需读取上下文并澄清。是否引入独立 Router 模块，以现有 service/host-tool 边界是否真正放不下为依据，而不是本计划的前提。

### Decisions：解决“已有数据仍需做窄语义判断”

Decisions 是 channel 调用的外部决策服务，适合回答有固定选项的小问题；它不等于 Router，不负责执行工作，也不授予权限。

| 用途 | Decisions 判断什么 | 判断后谁做事 | 状态 |
| --- | --- | --- | --- |
| PR/MR 引用识别 | 子区消息里的候选链接是否是当前任务的直接工作对象，而不只是参考 | 宿主按既有门槛保存本地 reference | 规格记载已实现并离线验收；实际启用取决于配置 |
| 语义 watch | 用户要求关注的条件是否已被采集结果满足 | 宿主在首次命中时向所属聊天受理独立续办任务 | 规格记载已实现并离线验收；需显式创建 watch |
| 待分类的外部事件 | 一条评论是否与某项已有工作有关，或应交协调路径 | **未来候选**：宿主先完成身份、订阅和权限门禁，再按确认的设计使用结果 | 尚未形成此项产品合同 |
| 长任务进展判断 | 有界证据是否表明需要人介入 | **未来候选**：先用确定性事实；只有实际需要且单独确认后才考虑 Decisions | 尚未承诺 |

**使用原则**：已知 task ID、显式路由、状态字段和停止意图能确定的事，由宿主直接判断；没有可靠归属时，父群 agent 按需读取上下文并协调。只有存在可独立定义、可测的窄语义分类问题时，才考虑调用 Decisions。判断失败或不确定时保持未知。Decisions 的结果是证据或建议，不是权限、事实证明或自动执行授权；provider 费用、数据外传和错误判断均需在具体能力设计时考虑。

## 阶段一：让助手一直可联系、可控制

**解决的问题**：一个子区在合并、下载附件或等待工作区时，不能让整个 Bot 像失联一样，也不能让取消命令排在卡住的操作之后。

### Feature list

- [ ] **消息独立受理**：一个聊天的慢操作不挡住其他聊天的新消息；消息是否已可靠接收有明确状态。
- [ ] **长操作期间可查状态**：一个子区运行 merge 时，用户仍能在其他聊天查询或继续交流。
- [ ] **长操作期间可停止**：用户能按现有权限和目标范围发起取消；停止失败或进程状态未知时明确告知。聊天级 watch 独立于源任务，停止源任务不自动停止 watch。
- [ ] **附件接收不堵全局**：大文件下载和转写在后台进行；其他聊天仍可交互。
- [ ] **重启后按原状态恢复**：区分尚未派发、已接受、接受不明和用户停止；可确认的已接受任务继续原会话，无法确认的结果如实保留，不盲目重复执行。
- [ ] **低打扰交付**：默认只在宿主确认合并成功后通知创建方；普通进度、合并失败和修复过程留在子区。用户仍可显式调整 listen。

**用户感受到的效果**：助手执行一项长任务时仍然能接收其他需求；需要停止时能找到控制入口，不必靠重启碰运气。

**项目落点**：以已有 `src/inbound/ingress-coordinator.ts`、`src/octo/index.ts`、`src/service.ts` 和现有非阻塞入站规格为基础，补齐尚未完成的边界和整体验证；通知复用 `src/threads/thread-notify.ts` 与既有 listen。现有规格标记整体尚未验收完成，代码已有部分实现。

## 阶段二：父群能看见关联的工作

**解决的问题**：父群知道自己派过任务，但目前没有一个可靠的总览，用户得逐个进入子区找进度、找问题。先覆盖有可靠创建关系的直接子区，不把不完整记录宣称为全部相关工作。

### Feature list

- [ ] **工作总览**：父群查询自己直接创建且关系可靠的子区及其持久 channel task，看到名称、任务目标、状态和记录时间；明确说明查询范围。
- [ ] **需要我处理**：将待回答的问题放在前面，按问题的精确 task ID 归属，显示对应子区和具体任务，方便用户跳转处理。
- [ ] **运行与排队列表**：区分正在执行、等待执行、失败、已结束；不让模型根据闲聊猜进度。
- [ ] **追加要求的呈现**：steering 可能并入已有回合而不是形成独立 task；缺少可靠持久关联时不伪造独立任务或声称已列出全部追加要求。确有需求时再补输入身份和消费记录。
- [ ] **空结果和未知状态**：创建关系缺失、子区不可访问或信息不完整时如实显示；不把空数据当作任务成功。
- [ ] **分页和按需读取**：子区多时可继续查询，不一次把所有任务正文和历史塞进父群上下文。
- [ ] **限定可见范围**：只查询当前聊天直接创建且调用者有权读取的工作；bot 可进入群不等于群成员都可读取所有子区内容。实施前确认成员可见范围，并在查询时按调用者和资源权限过滤。
- [ ] **Router 的全局视图**：父群 agent 在拆分新需求或回答进度问题时可先查现有工作；该视图有明确范围和缺口，不能保证识别所有已有工作。是否相同仍由 agent 结合上下文判断。

**用户感受到的效果**：问一句“现在有哪些事需要我”，得到例如“登录修复：等待你确认兼容范围；导出调查：执行中；文档更新：已结束”，并能定位到相应子区。结果说明仅覆盖当前聊天直接创建且有可靠记录的工作。

**项目落点**：围绕 `src/host-tools.ts`、`src/store/store-thread-listen.ts`、`src/store/store-tasks.ts` 和 `src/store/store-questions.ts` 增加只读查询。现有 `list-threads` 有远端结果截断；`thread-info` 可能建立 listen 记录，不能直接等同于严格只读总览。建议扩展现有 `octo_management`，具体接口在实施时确定。

**本阶段 Decisions 的作用**：不用于判定任务状态或是否有待答问题；这些已有持久事实。父群 agent 可以理解用户查询，但不需要额外增加 Decisions 调用。

**进入实施前需确认**：父群成员是否可以读取关联子区的任务目标、问题和结果；不能仅按 bot 的群许可决定调用者的读取权限。跨子区创建链的递归汇总按实际需求后续确定。

## 阶段三：让助手知道“这项工作交付了什么”

**解决的问题**：看到“任务完成”仍不知道是否提交、PR 是否存在、是否合并，也不知道一个 Loop 任务和多次执行如何对应。

### Feature list

- [ ] **工作详情**：从总览进入某项执行，查看其所属子区、精确关联的问题和已有结果。
- [ ] **子区级 Loop 关联**：展示有明确记录的 Loop workspace/task 与当前子区路由；当前路由不证明该子区所有历史执行都属于该 Loop task。
- [ ] **子区级 PR/MR 引用**：展示子区已绑定的工作对象，提供引用入口；现有 reference 归属子区，不天然归属某个 channel task，也不证明远端对象存在或已订阅。
- [ ] **子区级合并证据**：展示宿主记录的子区合并结果；现有 merge event 不携带具体 task ID。除非有独立证据，不把一次子区合并归给某个任务。
- [ ] **跨轮次和交付归属**：仅在持久来源能证明关系时，将同一业务工作的执行、PR/MR 和交付关联；缺失时显示未知。确有需求时增加最小工作身份和明确关联，记录来源与时间；不预先照搬通用 Ticket 状态机。
- [ ] **非代码交付**：调查、文档等工作可展示可定位的报告或其他已有产物，不强制要求 Git merge。
- [ ] **Router 的归属依据**：父群收到“继续处理刚才那个 PR”时，能先查已有引用和任务关联；有明确且唯一的目标才建议交还对应子区，关系不明或存在多个候选时澄清。

**用户感受到的效果**：问“登录修复合了吗”，助手能回答“这个子区有一次宿主确认的合并，但现有记录不能证明它包含登录修复”，或在存在精确关联时给出实际合并证据。不会把“子区合过”或“代码写完”说成“该任务已经合入”。

**项目落点**：复用阶段二入口，组合 `src/store/store-loop.ts`、`src/store/store-references.ts`、任务记录与 `thread_merge_events`。先按子区如实展示现有事实，再通过真实多任务、多轮次场景确定是否增加工作身份与精确关联。

**本阶段 Decisions 的作用**：复用已有 PR/MR 直接工作对象识别，辅助建立本地 reference；既有判断未完成时不补扫或跨重启恢复，因此没有 reference 不能证明没有 PR。它不能证明 PR 存在、测试通过或合并成功，这些需要实际记录或平台数据。

**阶段四前的关键依赖**：对所选外部来源，必须能确定一个有效订阅及其目标子区；如用户需要精确到业务工作，还须先有可靠的工作身份与关联。不能用模型猜测填补身份缺口。

## 阶段四：外部后续事件自动回到原任务

**解决的问题**：PR 评审、CI 或 Loop 状态变化出现后，用户不应该把内容复制到原子区，再解释一次背景。

### Feature list

- [ ] **选择首个真实来源**：推荐先评估 GitHub PR 评论，因为直接关联代码交付；如果当前 Loop 跟进更常用，则先做 Loop。一次只选一个来源完成闭环。
- [ ] **明确订阅**：让有权的用户或其已授权操作明确指定哪些外部对象需要跟进；现有 PR reference 不自动等于订阅。
- [ ] **Router 直达**：已订阅对象的后续事件经来源与权限确认后，直接送到绑定的子区，而不是先打扰父群再派发。
- [ ] **区分信息和指令**：外部评论、CI 日志或 Loop 变化作为带来源的输入；是否可以因此启动工作由订阅授权决定，不自动扩大权限。
- [ ] **处理无法确定的归属**：没有有效订阅或存在多个可能目标时，不向所有子区广播；按确认的授权范围交给父群协调或等待用户指定。
- [ ] **工作状态与订阅生命周期**：区分正常等待 review、用户明确停止、子区已归档但 PR 仍在进行；分别决定后续评论只记录、提示用户，还是在授权下继续工作。是否允许归档子区被事件重新激活，须在实施前确认。
- [ ] **停止与解绑生效**：用户停止任务、取消订阅或撤销授权后，后续事件按已确认规则处理，不自行让已停止的工作重新开工。
- [ ] **避免重复处理**：平台重复发送、重连或 channel 重启后，同一事件不应变成多次独立执行；接收结果未知时不盲目补发。
- [ ] **父群保持安静**：子区处理评审过程，父群沿用 listen 只收到应关注的结果。

**用户感受到的效果**：在用户明确订阅、授权继续处理且目标仍符合订阅规则时，PR 收到“请补一下超时处理”的评审评论，原子区带着原来的代码和会话继续处理；用户不用复制评论或重复交代背景。

**项目落点**：Loop 已有 workspace 快照和明确 task 路由，可继续复用；PR/MR 当前已有本地引用识别，但没有由此自动建立的评论订阅。首个候选场景是明确订阅的 GitHub PR review 评论；需要另行建设来源身份与 API 接入、订阅授权、事件去重、生命周期及恢复。具体规则在实现时确认。

**本阶段 Decisions 的作用**：明确的对象 ID 和订阅直接路由；只有一个已获准处理的事件仍存在语义歧义时，才可考虑用 Decisions 辅助判断相关性或建议交回父群。它不能绕过订阅/权限，也不能单凭其判断触发有副作用的工作。

## 阶段五：助手能解释哪里需要人、是否需要干预

**解决的问题**：长任务可能等待用户、等待外部系统、正常运行很久或已经失败；用户不应靠反复打开子区和猜测来判断。

### Feature list

- [ ] **按需状态解释**：用户询问时，整理任务状态、待答问题、已知失败和最近可用证据。
- [ ] **解释等待对象**：有结构化证据时说明是等待用户回答、等待执行或已知外部依赖；缺少证据则说未知。
- [ ] **给出下一步**：能确定用户可采取的动作时，指向问题或相关子区；不把建议当成已执行动作。
- [ ] **明确诊断能力上限**：现有 started 状态和静默时长不能普遍区分正常长操作、死锁和外部 API 等待；证据不足时返回未知，不承诺识别所有卡住原因。
- [ ] **显式条件观察**：用户说“关注某条件，满足后告诉我/继续处理”时，复用已有 watch；它是一次性有界订阅，不是全局任务监督。
- [ ] **可选主动提醒**：只有出现明确需求并另行确定成本、频率、接收方与停止规则后，才考虑主动监督；默认先支持用户主动查询。

**用户感受到的效果**：问“导出调查卡住了吗”，助手可以回答“它正在等你回答是否允许访问生产日志”，或者“当前没有足够证据判断是否卡住”，而不是凭最后一条消息时间编造结论。

**项目落点**：先组合任务、问题、worker 和已有 watch 的状态；不接管 OMP 的执行循环，也不替换进程 watchdog。

**本阶段 Decisions 的作用**：优先使用确定性状态。将来若真实场景需要理解有界日志或进展证据，可单独设计语义判断；模型判断必须与原证据一起呈现，不能独自发起恢复、扩大授权或宣称失败。

## 阶段六：经授权的主动协作（按需决定）

**解决的问题**：未来如果团队希望助手不只响应明确指令，还能发现某些明确规则允许处理的工作，需要一条可控的演进路径。

### Feature list

- [ ] **规则描述**：由用户明确指定哪些来源、什么条件、允许助手做什么。
- [ ] **先观察建议**：先记录“这条事件如果自动处理会做什么”，供用户查看；观察不启动任务。
- [ ] **有限自动处理**：用户确认规则和授权后，才允许限定范围内的自动接单或执行。
- [ ] **可停止、可追溯**：用户能停止规则或任务，查看原因、来源及执行结果；外部输入不能自行创建更宽的授权。

**用户感受到的效果**：在明确同意后，助手可以处理一类重复出现的工作，而不是监视整个群并擅自行动。

**Router 和 Decisions 的作用**：宿主先按规则、身份和权限过滤；Router 决定交给哪个已有工作或协调路径；需要语义判断时可评估 Decisions。自动执行范围始终来自用户授权，不来自模型评分。

**进入条件**：有实际使用需求和可接受的成本、权限与干预边界；不作为前五个阶段的前提。

## 推荐建设顺序

1. **先让助手可靠在线**：完成阶段一的既有入站和低打扰交付能力。
2. **再让助手看见有可靠关联的工作**：建设阶段二的只读总览，明确直接创建范围、steering 缺口和调用者权限。
3. **再让助手说清工作结果**：阶段三先展示子区级事实，再按真实场景建立必要的业务工作身份与交付关联；不能把子区事件推断成任务事件。
4. **再让信息自己找到工作现场**：阶段三提供可靠目标后，选择一个真实来源建设阶段四的订阅直达，明确等待 review、停止和归档的行为。
5. **最后增加诊断和主动性**：先做阶段五按需诊断；有实际需求后再考虑阶段六。

本文件是功能清单与推荐路径，不是具体实施规格，也不是对后续阶段的实施、部署或外部写入授权。每个阶段真正开始前，再根据当前代码和用户意图细化对应合同。
