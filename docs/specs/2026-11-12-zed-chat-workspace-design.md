# Zed 聊天工作区文件导航

日期：2026-11-12

## 用户原始需求

1. 「我想要 @packages/octobuddy-enhancer/ 点击 zed 链接时，有没有办法是打开群聊/子区对应绑定cwd + 对应文件？」
2. 「不考虑旧消息」：按点击时当前聊天绑定处理。
3. 用户确认查询当前聊天绑定、打开 cwd 和链接文件、查询失败或聊天切换时提示失败：「可以的」。
4. 用户选择「使用 1.29.1 Preview 及以后版本」。
5. 「我要打开的是基于 cwd 作为项目的文件，不是打开目录又打开了单独文件」：文件必须属于该工作区。
6. 用户选择「仅接受 Zed 原生接口」，并要求真实验证。
7. 「ok, 按照这个实现」：确认实测后的 Zed CLI 双 SSH 路径方案并授权实现。

## 目标和约束

真实点击群或子区消息中的 `zed://ssh/` 文件链接时，增强器读取当前聊天的精确身份，通过已有认证状态接口获取该聊天当前 cwd；使用链接的 SSH 主机连接解析 cwd 和文件的远端真实路径，将两个 SSH 路径作为独立参数提交给 Zed CLI。目标文件须在规范化 cwd 内，Zed 以 cwd 为项目根、在项目内打开文件并定位链接中的行号。旧消息仍使用点击时的当前绑定。不同聊天不能串用绑定；聊天切换、无法查询绑定、远端路径不可解析或目标不在 cwd 中时提示失败，不打开。其他 Zed 链接、本地文件操作和普通链接保留既有行为。

远端路径解析使用本机 SSH 配置和链接中的主机、用户名和端口，不通过 shell 拼接未经引用的路径；使用非交互式 SSH，失败及不可达明确报告，不退回错误工作区。调用的实际文件路径、工作目录与行号保持原意；`#L<n>` 和 `:<n>` 转换为 Zed CLI 可识别的行号。Zed 至少需要支持多个同主机 SSH 路径的版本（1.29.1 Preview 已实测）。Zed CLI 的退出失败必须反馈；它受理请求不保证远端连接最终成功。

聊天身份使用当前通信页面提供的 `openChannel`；查询结果与页面绑定相符，查询后及派发前核对身份。用户点击、插件与页面授权、状态凭据隔离沿用既有增强器契约。不引入 Zed extension，不改变 channel 状态接口或消息投递。

## 验收标准

- 群和子区使用各自绑定，连续切换不会用旧聊天结果启动 Zed；没有绑定或状态接口失败时不打开。
- 规范路径、包含空格或特殊字符的路径、行号和 SSH 用户名端口正确；符号链接经远端解析后文件位于 cwd 项目中。文件不属于 cwd 或远端解析失败时提示失败。
- 可信点击及插件生命周期门禁仍生效；状态凭据不传给子进程；其他链接维持既有处理。
- 使用临时真实 SSH 项目和 Zed Preview 验证单个工作区、项目内文件标签及行号；以隔离 OctoBuddy 和 HTTP fixture 验证点击到状态查询、Zed CLI 参数的完整链路。

## 已验证事实

在 Zed Preview 1.29.1 和 localhost SSH 临时项目中，同一命令传入 `/private/tmp` 真实目录及其文件可显示单一项目根、项目内相对路径标签和指定行，重复调用复用窗口。使用 macOS `/tmp` 符号链接时观察到额外文件项目项。LSP `window/showDocument` 也可打开项目内文件，但语言服务器的空项目自动启动未验证；本设计采用实测 CLI 路径。

实现后的真实 localhost SSH 验证通过增强器的 `openInZed` 调用 Zed Preview：窗口只显示规范化后的 `project` 项目，文件 `src/file with spaces.ts` 在项目内打开，光标位于第 2 行。隔离 OctoBuddy 实例配合状态 HTTP fixture 验证了群和子区分别使用各自 cwd，以及被客户端清空目标的 Markdown 链接恢复。
