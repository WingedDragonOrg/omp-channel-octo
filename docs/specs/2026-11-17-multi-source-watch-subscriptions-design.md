# 多来源事件 watch 订阅

日期：2026-11-17

状态：产品设计及首批实施已获授权；部署和创建真实订阅未获授权。

## 用户原始需求与确认

1. 原始需求：“watch 是不是能力太弱了? 而且当前好像很少被 agent 使用？是否可以扩展能力范围，支持多种 source 事件订阅抽象，且支持通过不停扩展实现接入新的 watch。支持不同的资源, github://can1357/oh-my-pi/pull/19544、gitlab://dmwork/octo-marketplace/-/merge_requests/70，支持 decision 通过自然语言识别 watch 是否结束，事件是否值得消费。包括 octo://loop/ octo://groups octo://docs 等等。”
2. 目标、范围、约束和验收原文：“目标：评估并扩展当前 watch，使 agent 可通过可持续扩展的多种 source 订阅事件，既可判断 watch 何时结束，也可判断具体事件是否值得消费。

范围：调查现有 watch 的能力、实际可观测使用情况和 agent 使用门槛；分析多来源协议/资源标识、接入扩展方式、事件获取与游标、确定性事件过滤和 Decisions 语义判断、订阅与结束规则、面向 agent 的发现和调用方式。结合 GitHub、GitLab、Octo Loop、群及文档等示例，以现有授权和可用 API 为事实依据。

约束：先使用 spec-design 在子区与 owner 确认产品契约，包括通知与自动续办的授权、持续订阅的期限和成本、外部内容及模型数据外传、停止/撤权、事件去重和重启恢复；不臆造来源能力或凭据，不访问权限外资源，不绕过用户决定。现有单次语义 watch 与任务/会话隔离及进程安全合同须纳入兼容或迁移设计。设计确认后再按 owner 决定实施，不假定全部来源可一次完成。

验收：形成经 owner 确认、可实施的分阶段设计，说明具体首批来源与接入方式、事件是否消费和 watch 是否结束的判断边界、失败和权限行为，并清晰区分现状实测与推测。”
3. owner 选择有界多事件订阅：一次明确授权覆盖订阅内多个相关事件，达到结束条件、截止时间或预算后停止，不自动续期；选择自动续办：事件作为独立排队输入，在订阅时明确的原任务范围内处理，事件内容不赋予新的业务权限。
4. owner 对期限和接入方式补充：“沿用现有上限，但不一定是轮询，部分外部服务可能支持订阅或其它形式，这个是接入实现定的，不是 watch 本身，所以不应该有 5 分钟检查这个限制，并且本地怎么可能没有 glab? 且 gitlab 协议增加一层 host, 例如: gitlab://codex.mlamp.cn/dmwork/...”此项修正之前对统一轮询间隔的建议。
5. owner 选择每个订阅明确授权有界事件内容外传：创建前展示来源、服务和字段范围，仅发送过滤所需的有界内容与条件；无法获得授权时仅使用确定性过滤。首批选择 GitHub PR 与 GitLab MR；Loop、群和文档后续按 API、权限和路由合同接入。
6. owner 确认本规格的完整设计，包括第 3–8 节的首批范围、预算、恢复与权限合同；确认设计不等于授权实施。
7. 后续授权：“形成 spec 方案，并实现、验收通过”。此项授权首批实施及隔离验收。
8. 后续补充：“补全，直到完成并验收”。owner 在多页连续性决策中选择“允许尽力而为”：翻页、重叠扫描和去重，检测到缺口时报告；明确可能漏掉扫描间删除、覆盖或迟到的事件，不声称完整连续。此项替代原先要求多页无法证明时拒绝就绪的约定。

## 现状与证据

现有 `src/watch/` 是可信本机脚本或可执行程序采集 stdout，再由共用 Decisions 判断单个语义完成条件。宿主保存聊天级订阅，首次满足后产生唯一独立排队输入；源任务完成、取消或 `/new` 不停止它。脚本是已授权本机执行，不是只读沙箱。当前工具说明要求用户明确提出持续关注，确定性状态优先使用程序机制；agent 须自行构造采集器，没有第一类 source、资源或事件游标。默认 5 分钟检查、6 小时期限，最多 24 小时、300 次检查；这些是现有脚本 watch 的合同，不是所有 source 的统一时间模型。完整旧合同见 `2026-11-04-bounded-stoppable-watch-design.md`。

默认配置指向的本地状态库只读查询中，当前 bot 留存 watch 记录为零；未核实该库是否为当前聊天运行实例，也不能从留存记录推断历史创建尝试、失败率或其他实例使用情况。离线 benchmark 的已有结果证明宿主链路，不证明线上使用、模型质量或费用。脚本构造和严格触发说明是可观察的使用门槛；它们是否导致低使用率未证实。

对用户给出的 GitHub PR，公开 REST 读取成功；这不证明私有仓库访问。`gh` 可用；`glab` 实际安装在 `/opt/homebrew/bin/glab`，当前进程 PATH 未包含该目录。`gh` 和 `codex.mlamp.cn` 的 `glab` 身份检查成功，并通过该实例只读 API 读取示例 MR 70；不证明其他项目的权限。Octo CLI 身份已核对为当前 bot，但具体 Loop、群及文档资源权限未实测。GitHub 活动流与 GitLab 事件 API 各有保留、分页和覆盖限制；GitLab 文档明确部分 MR discussion note 不在 Events API 中。ETag、时间戳和普通分页位置不是通用事件游标。

只读初始化 smoke 中，GitLab 示例 MR 成功；GitHub 示例 PR 在补全来源请求期限与多页读取后返回成功（4.33 秒）。上述只证明当时的读取结果，不证明长期订阅、权限变化或跨重启交付。

参考：[GitHub events](https://docs.github.com/en/rest/activity/events)、[GitHub PR reviews](https://docs.github.com/en/rest/pulls/reviews)、[GitLab events](https://docs.gitlab.com/api/events/)、[GitLab MR](https://docs.gitlab.com/api/merge_requests/)、[GitLab notes](https://docs.gitlab.com/api/notes/)。

## 产品合同与预算

watch 是当前 bot 和真实聊天归属的持久订阅；用户明确授权后可消费多个事件。每个相关事件创建一个独立续办输入，按订阅明确的原任务范围执行；不是新的人类指令、额外业务授权、待答问题答案或当前任务 steering。结果及通知走现有聊天输出和 `listen` 规则。唤醒任务不得创建后继 watch；不能因链接存在而自动订阅。

默认期限 6 小时，最长 24 小时，绝对截止时间不因重启延长；无自动续期。有效订阅每聊天最多 5 个、每 bot 最多 20 个，旧新订阅共用配额。每个多事件订阅最多 300 次实际来源请求、300 次 Decisions 请求及 20 次独立续办，创建时可指定更低预算并显示剩余预算；网络分页请求各计一次，模型判断实际请求各计一次，受理续办计一次。派发意图持久化后即扣预算，未知请求接受不退回预算。预算耗尽禁止新增相应操作并停止继续采集，允许已扣预算的在途请求结算及已受理续办派发；显式 stop、截止和撤权仍撤销未派发工作。公开耗尽原因及未处理事件，不静默丢弃。来源请求预算不赋予统一轮询频率；来源依据自身 API 的速率限制和交付机制调度。

agent 可发现已注册来源、资源格式、事件范围、获取方式、覆盖限制、判断选项和当前配置可用性；不披露凭据。创建时展示目标、事件范围、持续期限及预算、续办任务范围、Decisions endpoint/model 与将发送的字段。语义判断涉及来源内容时须取得针对该订阅、该服务和该字段范围的明确授权；无法取得时只支持确定性过滤和确定性结束。operator 的 Decisions 配置不替代本订阅授权。无匹配来源、不可判定的资源、无权限、缺凭据或超出能力时明确拒绝，不创建伪订阅。

## 来源与扩展边界

宿主管理注册的 source 适配器，适配器声明支持的资源格式、事件类型、读取方式、权限要求、覆盖与恢复能力，负责资源解析、获取与标准化事件及其来源身份/版本。核心持久化订阅、预算、事件处理、停止与恢复；不假设适配器一定轮询。未来推送接入须单独确定接收端、认证、去重、撤销和恢复；本期不创建 webhook 或网络监听器。新来源通过受控代码注册；外部内容不能选择或加载代码、主机凭据或用户身份。

| 阶段 | 资源与方式 | 可观察范围和限制 |
| --- | --- | --- |
| 首批 GitHub | `github://<owner>/<repo>/pull/<number>` 或对应 HTTPS；只读 PR REST、issue comments、PR reviews | 对当前 PR 字段做快照比较，获取讨论评论和 review。使用现有授权身份访问私有资源；不承诺行内 review comments、CI、全部历史事件或实时完整事件流。 |
| 首批 GitLab | `gitlab://<host>/<namespace>/<project>/-/merge_requests/<iid>` 或对应 HTTPS；只读 MR 和 MR notes API | host 显式指定；项目路径和 IID 不能与其他实例混用。状态做快照比较，读取 notes；不承诺所有行内 discussion、CI 或完整历史。身份与资源授权由该实例决定，不通过更换凭据绕过拒绝。 |
| 后续 Loop | 已授权 workspace/task | 先核验实际 API、身份、快照和现有 Loop 路由；不能重复现有任务事件或绕开负责人/路由资格。 |
| 后续群 | 已授权群/子区 | 不独立抢占已有 bot event queue 或 ack；必须先设计共享消费者与权限、覆盖、恢复。 |
| 后续文档 | 已授权 document | 基于具体可用 API 确定变更覆盖及恢复；普通内容或历史分页 cursor 不等于变更订阅 cursor。 |

首批 snapshot 比较字段为状态、合并状态、标题、head SHA；comments、reviews、notes 分别以来源对象 ID 和可观察版本识别。初始建立时读取当前快照与可见事件基线，不将历史评论逐条视为新事件；立即对当前状态评估结束条件。分页未读取完或已检测到覆盖缺口时不得宣称订阅就绪或推进位置。后续状态对比仅能报告观察到的净变化，采集之间发生又恢复的中间变化可能不可见。源对象编辑、删除、分页变化、保留上限及服务端延迟按实际 API 能力报告；已检测到的连续性缺口须记录，不能报告为无变化。消费者可查询缺口及失败，不推测遗漏事件。
基线以首次采集开始为分界：基线开始前已存在的对象不作为新事件；扫描期间新增的对象作为候选事件处理。分页使用有界遍历、重叠扫描和稳定身份去重；已检测到的页序不一致、访问失败、对象丢失或预算不足须报告覆盖缺口，不能伪装成无变化。来源不提供快照 token 或可重放事件水位，因此多页扫描是尽力而为：可能遗漏扫描间删除、覆盖和迟到的事件，也不能还原两次观察之间被覆盖的版本。创建及发现入口须明确披露此限制，不得声称完整连续。
多页列表完成两次有界扫描并比较可见记录及版本，不一致时报告缺口；一致只表示两次读取一致，不代表源端提供了固定快照。每次 HTTP 请求及响应体读取合计最多 15 秒，超时与调用方取消分别报告。

## 判断、外传与处理顺序

按已授权资源和事件类型先确定性过滤；它只影响消费判断，不能阻止结束条件独立评估。事件是否值得消费与 watch 是否结束是两个独立判断，可分别采用明确字段/事件规则或自然语言。只在需要语义判断时请求 Decisions；外传仅为已授权的判断条件、必要有界事件字段与时间，不附带其他聊天、session、原始工具历史或密钥。显式披露目标 provider、模型、字段和可能的私有业务文本；模式脱敏不是完整 DLP。来源数据是不可信内容，不能修改判断规则或增加权限。
确定性结束规则使用 `endWhen: {field, equals}`，字段为 `state`、`merged`、`title` 或 `headSha`；`merged` 的值为 boolean，其余字段为 string。该规则与自然语言 `endCondition` 互斥，可在基线及后续快照观察时判断，不调用 Decisions。
发起 Decisions 前，将有效代次、截止时间、当前权限和字段外传授权检查，与请求派发意图及预算扣减在同一持久串行边界完成；stop 或已知撤权先提交则不得发起请求。派发意图先提交的请求视为在途，撤销后尽力中止并如实记录，已外传内容不可撤回。

语义结果分为肯定、否定、证据不足及失败；肯定须达到既有 0.95 阈值。失败、低置信度和证据不足不冒充否定，也不能结束 watch。未完成判断的事件及其必要证据持久保留，不推进为已处理；按剩余预算继续，无法继续则显示失败或覆盖缺口，不悄然丢弃。每个判断记录明确的状态和结果供查询。

同一个事件既值得消费又满足结束时，在同一持久边界先受理唯一续办并结束订阅，不再接收新事件；自然结束本身不撤销该事件已受理的续办。同批已持久观察到的其他事件继续完成消费判断或明确报告无法处理，不能因结束事件的排序而静默丢弃。显式 stop、到期、聊天删除或撤权在首次派发前仍可撤销续办。若仅结束则不创建续办；仅消费则维持订阅。对基线当前状态满足结束时可结束，不将基线历史当成新事件消费。

## 持久化、授权及恢复

持久保存来源规范、明确授权、绝对期限、预算、来源恢复位置、基线、每个事件身份及版本、判断状态、续办关联、终态和可查询的失败/覆盖缺口。来源对象事件身份按实例、资源、对象和可观察版本构成；快照每次观察到变化时分配持久单调转换序号，并与新快照及事件在同一事务提交，因此 A→B→A 是两次不同转换而重复恢复同一转换沿用原身份。同一订阅相同身份/版本只受理一次，独立订阅各自处理。来源位置与待判事件写入原子提交；判断完成但尚未受理续办也是持久可恢复状态，重启根据已保存结果幂等受理。已检测到分页不完整、远端返回不一致或重启期间丢失时显式标记缺口。采集结果提交、判断结果提交、续办受理和首次 prompt 派发均复核订阅代次、期限、目标及权限。

stop 先持久撤销尚未派发事件与续办，再停止来源工作和在途判断；迟到结果不能复活。到期、聊天删除及可观察到的撤权执行同样的派发前门禁。已派发续办显示 task ID，按现有 `/cancel` 及 exact-session 合同处理，不声称回滚。权限拒绝、资源不可访问或凭据失效明确终止或标记不可用，不转投父群、不更换凭据；短暂故障在来源、模型与剩余预算边界内恢复。外部系统的权限变化只有在下次可验证时被发现，不承诺即时获知。

重启恢复每个订阅、来源位置、待判事件和已受理续办；同一事件不能重复本地受理，已派发任务按原 session 的既有接受/未知语义恢复，不重放原 prompt。外部请求、模型调用和已经执行的副作用不承诺 exactly-once。来源无法恢复或覆盖断点时明确记录缺口，不伪称连续。

## 旧 watch 兼容

旧脚本 watch 的接口、单次命中、`watch:<id>` 身份、默认及检查上限、聊天归属、停止/到期、进程组/watchdog、未知进程与 cwd 保护全部保留。旧记录不自动转换成多事件订阅；旧工具调用仍可用，`/watch` 和 list/get/stop 均能管理两种订阅。旧新订阅共享配额及权限门禁，但来源实现与状态机不得削弱旧进程合同。源任务与源 session 的完成、取消、`/new`、`/reset` 不撤销订阅；受理后继续遵循现有 session 和 cancellation 约束。

## 验收

1. agent 可发现首批来源的资源格式、事件范围、约束和 budgets；未经明确持续观察及数据外传授权不能创建需要相应授权的订阅。两种 URL 均能规范化，GitLab host 不可省略或猜测。
2. 隔离 GitHub/GitLab API 夹具验证基线、状态净变化、评论/review/note、分页、重复、编辑、覆盖缺口、授权拒绝和预算耗尽；不宣称覆盖未提供的事件。使用已安装 CLI 和隔离资源验证实际接入链路；不向真实 PR/MR 写入或注册 webhook。
3. 验证消费/结束的四种组合、初始状态即结束、确定性与语义路径、低置信度/失败、同一事件消费并结束、多个相关事件独立受理；外传捕获仅含已授权字段。
4. 测试 stop、到期、删除和撤权分别与采集、判断、受理及首次派发竞态；已派发任务使用既有取消语义，pending ask 不被回答、当前任务不被 steering、listen 规则不被绕过。
5. SQLite 迁移、重复投递、分页断点、SIGTERM/SIGKILL 重启及未知接受保持本地唯一受理和原 session 合同；已检测到的覆盖缺口须报告。旧 watch 测试和真实采集进程/watchdog 重启验收保持通过。
6. 单独证明来源预算、判定预算及续办预算有界；无统一强制轮询间隔、无自动续期。测试使用本地模型替身与隔离资源，不注册常驻 bot、不调用真实收费模型，不修改真实业务数据或常驻服务。
