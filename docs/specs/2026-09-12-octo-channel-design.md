# OMP Octo 个人远程助手设计

日期：2026-09-12
修订日期：2026-09-17
状态：产品设计已确认

## 背景与目标

通过 Octo 私聊和指定群聊操作本机 OMP。使用独立于终端的持久会话，保持用户当前全自动执行习惯。channel 是常驻消息服务，OMP 是通过 stdio RPC 驱动的子进程；不依赖模型 API auth-gateway。

## 范围

包含个人单 Bot、单服务实例、文本指令与回复、执行状态、新建会话、指定目录、取消、会话恢复、消息去重和连接重建。支持私聊、指定群及 CommunityTopic 线程（channelType=5）内明确 @Bot 的指令；支持群/线程共享说明、线程默认继承父群工作目录、群/线程对话历史的增量上下文注入（详细设计见 `docs/specs/2026-09-16-group-history-context-design.md`）、线程隔离工作区的 Worktrunk 生命周期（详细设计见 `docs/specs/2026-09-17-thread-worktrunk-design.md`）、任务启动失败的分类报错与可观测性（详细设计见 `docs/specs/2026-09-17-task-startup-failure-design.md`）、常见入站消息类型的内容提取与附件接收（详细设计见 `docs/specs/2026-09-16-inbound-message-content-design.md`）、`thread-dispatch` 的派发任务完成回传（`notify` 开关，详细设计见 `docs/specs/2026-09-17-thread-completion-notify-design.md`）、出站文件和持久化问答、已开通群/子区内成员的消息驱动与 ask 卡片作答（命令仍仅 owner；详细设计见 `docs/specs/2026-09-17-group-member-participation-design.md`）。

不包含终端会话接管、多用户服务、通用网络 Agent gateway、文档评论任务、服务端通用 bot_task、群历史归档与检索、出站附件之外的通用文件托管和交互 callback 系统。channel 仅提供由 OMP host tool 明确发起的出站图片/文件发送，以及由能力 profile 明确启用的 Octo raw type17 `octo/v1` AdaptiveCard 1.5 进度展示和 `octo/v2` 交互问答卡片；交互卡片的上行只使用该 Bot 自己的事件队列（`/v1/bot/events` 轮询与 ack），不注册回调地址、不实现通用 callback 或审批流。收到的入站消息按已确认的类型表提取内容，贴纸、系统与 CMD 等没有内容的类型明确告知，不作为成功执行。范围以个人 IM 交互为准，不继承参考适配器的其他任务入口。

## 已知约束与资料

- 本机当前 OMP v18.1.21 提供 `--mode rpc`、`--cwd`、`--resume`、`--approval-mode yolo`、`--extension` 及 `session.compacting` 生命周期能力；本地兼容解码器按 v18.1.18 保持 RPC 兼容。RPC 提供 prompt、steer、abort、状态和会话事件；启动 ready 不代表模型调用可用。模型选择走启动参数、内建命令与 RPC 只读目录（v18.2.3 实测）：OMP 自带 `/switch` 内建命令（ACP 可见），选择器接受 `provider/id`、模型 id/唯一子串、`@角色`（`settings.modelRoles`）与 `:level` 后缀，命中后只改本会话（`setModelTemporary`），分发发生在 RPC 的 prompt 路径、agent 回合之前（响应 `agentInvoked:false`），因此回合运行中同样可用；成功时先发 `command_output` 与带解析后模型与级别的 `config_update`，再回响应，无法解析时只发 `command_output`（`Unknown model: …`）。`--model <provider>/<id>[:level]` 用同一解析器（`@smol` 这类角色别名同样接受），启动时生效并覆盖 `--resume` 会话里记录的模型；传无法解析的值使 worker 启动失败（`Model "x/y" not found`），所以落盘前必须由 OMP 自己校验过。`get_state` 返回当前模型与思考级别，`get_available_models` 返回当前已配置凭据的可用模型。线程隔离工作区在本机存在兼容 Worktrunk（稳定 v0.76.x）时由宿主调用 wt 完成创建、合并与清理（v0.76.0 实测；合并没有回退），否则创建回退 `omp worktree add`（v18.2.1 实测，clone-first 由 `worktree.clone` 设置决定）、清理回退 `git worktree remove`。子代理可观测性走 OMP 自身的 subagent 通道（v18.2.1 实测）：`set_subagent_subscription` 选择级别（`off`/`progress`/`events`，默认 `off`），订阅后 RPC 侧推送 `subagent_lifecycle`（`id`、`agent`、`agentSource`、`status: started|completed|failed|aborted`、可选 `description`、`index`、`parentToolCallId`、`detached`）、`subagent_progress`（`progress.status`、`lastIntent`、`currentTool`、`toolCount`、`recentTools` 等）与 `subagent_event`（原始子事件），`get_subagents` 另有存活子代理快照。channel 只订阅 `progress` 级别。
- OMP SDK 可嵌入，但本设计选择 RPC，保持进程边界。
- Octo 运行参考：[openclaw-channel-octo](https://github.com/Mininglamp-OSS/openclaw-channel-octo)。其 README 确认 REST 注册、WebSocket 实时收发和自动重连。
- 账户参考：[create-openclaw-octo](https://github.com/Mininglamp-OSS/octo-adapters/tree/main/create-openclaw-octo)。使用 BotFather 创建的 User Bot；`app_` App Bot 仅支持私聊，不能满足群聊验收。
- octo-adapters 当前源码树主要提供安装 CLI；协议运行时代码在独立 channel 仓库。实施时以运行时代码核实报文、消息 ID、mention 元数据和发送接口，不凭顶层 README 猜测端点。
- RPC、SDK 和审批机制参考 OMP 自带 docs/rpc.md、docs/sdk.md、docs/approval-mode.md。
- 上游 `Mininglamp-OSS/octo-server` 的 `modules/bot_api/typing.go` 表明 90 秒后至 180 秒 TTL 窗口可能抑制 CMD typing 投递，即使 HTTP 返回 200；channel 对 agent-attached 消息在权限门通过后立即发出 typing，并在附件组装、排队与执行期间每 3 秒续期、任务终态熄灭（契约详见验收 39 与 `docs/specs/2026-09-20-prompt-typing-feedback-design.md`），不通过客户端绕行，也不承诺绕过服务端节流或离线时连续可见。真实部署尚未完成超过 90 秒的视觉验证；密集多轮会话中服务端死区可能使 typing 最长约 90 秒不显示，属上游既定契约。

## 关键决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 身份 | owner 用户 ID、允许群 ID 列表；已开通群/子区内的成员可驱动助手 | 私聊、命令与配置面只归 owner；成员在允许列表命中的聊天内以结构化 @Bot 发起消息、回答 ask 卡片（详细设计见 `docs/specs/2026-09-17-group-member-participation-design.md`） |
| 执行 | yolo；channel 不添加逐次审批 | 保持全自动习惯 |
| 会话 | 每个聊天一个当前会话，历史保留 | 隔离聊天上下文 |
| 目录 | `/new [目录]`、`/reset [目录]`；省略目录按目标默认目录解析（DM/群沿用当前绑定，首次 `~/tmp`） | 每次 fresh 会话都有确定工作目标 |
| 线程目录 | CommunityTopic 线程尚无已验证会话时，默认目录取父群当前绑定 cwd；线程首次成功建立会话即固定，与父群解耦 | 线程默认落在父群项目上；cwd 可共享，session 与共享说明仍按聊天目标隔离 |
| 线程隔离 | `create-thread` 带 `worktree_name` 时在调用方目录所属仓库旁建立 git worktree（目录与分支名即该名称），并把新线程绑定到该目录（`cwd_pinned`）；本机有兼容 Worktrunk 时创建经 `wt switch --create`，否则回退 `omp worktree add` | 需要独立工作区的线程不必共享父群目录；工作区名字由调用方显式给出，绑定与目录解析顺序一致，`/move` 可显式退出 |
| 工作区合并 | 子区 `/thread merge` 只注入合并指令 prompt，助手经 `octo_management` 的 `thread-merge` 由宿主执行 `wt merge`（默认 pipeline：squash、rebase、fast-forward、合并后删除工作区与分支）；命令即 owner 对合并 + 清理的确认，指令正文要求除非有明确必要理由（并向 owner 说明）直接按默认参数执行，要保留工作区须说明理由并显式传 `remove:false`；无兼容 wt 时不提供 | 命令发出即默认收尾，不把「保留工作区」呈现为对等选项；工作区删除即本子区 cwd 失效，属既定结果、不作为反复提示或保留理由；审批、超时与错误边界统一留在宿主 |
| 工作区清理 | `thread-delete` 在服务端删除成功后联动清理 `cwd_pinned` 工作区：有兼容 wt 时 `wt remove`，否则回退 `git worktree remove`；默认只清干净工作区，`force=true` 丢弃未提交改动 | 删除线程即回收工作区，未提交的工作不会在默认路径下被静默丢弃 |
| 派发回传 | `thread-dispatch` 带 `notify=true` 的派发任务在其运行中终态（完成/失败/取消/中断）向发起派发的聊天回传一条有界通知——合成消息 `notify:<任务 id>` 按该聊天的追加模式交付（并入可接收 steering 的运行中回合，否则成为其一个 durable 任务）；回传登记随任务行持久化、默认 `false`，是否开启由派发方自行判断；派发被并入运行中回合时不生效并在收据中说明；服务停止/重启导致的终态不回传 | 派发出去的活有人盯结果；通知是一次性 durable 输入，重启与崩溃循环都不放大 |
| 迁移 | `/move <目录>` 使用 OMP 原生 `/move`，沿用当前 session ID、历史与附件 | 保持会话连续性，不伪造新会话 |
| 调度 | 同会话串行，同规范化目录串行；迁移同时持有真实源、目标目录 lease | 避免 channel 内任务同时修改同一目录 |
| 故障 | 保存历史，不自动重跑已交付 Agent 的任务 | 工具副作用无法安全推断或回滚 |
| 共享说明 | 按持久 OMP session 与聊天目标绑定 version；首次或 version 变化时注入，普通未变化 turn 不注入 | 降低重复输入并保持群/线程隔离；压缩生命周期单独负责恢复 |
| 入站内容 | 按已确认类型表提取文本；媒体附件下载到状态目录后以本机绝对路径交给 Agent；回复消息按同一张表读取客户端内联的被引用 payload（文本进引用块、媒体并入本条附件——被引用的是无正文媒体时以 `[引用 <发送者>]` 标题注明来源）；群/线程中受权消息本身无附件、无可用引用时，按「同一发送者、10 分钟窗口、唯一一条带附件消息」做「这个」关联取回（歧义/跨发送者/超窗一律不关联，详见 `2026-09-16-group-history-context-design.md`）；贴纸、系统与 CMD 等仍明确告知不支持 | 让常见消息真正可驱动 Agent，同时保持权限门、单一体积上限和可解释的拒绝行为 |
| 群自助开通 | 允许列表 = 配置 `allowedGroupIds` ∪ 状态盘 `allowed_chats`；owner 在未开通群/子区 @Bot 时收到一条节流短通知，回复固定口令 `开通本群` 即开通该聊天（状态盘持久，配置文件同步追加） | owner 现场把 bot 拉进新群后无需改配置或重启；非 owner 与非 @Bot 消息保持静默拒绝，开通动作只归 owner |

## 设计

### 运行和配置

使用 TypeScript/Bun 常驻服务，主动连接 Octo，启动并管理 OMP RPC worker。无需为 RPC 开放网络监听端口。macOS 使用 launchd 托管；机器休眠或离线期间不承诺可用。

本机入口为 `oco`（`omp-channel-octo` 的别名，`bun link` 安装）：`start` 是守护进程托管的服务进程入口，`run` 是不探测守护进程的调试入口，`restart`/`status`/`logs` 通过自动识别出的守护进程程序操作常驻实例，`test --card` 发送真实预览卡。配置在 `~/.oco/config/config.json`，服务日志由服务自持在 `~/.oco/logs/`，状态目录仍在 `~/.local/state/omp-channel-octo`（数据库、附件、sidecar、spool），OMP 会话默认落在 `~/.oco/sessions/`（每个项目一个子目录，见下）；守护进程与程序名不写进配置。详见 `2026-09-16-oco-cli-entry-design.md`。

配置包含 Octo API 地址（缺省为 `https://im.deepminer.com.cn/`）、Bot token、可选 owner 用户 ID、允许群 ID、OMP 可执行文件、本地状态目录与会话目录（`sessionsDir`，缺省 `~/.oco/sessions`，每个项目一个子目录）；WebSocket 地址可按现有发现机制取得或显式配置；`ask` 块可配置问答等待超时 `timeoutMs`（默认 6 小时，允许 30 分钟到 7 天的整数毫秒，越界或非法值启动即拒绝）。未配置 owner 时，服务仅在该 Bot 尚无持久 owner 的条件下接受首次有效私聊绑定。凭证只来自本地配置或环境，不通过聊天设置，不写入日志。使用环境凭证时环境变量名默认 `OCTO_BOT_TOKEN`，显式名称仅允许 `OCTO_` 或 `OMP_CHANNEL_OCTO_` 前缀；所有这两类前缀的变量都会从 worker/watchdog 环境中剔除，以免子进程继承凭证。启动时校验配置、账户能力和状态目录可写性。同一 Bot 只允许一个 channel 实例，使用本机独占锁；不支持跨机器复制运行同一账户。
发卡前必须通过同一能力门禁：profile `enabled=true`（兼容服务端返回 `1`），`profiles` 包含 `octo/v1`，`card_version=1.5`，且 `config.card_enabled=true`、`config.display_enabled=true`、`config.reasoning_enabled=true`；`TextBlock` 是唯一硬依赖，`Container` 等可选元素缺失时使用 fallback；若响应提供 `elements` 或 `limits`，则遵守所需元素和各项限额（包括 payload、node、depth 限额）。能力响应明确不满足必需条件时按未启用处理；HTTP 失败属于请求失败，不等同未启用，不通过发送试探能力。
`launchd install` 只负责生成并写入权限为 `0600` 的 plist，不调用 `launchctl`；需要实际加载服务时由运维显式执行：

```sh
launchctl bootstrap "gui/$(id -u)" "$HOME/Library/LaunchAgents/com.omp.channel-octo.plist"
launchctl bootout "gui/$(id -u)/com.omp.channel-octo"
```

`launchd uninstall` 只删除 plist，不代替 `bootout`。当凭证来自配置环境变量时，安装生成的私有 plist 会包含该变量及 token；该文件必须继续保持 `0600`。plist 固定记录安装时解析出的 OMP 可执行文件，运行时复用该路径，不自动切换本机其他 OMP。

复用本机 OMP 模型、Skills、扩展和项目环境。worker 明确设置 yolo，避免项目默认模式改变约定。OMP 显式工具 deny 或必须使用 UI 的扩展不由 channel 绕过；无法无界面完成时明确失败，不静默等待。执行权限不是沙箱，也不承诺限制 Agent 对目录外文件或网络的访问。

### 入站权限与路由

路由键为 Bot 身份、聊天类型和真实聊天 ID 的组合，不使用昵称。私聊（channelType=1）在已有持久 owner 时必须来自 owner；未配置且尚无持久 owner 时，仅支持的非空文本、`senderId` 与 `messageId` 非空且发送者非 Bot 的首条有效私聊可原子绑定 owner，并只确认不执行任务。传输层可能携带 `owner@bot` 形式的 raw channel ID，但归一后的 `channelId` 与 `senderId` 始终取真实发送者 UID，`owner@bot` 只属于传输层 ID。群（channelType=2）和 CommunityTopic 线程（channelType=5）要求允许列表命中的真实 channel ID 与结构化 mention 指向当前 Bot，且不会触发首次认领：owner 的消息按此放行；已开通聊天内的其他成员同样以「结构化 @Bot」为条件放行（成员不享有免@豁免），其余成员消息静默拒绝。群级免@只对 owner 生效：`GET /v1/bot/groups/{group_no}/mention_pref` 的 `effective` 由服务端把 bot owner 的免@意图与群级 `allow_no_mention` 开关 AND 后给出，为真时 owner 在该群及其线程的未 @Bot 消息照常放行——这是群设置本身授予的豁免，不是 channel 放宽权限。判定按群缓存 60 秒（线程用父群 ID），且只在 owner 消息没有 mention 时才发起查询；查询失败或响应不符合契约时保持「必须 @Bot」，并只做短暂负缓存，避免上游故障拖住入站处理。免@只解除 owner 消息的 mention 条件，允许列表、Bot 回声过滤与首次认领规则都不变。线程的允许关系继承父群：允许列表里有该线程的完整真实 channel ID，或父群 ID（`____` 之前的段）在允许列表里，都算命中，因此白名单群下新建的线程无需额外配置即可对话；不在允许列表的群及其线程仍一律拒绝。文本中的名字或 @ 字符串不能替代 mention 元数据。目录继承复用父群绑定的 cwd，允许关系继承只决定该线程能否发起任务，两者都不改变 owner 判定、共享说明隔离或线程自身的绑定。先验证，再处理所有命令和普通消息。Bot 自发消息、成员未 @Bot 的消息、未开通聊天里的消息与其他任务入口均不触发 Agent。

允许列表由两部分取并集：配置的 `allowedGroupIds`（操作者基线）与 owner 在运行中开通的聊天（状态盘 `allowed_chats` 表，跨重启保留）；两者的命中与线程继承规则完全一致。未开通群/子区的默认行为仍是静默拒绝（不落 `inbound`、不打日志、不回复），唯一例外是 owner 在该聊天内 @Bot 的提及：它收到一条短通知，说明本群/本子区未开通并给出固定口令，同一聊天 10 分钟窗口内只提示一次（节流在进程内，重启后可能再提示一次）。owner 的回答仍须 @Bot，mention 剥离并去掉首尾空白后恰好等于口令 `开通本群`（区分大小写、不做其他归一化）时，该聊天被持久开通：先写状态盘 `allowed_chats`（`bot_uid`、`channel_type`、`channel_id`、`granted_by`、`granted_at`，幂等），再把该 ID 追加进配置文件的 `allowedGroupIds`（原子重写、保留原文件权限与其余字段；失败只记一条日志并在确认消息中说明，不回滚状态盘开通），下一条消息即可正常执行，无需重启或重载配置。口令消息按既有命令 claim 去重，重投不会重复开通、也不会落成任务；非 owner、未 @Bot、近似文本、Bot 回声与私聊的拒绝路径保持原样。子区按「本子区」提示与开通，只覆盖该子区；父群开通后其子区按继承规则随之可用。口令不是注册命令：未开通群的消息不会进入命令解析，已开通聊天收到同一文本时按普通消息处理。

入站记录绑定原始聊天、发送者、消息 ID、会话 ID 和目录；之后回复只使用该记录，不读取可变的“当前聊天”。群和线程输出对成员可见，不发送完整工具原始结果、模型思考或系统上下文；发送助手可见正文与真实工具执行的简短进度。进度不作为普通聊天文字，而是在首次真实工具进度时懒建同一张可编辑卡，后续按最新状态编辑；卡片不可用或状态接口故障不得阻断正文。助手正文仍可能包含用户明确要求的文件内容，不承诺自动识别所有敏感信息。

### 命令

channel 在自身命令注册表中注册下列命令，`/help` 展示用法。这里不依赖 Octo 客户端提供命令菜单 API。

| 命令 | 行为 |
| --- | --- |
| `/new [目录]` | 创建并绑定 fresh OMP 会话；省略目录时按目标默认目录解析，无可用绑定时使用 `~/tmp`；成功回执含 session id、cwd 与该会话实际生效的模型（`已创建会话 <id>，cwd=<目录>，模型=<provider/id[:level]>`，未指定聊天模型时取 OMP 实际默认；模型查询失败或未报告时以不含模型的回执送达） |
| `/reset [目录]` | 与 `/new` 使用相同的目录解析，但明确重置为 fresh 会话；原会话历史文件保留；与 `/new` 共用创建路径，成功回执同式（含实际模型） |
| `/move <目录>` | 调用当前会话的 OMP 原生 `/move`，校验刷新后的 session state，沿用同一 session ID、历史和附件 |
| `/thread <任务>` | 交给助手处理：助手自行确定子区名称与 `worktree_name`，新建带独立 git worktree 的 CommunityTopic 子区并把任务派发进去（派发正文按 SDD 格式写；清晰到可直接生成 SDD 的需求直接开工，否则发起会话只做够派发的最少澄清、剩余澄清由子区按 SDD 格式进行）；只在群聊中可用 |
| `/thread merge` | 子区中把本区隔离工作区的分支经本机 Worktrunk 的 merge pipeline 合并回目标分支；命令只注入一条合并指令 prompt，执行由助手经 `octo_management` 的 `thread-merge` 让宿主完成；命令即 owner 的合并 + 清理确认——除非有明确必要理由（并向 owner 说明），指令要求按默认参数执行（合并成功后删除工作区与已合并分支），保留工作区须说明理由并显式传 `remove:false`；参数按首词识别，首词 `merge` 之后的文本作为 owner 补充说明随指令交给助手；仅绑定隔离工作区的子区可用，主群、私聊、未绑定工作区的子区与没有兼容 wt 的环境只回复提示 |
| `/queue <文本>` | 把该文本作为排队任务追加在当前任务之后，不受当前追加模式影响；正文经与普通任务相同的组装点，随消息发来的附件以本机绝对路径进入排队任务的正文 |
| `/mode [steer\|queue]` | 设置/报告该聊天的追加模式：`steer`（默认，`default` 同义）把运行中的新消息注入当前回合，`queue` 把它变成排队任务；无参数时报告当前设置 |
| `/switch [模型]` | 无参数时报告本聊天当前模型与可用模型列表（运行中的回合用其活会话读 `get_state`/`get_available_models`，否则由 fresh 一次性 worker 读取）；带参数时把选择器交给 OMP 自己的 `/switch` 解析并应用（`provider/id`、模型 id/子串、`@角色`、`:level`）——有运行中的回合时切该会话，空闲时解析后按聊天持久化、之后启动的 worker 带 `--model`；`default` 恢复跟随 OMP 默认 |
| `/interrupt` | 中止当前聊天的运行中回合，保留已排队消息与它后面的排队任务；不终止 worker |
| `/cancel`（`/stop` 同义） | 取消当前聊天正在执行的任务，并清除该聊天待执行消息 |
| `/status` | 返回当前会话、目录、追加模式和运行/排队/中断状态 |
| `/restart [now]` | 通过部署方配置的重启命令安全重启 channel；省略参数时在有任何运行/排队任务时拒绝；`now` 强制重启并中断在途任务 |
| `/help` | 展示 channel 命令及目录用法 |

当前聊天有待回答问题时，owner 在该聊天的非命令回复就是答案本身：合法选项编号按选项校验，其他文本原样作为自填答案；没有待回答问题时同一文本按普通任务输入处理。待回答问题的答案优先于追加模式，不能被 steering 或排队吞掉。`thread-dispatch` 交付到子区的内容是显式交接而不是 owner 的回复，不作为该子区待回答问题的答案。问题以交互卡片投递时，owner 对该卡片的一次按钮点击同样是这个问题的答案：点击与文本回复共用同一个答案 compare-and-set，只有一方生效，其他人的点击只 ack 不生效，卡片只是多一条作答路径而非唯一路径。

追加模式决定该聊天在已有运行中任务时如何处置新消息，按 `botUid` 与真实聊天目标隔离并持久化，跨重启保留，未设置时默认 `steer`。`steer` 模式下的普通文本经持久 claim 后作为 OMP `steer` 帧注入当前运行中的回合，与当前回合共用同一条任务和正文流；每条被注入的消息都是新的一轮，进度随之在新卡片上继续（见进度卡章节）。`queue` 模式下的普通文本走既有 durable acceptance，成为在该任务之后执行的排队任务，保留独立的正文消息与进度卡。OMP worker 只在其回合仍在流式输出时接受 steering：没有运行中的回合、回合已经结束或 OMP 拒绝该帧时，该文本回退为普通排队任务，不静默丢弃。`/queue <文本>` 始终走排队任务路径。把正文交给助手的命令与普通文本走同一条追加路径：`/thread <任务>` 的交付说明同样按该聊天的追加模式处置（运行中的回合能接收 steering 时并入该回合，否则回退为 durable 任务），`/queue` 则是任何模式下都排队的显式入口。`thread-dispatch` 交付到子区的内容按目标子区自己的追加模式处置：子区运行中的回合能接收 steering 时并入该回合，否则成为该子区的 durable 任务，工具结果与发起群回执都如实报告这次交付。追加模式因而是每个聊天唯一的处置开关，到达该聊天的正文都由它决定并入回合还是成为任务。steering 不产生新的任务记录或正文消息，也不改写当前回合已建立的群说明快照。

追加消息的可见性以「被消费」为准，而不是「投递成功」：`steer` 帧返回成功只表示消息进入 OMP 的内存待注入队列；OMP 在注入边界把它并入回合上下文（表现为一条 `role: user` 且 `steering: true` 的用户消息进入事件流）时，channel 才在该聊天补一行「已并入当前回合 ▸ <正文前 20 字>」回执。`queue` 模式与 `/queue` 产生的排队任务，只有接受时该聊天或目录已在忙、因而确实等待过的，才在真正从 `queued` 变为 `started` 时补一行「开始执行排队消息 ▸ <正文前 20 字>」；未被消费、被 `/cancel` 或进程重启丢弃的追加消息不产生回执。回执正文取该消息实际注入回合的正文（含引用/附件块）的单行前 20 字，超长以省略号截断，空文本只发前缀。

`/interrupt` 向该聊天运行中的回合发送 OMP `abort` 并保留同一 worker：不进入排队任务的 durable 取消路径，不清空已通过 steering 或 `/queue` 追加的消息，也不停止 worker 进程；该回合之后的排队任务按原顺序继续执行。回合因该中止结束且其后没有任何真实事件时，任务终态记为 interrupted，进度卡记为 cancelled；若回合继续产出正文或工具事件（例如处理已追加的消息），任务按正常完成结算。`/interrupt` 在运行时即时回复一条中断确认，失败时明确回复中断未被接受。

`/cancel` 与 `/stop` 是控制路径：发送 abort、等待 worker 停止，并清除该聊天的待执行消息与排队任务，因此同时也丢弃尚未消费的 steering 与排队消息；不回滚已经发生的副作用。

`/restart` 由 channel 检测出的守护进程执行：启动时按自身 PID 在 Super 的程序列表里认出托管自己的程序（见 `2026-09-16-oco-cli-entry-design.md`），命中才提供重启端口；未检测到守护进程时明确回复“未检测到守护进程，无法重启 channel。”且不猜测重启机制。命令由 channel 以独立会话派生，进程停止由该守护进程负责（Super 的 `restart` 会先给 channel 发 SIGTERM），channel 自己不会在命令未停止它时擅自退出，只记录一条告警。发起的聊天先收到“正在重启 channel”，请求被持久化；进程恢复后在原聊天投递“channel 已重启完成：PID …，启动于 …”。重启时被中断的在途任务发送“channel 正在重启，本会话任务已中断；重启完成后会在本会话确认。”，未开始的排队任务在下次启动按 interrupted 报告。重启完成通报超过 10 分钟未投递则丢弃，不对未发生的重启做确认。被中断回合的进度卡不再停留在「进行中」：卡片身份与快照已按任务持久化，新进程在启动时补发一次终态编辑（见卡片持久化），并照常投递重启中断的正文通知。

`/switch [模型]` 按聊天目标查看与切换模型：无参数时报告「当前模型 + 按 provider 分组的可用模型（总模型数超过 80 时截断并说明总数）」——有运行中的回合时由该回合的活会话读 `get_state`/`get_available_models`（模型标注「运行中会话」，与本聊天指定值不同时并列给出），否则用既有 `WorkerFactory` 起一个 fresh 一次性 worker（临时会话目录，`mkdtemp` 创建、读完即停并删除）读取，空闲且未指定时标注「OMP 默认」；带参数时把选择器原样交给 OMP 自己的 `/switch` 解析——`provider/id`、模型 id 或唯一子串、`@角色`（OMP `settings.modelRoles` 的映射）与 `:level` 后缀都由 OMP 决定，channel 不复制解析规则；解析成功时把 `provider/id:level` 写入状态盘 `chat_models`（按 `botUid` 与真实聊天目标隔离，不继承），解析失败回单行中文错误且不改状态。生效分两部分：有运行中的回合时选择器直接分发给该回合的活会话（OMP 只改本会话、不产生 agent 回合，实测回合运行中可用且该回合继续跑完）；之后启动的 worker（任务路径与 `/new`、`/reset`、`/move`）组装 `WorkerOptions` 时读取该值并传 `--model`，resume 的会话也因此覆盖记录里的模型，服务重启后仍生效。`default`（不含 `/`）清除本聊天模型、之后跟随 OMP 默认，运行中的会话不被改动（要移动它用 `/switch @default`）。该命令不取目录 lease——探测 worker 是 fresh、不跑 agent 回合、独立会话目录的一次性进程，不读写任何聊天会话；worker ledger 以 `switch-` 前缀记录并在停止后清除，临时目录随即删除。

群中使用 `@Bot /new <目录>`、`@Bot /reset <目录>` 或 `@Bot /move <目录>` 等相同命令；剥离已验证的 Bot mention 后解析。命令与 mention 的先后顺序不固定：客户端可能发送 `@Bot /command <参数>` 或 `/command <参数> @Bot`，解析前剥离全部已验证的 Bot mention，无论它位于命令前、命令后还是参数中间，并清理剥离处残留的空白。结构化 span 与文本对不上或缺失时，退回按 mention uid 列表匹配独立出现的 `@BotName` 或 `@BotUid` 词元（两侧为空白或文本边界，允许尾随冒号）；未指向当前 Bot 的文本型 `@` 不剥离，用户正文中的其他 `@` 保持原样。命令只允许 owner 发起：成员发来的 `/` 开头消息一律不执行、也不交给 Agent（OMP 会在 RPC prompt 路径对内建命令做分发，透传等于把命令面暴露给成员），同一聊天 10 分钟窗口内至多回一条提示「命令仅 owner 可用；需要助手做事请直接 @<BotName> 说明。」，并按既有命令 claim 去重、重投不重复提示。channel 内置 `/new`、`/reset`、`/move`、`/thread`、`/queue`、`/mode`、`/switch`、`/interrupt`、`/cancel`、`/stop`、`/status`、`/help`、`/restart` 始终硬拦截，不发送给模型；若存在同名观察器也不能改变这一安全语义。其他 slash 输入按原始 `message.text` 作为普通 OMP task 透传，未知命令不再返回“不支持的命令”。
可通过服务选项注册自定义 `ChannelCommandHandler`：`name` 去除首尾空白并按小写规范化，`intercept` 明确决定是否消费，`handle(context)` 接收原始 `InboundMessage`、规范化命令名和解析后的 argument。`intercept=true` 在持久命令去重后执行 handler，成功后消费且不启动 OMP；失败保持可重试的命令状态且不启动 OMP。`intercept=false` 先完成现有任务 durable acceptance，再调用 handler 并继续透传原始文本；handler 异常不得阻断任务或 prompt，重复消息不得重复 handler 或 task。handler 必须经过既有 owner、群/线程 mention 和消息 ID 校验；空名、非法名或规范化后的重复注册在创建服务时拒绝，不能静默选择。

`/new`、`/reset` 的完整剩余文本是一个路径；可移除一对匹配的外围单引号或双引号。支持绝对路径、当前运行账户的 `~/`；拒绝相对路径、其他用户的 `~name` 和空引号。路径不经 shell 执行，不展开环境变量、通配符或命令替换；特殊字符按文件名处理。

省略目录时的默认目录按目标解析，顺序固定为：① 该目标已有绑定且绑定已有已验证会话文件，或该绑定目录是显式指定的隔离工作区（`cwd_pinned`，尚未建立会话时同样生效），沿用其规范化 cwd；② 目标是 CommunityTopic 线程（channelType=5）且其父群存在绑定，取父群绑定 cwd；③ 其余情况首次解析为 `~/tmp`。父群指线程真实 channel ID 中 `____` 之前的父群 ID，按 channelType=2 目标查询；channelId 不含合法父群段、父群无绑定或父群 cwd 已不可用时按 ③ 处理，不因此拒绝任务。显式绑定的隔离目录不可用时按后续顺序继续解析（线程回退父群或 `~/tmp`），不拒绝任务。

`/thread <任务>` 把意图交给助手处理，而不是由宿主同步建区：命令把「原始意图 + 交付说明」作为正文交给助手（正文先经普通任务同一条组装点组装：随消息发来的附件下载到本机、绝对路径写进意图，引用块同理；该正文按该聊天的追加模式处置，与普通文本完全一致——运行中的回合仍能接收 steering 时交付说明并入当前回合，由运行中的助手建区并派发；没有运行中的回合、OMP 拒绝该帧或该聊天为 `queue` 模式时，它成为当前聊天的一个 durable 任务并在正忙时排队等待）。助手先理解意图并自行确定简洁的子区名称与 ASCII 的 `worktree_name`；用 `octo_management` 的 `create-thread`（带 `worktree_name`）建隔离子区，再用 `thread-dispatch` 把任务派发进去；派发的任务正文统一按 SDD 格式写（目标、范围、约束与验收标准）：需求简单或非常明确、清晰到子区可以直接由正文生成 SDD 时直接派发，让子区生成 SDD 并立刻开工；否则命令发起的聊天先按这些要素做够派发所需的最少澄清，正文写明已知内容，并要求子区先按 SDD 格式把尚不明确的需求澄清成 SDD（可实施的设计）再动手，需要 owner 拍板的问题在子区内用 `ask` 提出，环境里有 `spec-design` 等澄清或设计技能时引导子区用该技能完成澄清；详细的需求澄清在子区内进行，命令发起的聊天不做过于详细的需求澄清。子区据此按 `create-thread` 相同的路径获得独立 git worktree 并把绑定固定到该目录（`cwd_pinned`），派发经与 `thread-dispatch` 相同的 durable 入站路径（发送者为持久 owner，子区内显示派发说明，命令发起的群收到一行回执）。工作区创建失败不回滚已创建的子区与已派发的任务：工具结果报告 `worktree_error`，子区按普通目录顺序执行任务。`/thread` 只在群聊（channelType=2）中可用，私聊与子区中的调用分别明确拒绝且不创建子区；任务文本为空时回复用法。

`/thread merge` 是子区中的合并入口：`/thread` 的参数去首尾空白后首词为 `merge`（其后是行尾，或非字母数字、下划线、连字符的分隔符——`merge-fix` 这类名字不算）时进入该路径，首词之后的文本作为 owner 补充说明附在合并指令里交给助手。仅当该聊天是 CommunityTopic 子区（channelType=5）、其绑定为 `cwd_pinned` 隔离工作区、部署提供隔离能力、本机存在兼容 wt（稳定 v0.76.x，探测按 `wt` 与常见安装位置进行）时，命令在释放自身 claim 后把「合并指令」prompt 交给助手——与建区 prompt 同构（说明 owner 要求把本子区工作合并回目标分支、合并由宿主执行、调用 `octo_management` 的 `thread-merge` 而不要自己运行 wt、默认走 wt 默认 pipeline（命令即 owner 确认合并并清理——除非有明确必要理由并向 owner 说明，否则直接按默认参数执行、合并成功后删除工作区与已合并分支，要保留工作区须说明理由并显式传 `remove:false`（工作区删除造成的本子区 cwd 失效是既定结果——owner 已知，不反复说明、也不作为保留理由）、成功汇报目标分支与结果细节、失败处置后重试，并附 owner 补充说明（如有）与工作区路径），该正文按该聊天的追加模式交付（可接收 steering 的运行中回合并入，否则成为 durable 任务），命令本身不执行 wt。主群、私聊、未绑定工作区的子区、部署无隔离能力，以及 wt 缺失或版本不受支持时只回复一条提示、不产生任务。

线程的目录继承只在它还没有已验证会话且没有显式隔离绑定时生效。线程第一次成功建立会话（`refreshState` 确认并持久化 session 文件）后，其 cwd 固定为绑定 cwd；父群随后 `/new`、`/reset`、`/move` 不改变任何既有线程绑定。已建绑定但从未成功建立会话的线程在下一个任务重新按上述顺序解析，并把解析结果写回绑定，显式 `/new <目录>` 会解除隔离绑定。服务启动时不为存量绑定做一次性回填，也不新增用户可见提示；`/status` 按绑定 cwd 照常报告。

`/move` 必须提供目标路径，按同样的安全规则解析；它只在当前绑定存在精确可恢复 session 文件时执行。channel 先取得并持有真实源目录与目标目录 lease，调用 OMP 原生 `/move <目录>`，再通过 `refreshState` 校验 session ID、session 文件和规范化目标 cwd，成功持久化后才更新绑定。源目录或目标目录有运行/排队任务、未确认停止的 worker 或 lease 冲突时拒绝，不隐式迁移或丢弃任务。

显式目录必须已经存在、为目录且可访问。使用 realpath 规范化并记录，符号链接别名共享同一个调度锁。创建 fresh worker 时传入 `--cwd`，不靠会话内 cd 模拟目录切换；创建或持久化失败保留原会话绑定。`/new`、`/reset`、`/move` 成功后才确认成功。

当前聊天有运行中或排队任务时 `/new`、`/reset`、`/move` 明确拒绝，并提示先 `/cancel`；没有会话时第一条合法普通文本按同一默认目录解析顺序创建会话，再处理消息。历史 OMP 会话文件保留，本次不提供 IM 历史列表或切回命令。

原生迁移的 worker 若无法确认停止，源目录和目标目录都持久标记为 blocked；服务重启恢复 worker ledger 时仍同时阻塞两目录，直到停止状态可确认。外部移动不通过最近文件猜测，而在后文定义的精确身份规则下自动重绑。

### 群说明、Host tools 与问答

每个群或线程任务在完成权限、去重和 durable acceptance 后，检查一次当前 Octo 共享说明的 version；channelType=2 从服务端 `groups/{id}/md` 读取 `GROUP.md`，channelType=5 从 `groups/{parent}/threads/{short}/md` 读取独立 `THREAD.md`。读取共享说明失败则该任务失败且不得启动 worker。读取结果规范化为带 `present`、完整 `content` 和按目标稳定且不可复用的 `version` 的快照；空内容是 `present=false` 的有效快照，必须保留其 server version。初次从未有说明的 404 可规范化为只用于初始无说明状态的 version 0 哨兵；已有 server version 的目标删除时必须由服务端返回新的删除 version，不能用无 revision 的 404 假装 version 未变化。

共享说明状态按 `botUid`、真实聊天目标和持久 OMP session 隔离。worker `create` 完成并由 `refreshState` 确认真实 OMP session ID 后，宿主才发布该 session 的受控 context sidecar；任务或绑定阶段产生的占位 session ID 不能作为 sidecar 或 marker 的身份。sidecar 只包含目标、真实 session ID、当前 turn 的 immutable snapshot、注入决策和不含秘密的 injection attempt ID，不包含 Bot token，extension 不得按 cwd、全局文件或模糊 session 回退。宿主在每次 `prompt` 前把本 turn 的绑定 session 发布到同一作用域（`bound-session.json`），并保留为该作用域的当前 session；extension 据此把同一 worker 进程内 OMP 为 subagent、eval 子会话等打开的 session 与 channel turn 区分开：不是该绑定 session 的 turn 既不注入共享说明也不被拒绝，绑定 session 缺失 sidecar 或校验失败时仍必须 fail closed；从未发布过绑定 session 的作用域沿用原有严格行为。

新建 session 在第一次 agent start 注入完整的最新共享说明。恢复已有 session 时，若持久 marker 已证明同一 session、目标和 version 已成功提交，则不重复注入；没有 marker 或 marker 处于 pending 时按首次注入处理。普通 turn 只有在当前 version 与已提交 marker 不同时才注入，注入内容为完整最新快照，并附带版本变化说明；不生成 old/new diff。普通 `worker.prompt` 的 system-level 共享说明只由固定 OMP extension 的 `before_agent_start` 生命周期从 sidecar 注入，prompt 文本本身不携带共享说明正文；extension 的输入必须校验 Bot、目标和真实 session ID，缺失或不匹配时 fail closed。启用群历史后，prompt 文本由宿主拼接"群对话历史块 + 原始用户文本"，历史块属于用户消息而不是 system-level 上下文，与共享说明互不合并，规则见 `docs/specs/2026-09-16-group-history-context-design.md`。

注入采用 `pending`/`committed` 两阶段。宿主先原子发布 sidecar 和 pending 状态；extension 在返回 system-level context 前，以 injection attempt ID 原子写入同 sidecar 作用域的 `prepared` receipt。receipt 只证明 extension 已校验目标并生成了指定上下文，不代表模型已经接受；receipt 缺失、过期或绑定不匹配时，`before_agent_start` 必须失败，OMP 不得进入模型调用。宿主观察到 matching receipt 和 OMP prompt acceptance 后，才以同一 attempt ID 做 CAS，把该 version 标为 committed；未确认 acceptance 的 pending 在下一次任务中重放，不能静默跳过。正常成功路径同一 version 只注入一次；进程在 acceptance 与 marker 提交之间崩溃时按保守的 at-least-once 重放，以优先保证不丢共享说明。

OMP `session.compacting` 生命周期在压缩时把当前 turn sidecar 中的完整共享说明和 version 边界加入压缩上下文，即使 version 未变化；这是为保证压缩后仍保留 group/thread 语义的恢复性注入例外，不推进普通 turn 的 committed marker。当前 turn 的 sidecar 在 `octo_management` 的 `description-write` 后保持 immutable，compaction 使用本 turn 已建立的快照；写入成功的新 version 只在下一 turn 重新读取并发布。恢复后的下一次普通 turn继续依据 committed marker 判断，不因 compaction 再次重复注入。GROUP.md/THREAD.md 中的内容是共享上下文，不改变发送者身份、权限或 cwd。

群和线程任务获得一个复合工具 `octo_management`，动作固定为 `group-info`、`group-members`、`group-update`、`description-read`、`description-write`、`list-threads`、`create-thread`、`thread-info`、`thread-members`、`thread-join`、`thread-leave`、`thread-delete`、`thread-merge`、`thread-dispatch`，对应服务端 `groups/{id}`、`groups/{id}/members`、`groups/{id}/info`、`groups/{id}/md`、`groups/{id}/threads`、`groups/{id}/threads/{short}` 及其 `members`/`join`/`leave` 路径。目标固定为当前聊天：群任务取当前 `group_no`，线程任务取父群 `group_no`，`thread-*` 动作省略 `short_id` 时取当前线程，模型不能传入其他群或线程 ID。`group-update`、`thread-delete`、`thread-join`、`thread-leave` 等写操作的授权由服务端判定（`bot_admin`、线程创建者或群管理员），客户端不放行服务端拒绝的动作，也不做额外提权。失败时把服务端错误正文压成单行、截断到 200 字符后作为工具错误返回，便于模型纠正参数；错误文本在 HTTP 状态后带上服务端机器码（如 `err.server.bot_api.store_failed`）——bot API 在兼容窗口内把所有错误都以线缆 400 返回（服务端 `pkg/httperr/respond.go` 的 `ResponseErrorL` 固定传输状态 400，正文 `error.http_status` 才是语义状态），因此参数错误（`err.server.bot_api.request_invalid`）与内部失败只能靠正文的 code 区分；返回值按固定上限裁剪（成员 200、线程 50）并显式给出总数与截断标记，名称截断到 200 字符、公告截断到 2000 字符，不返回原始 HTTP 响应或凭据。`thread-delete` 对服务端瞬时存储失败做有界重试：响应为任意 5xx，或响应体 `error.code` 为 `err.server.bot_api.store_failed`（该内部失败在兼容窗口内同样以线缆 400 到达）时，换一条新连接（Bun fetch 显式 `keepalive: false`，不复用连接池的 keep-alive 连接）重试一次；服务端删除本身幂等，重试不会重复删除。重试成功后同样返回「已删除线程 `<short_id>`」；两次都失败时仍返回单行、≤200 字符的服务端错误，不把失败折叠成成功；4xx 参数与权限拒绝不重试。`thread-delete` 另有可选布尔参数 `force`（默认 false）：服务端删除成功后，被删子区存在 `cwd_pinned` 绑定时联动清理该工作区——本机有兼容 wt 时 `wt remove --foreground`（分支已合并即删除、未合并保留），否则回退 `git -C <path> worktree remove`；有未提交改动且未传 `force` 时保留工作区并在回执说明「可传 force=true 强制删除」，`force=true` 时丢弃未提交改动；工作区已不存在时回执说明；清理失败只进入回执、不影响已生效的删除；部署未提供隔离能力或绑定非 `cwd_pinned` 时不清理、回执维持原文。

`thread-dispatch` 让当前群/线程会话把一条任务派发给本群的某个 thread：先按服务端读取该 thread 的真实 `channel_id`（必须属于当前群），在该 thread 里投递一条可见的派发说明，再把内容按该 thread 自己的追加模式交付——入站消息 ID 使用 `dispatch:` 前缀的唯一值、发送者为持久 owner、目标为该 thread；`steer` 模式的子区有可接收 steering 的运行中回合时内容并入该回合（工具结果 `delivery` 为 `steered`），否则按与真实入站相同的 durable 路径成为该子区自己的任务（`delivery` 为 `queued`）。工具结果带回 `delivery`，发起群的回执如实描述这次交付（并入运行中回合，或在该子区作为独立任务执行）；派发不等待该任务完成。被派发的任务在目标 thread 的绑定与 session 中执行，cwd 按线程默认目录规则解析（未建会话时继承父群绑定 cwd，因此与父群任务按目录串行），结果投递到该 thread 而不是发起聊天。派发是显式交接而不是 owner 的回复，因此从不作为该 thread 待回答问题的答案；被派发任务自身仍照常排队、在自己回合里接收 steering 与问答。派发的深度固定为 1：任务记录的消息 ID 带 `dispatch:` 前缀时，该任务的 `octo_management` 不提供 `thread-dispatch` 动作，客户端也拒绝该动作。

`create-thread` 另有可选字符串参数 `worktree_name`：给出名称时，宿主在调用方当前目录所属的仓库（`git rev-parse --show-toplevel`）旁建立独立 git worktree，并把新线程绑定固定到该目录。名称同时是工作区目录与分支名（`<repo>.<worktree_name>` 的 ASCII slug，超过 32 字符截断），因此必须含 ASCII 字母或数字——纯中文等无法 slug 的名称在创建线程前被拒绝（`worktree_name must contain ASCII letters or digits (e.g. fix-login)`），不生成无意义的数字目录；名称被占用时退到 `<slug>-<short_id>`。创建在本机存在兼容 Worktrunk（稳定 v0.76.x）时由宿主调用 `wt switch --create <branch> --no-cd --format json --config-set worktree-path=<候选路径>`（项目 hooks 按 `.config/wt.toml` 执行，宿主不传 `-y`/`--no-hooks`；未审批的命令在非交互环境按 wt 自己的错误失败，wt 创建失败或超时也按失败回报而不是静默改用 OMP 路径）；wt 缺失或版本不受支持时调用部署解析出的 OMP 可执行文件的 `omp worktree add`，继承 OMP 自身的 clone-first 行为（未跟踪与被忽略的文件如 `node_modules` 一并克隆，无需重新安装依赖）；两条路径都有界超时 120 秒、随工具取消信号中止，目录/分支命名与占用退让一致。绑定写入 `chats.cwd_pinned`，线程随后按该目录建立自己的 session；worktree 创建失败不改写已经创建的线程，工具结果返回单行、截断 200 字符的 `worktree_error`，线程仍按普通目录顺序使用。成功时结果在 `worktree` 字段返回路径与分支。省略该参数时不建立工作区，线程按默认目录规则继承；部署未提供隔离能力时同样以 `worktree_error` 说明，不伪装成功。

`thread-dispatch` 还可带可选布尔参数 `notify`（默认 `false`）：为 true 时这条派发任务在其运行中终态——`completed`/`failed`/`cancelled`/`interrupted`——向发起派发的聊天（调用方，即群聊或子区）回传一条有界通知，是否开启由派发方自行判断（工具描述与 `/thread` 指令给出判断建议：派发后不再盯、又需要知道结果时才开启）。回传登记随任务行持久化（`tasks` 表的 `relay_channel_type`/`relay_channel_id`/`relay_thread_name`，空 = 不回传），跨重启保留；派发被并入运行中回合时不产生任务行、回传不生效，收据与工具结果（`notify=skipped`）如实说明。通知是一条合成入站消息（消息 ID `notify:<子区任务 id>`、发送者为持久 owner、`messageSeq=0`），按发起派发聊天的追加模式交付：运行中且可接收 steering 的回合把它并入（不额外唤醒），否则成为该聊天的一个 durable 任务（恰好一次唤醒）；它不经过权限门，也不被当作待回答问题的答案。通知正文有界：子区名称、`short_id` 与 `channel_id`、任务 id、中文状态、任务摘要（首 200 字符）以及结果/失败原因/取消或中断说明（首 1500 字符），外加一行回传提示；投递失败只记 `[thread-notify]` 日志、不重试。服务停止/重启导致的终态不回传：优雅停止把在途任务落成 `cancelled`，该路径由 `stopping` 标志整体跳过（用户 `/cancel` 不置该标志，照常回传），`markInterruptedOnStart` 落成的 `interrupted` 不接入；重启通告仍只发给任务所在聊天，重启恢复不放大成派发方的成批模型回合。同一任务至多通知一次：终态任务不会被再次 settle，稳定的消息 ID 又是 `inbound` 去重键。非派发来源的子区任务——owner 或成员在子区直接发出的消息、`/queue`、问答唤醒——没有登记，永不回传。回传在 `runTask` 的 `finally` 中于该任务的 runtime 注销之后发出，派发方与子区共享 cwd 时不会因此多收一行「开始执行排队消息」回执。

`thread-merge` 是 `octo_management` 中执行工作区合并的动作：只接受当前子区，且要求该子区绑定隔离工作区、部署提供隔离能力、本机存在兼容 wt；宿主以工作区为 cwd 运行 `wt merge --format json`（600 秒上限、随工具取消信号中止、不传 `-y`），执行前校验工作区目录存在且是 linked worktree（`rev-parse --git-dir` 与 `--git-common-dir` 不同，主检出因此不可合并）。可选参数逐项映射 wt：`target`（默认仓库默认分支）、`squash`/`commit`/`rebase`/`remove`/`ff`（默认 true，false 映射 `--no-*`）、`stage`（`all`/`tracked`/`none`，默认 `all`），全部省略即 wt 默认 pipeline（squash、rebase、fast-forward、合并后删除工作区与已合并分支）。成功返回 wt 的结果对象（`branch`/`target`/`squashed`/`rebased`/`committed`/`removed`）；失败返回单行、≤200 字符原因——rebase 冲突时工作区留在 rebase 现场、目标分支未改动，助手处置后可重试。

`octo_management` 的 `description-read` 每次通过实时 `getGroupContext` 读取服务端当前说明，不使用 prompt 或 compaction 快照；`description-write` 只更新当前群/线程目标且需要服务端 `bot_admin` 权限。写入成功后，后续任务和 extension sidecar 使用新的 version；当前 turn 已经建立的 context 不回写。私聊不读取或注入群说明，也不获得群说明动作。

所有任务都获得固定目标与 cwd 的 `ask`、`octo_send_file` 工具，以及控制 channel 自身的 `channel_control`；群和线程额外获得复合工具 `octo_management`。`channel_control` 的 `restart` 排定一次 channel 重启：它在本回合结束后、且 channel 没有运行中或排队任务时才让检测出的守护进程重启自己，完成后在发起会话通报新 PID；因此在自己的回合里改完代码即可让新实现生效（自迭代），既不打断正在投递的回复，也不需要外部脚本或延迟作业。未检测到守护进程时明确回复未检测到且不猜测重启机制。`status` 返回进程 PID、运行中的会话目标、排队任务数、被阻塞目录数与是否已排定重启，供重启前后核对。文件工具的相对路径按任务 cwd 解析，绝对路径可指向本地其他文件，系统不提供目录沙箱保证；发送前复制到 stateDir spool；outbox 保存稳定 client message ID，断线重试不重跑任务。文件永久失败标记 dead 并报告，但不得阻塞后续文字 outbox。

`ask` 创建带持久化 ID 的问题后暂停当前任务，并给出一段包含问题正文、编号选项（如有）和回复规则的文本。只要该聊天存在待回答的问题，owner 或已开通群/子区内的成员在该聊天的下一条非命令文本即被当作答案：只有一个待答问题时它就是该问题的答案——合法选项编号按该问题单选/多选的数量和范围校验，其他文本原样作为自填答案返回给模型；一次 ask 的多个问题同时待答时，这条文本作为整组答案，同一文本写入该组每个仍未作答的问题（逐题按各自规则解释：编号在范围内取编号、否则原样），该 ask 立即在所有问题上返回而不逐题等待，已作答的问题不重复写入。命令仍然优先。不提供默认答案；无待回答问题、不同聊天与重复投递的回复都不作为答案，其中无待回答问题时的文本按普通任务输入处理。等待超时不再是过期：等待超过配置的 `ask.timeoutMs`（默认 6 小时，允许 30 分钟到 7 天）时，问题行保持 pending、卡片保持可提交，等待中的回合像被取消的 tool call 一样停住（任务记为 interrupted，不向聊天发送任何提示）；owner 或成员之后的答复照常记录为答案，并作为该会话的新回合输入投递（正文写明所答问题与还原后的答案）——运行中的回合按该聊天的追加模式并入，否则成为 durable 任务——agent 在同一 session 继续。同一次 ask 的整组问题共用创建时开始的计时，整组一起停住。取消或服务重启会使等待失效：取消封闭该聊天的问题，重启把遗留问题标记为 cancelled。

整组问题初始化中途失败时，已建立的问题取消、等待者与超时计时器释放，原始落库错误继续返回调用方；后续普通消息仍走正常输入路径，修复存储故障后的下一次提问可正常完成。

部署宣布交互档时（`GET /v1/bot/card/profile` 的 `profiles` 含 `octo/v2`、`config.card_enabled`/`display_enabled`/`interaction_enabled` 为真），问题改以 type-17 交互卡片投递，并把卡片的远端 message ID 记在承载该问题的行上；信封的 `plain` 与同一问题的纯文本渲染逐字一致，所以不认该 profile 的客户端照常显示问题文本。单独一个问题时，卡体是问题正文与编号选项：单选问题为每个选项一个 `Action.Submit` 按钮，每个按钮各占卡体中的一个 `ActionSet`（其 `actions` 数组只放该选项一个动作——客户端对整卡做白名单校验后交官方 AdaptiveCards SDK 渲染，卡体 actionset 纵向堆叠、一行一个；卡级 `actions` 区把多个动作排成一行并裁掉溢出，因此选项按钮全部下移到卡体，卡级动作区只留自由输入字段的提交按钮）——按钮标题按显示宽度有界（40 半角列，约 20 个全角字形，超出以省略号截断；客户端按固有宽度单行摆放按钮、超宽只溢出裁切不换行），完整选项文案与描述始终逐字保留在编号行——并附一个自由输入字段与提交按钮；多选问题为 `Input.ChoiceSet` 加自由输入字段与提交按钮；无选项问题为 `Input.Text` 加提交按钮；选项题的自由输入填写后以它为准。一次 ask 的多个问题共用一张卡：每题有独立输入 id（`ask_choices_<n>`/`ask_text_<n>`，n 为题序）、选项题同时渲染选择控件与「其他」自由输入（填了以其他为准）、无选项题渲染 `Input.Text`，整卡只有一个「提交全部答案」。一次提交把填写了的问题各做一次答案 compare-and-set（同一存储事务），未填的问题保持待答、卡片换新的 action id 生成重绘后继续可答；全部作答后卡片改写成终态，每题显示已回复与所选或自填内容。整卡发不出时——未宣布交互档、信封超出服务端 limits（node/depth/payload）、或发送失败——回退为逐题投递：每题按上面的单题卡或纯文本单独提问并逐个等待，问题语义不变。点击与文本回复共用同一个答案 compare-and-set：只有一方生效；owner 的点击在任何聊天有效，成员的点击仅在问题所在聊天是已开通群/子区（允许列表命中，线程继承父群）时有效，其余点击不生效（ack 但不落答案、不重绘、不唤醒）；问题关闭后的点击不覆盖已记录的答案；服务端对同一 `(message_id, action_id, operator_uid)` 只受理一次点击，因此未成答的点击（例如空内容提交）用新的 action id 重绘卡片并回复一次提示，用户仍可继续作答。每次答案落盘同时记录提交人 uid（问题行 `answered_by`）：`ask` 工具返回值的每条答案带 `answeredBy`（身份始终是 uid），而用户看到的署名把该 uid 解析成显示名——`GET /v1/bot/user/info` 按 uid 取名，结果进 30 分钟 TTL、最多 200 条、单次查询 3 秒预算的有界缓存（同一 uid 的在途查询合并，失败不缓存），查不到、超时或失败一律回退成 uid，且从不影响答案落盘与卡片改写；卡片已回复行把名字渲染成自带 `weight: Bolder` 的 `TextRun`（真机实测 2026-09-19：加粗成立，Markdown 文本在卡片内不承担加粗），同一句的 `plain` 文本回退走消息正文，那里没有样式可用，名字用 Markdown 加粗（`已由 **名字** 回复：…`，真机实测正文把两个星号吃掉并显示为加粗）；两处句子同源，只有强调手段不同；等待超时后的唤醒文本仍按 uid 标注提交人；需要名字时 agent 也可用 `octo_management` 的 `group-members` 查询。答案落盘后卡片被 best-effort 改写成终态（已回复并带上所选项、已取消），改写失败只记日志，不影响答案。

交互卡片的上行由 channel 主动消费 Bot 事件队列：`POST /v1/bot/events` 长轮询读取（`wait` 上限低于客户端请求超时并留余量），游标按 `botUid` 持久化且单调递增，事件处理完成后才 `POST /v1/bot/events/{event_id}/ack`，ack 失败或处理可重试时保留游标让同一事件下轮重读。投递是至少一次：重复投递的点击按已记录答案处理，不再作答也不重复改写。该队列只有本 channel 一个消费者；非 `card_action` 的事件（含无 `event_type` 的旧式消息事件）ack 后略过，不参与聊天路由。部署没有该端点时事件轮询自行停止，问答退回纯文本路径。

事件 ACK 暂时失败时保留当前游标，按轮询失败相同的 5 秒退避继续读取和确认；不终止消费者，也不越过尚未确认的事件处理同批后续事件。事件处理返回可重试结果时同样间隔 5 秒再尝试，连续 5 次仍无法处理才确认并丢弃该事件，避免即时重投在故障恢复前耗尽预算。
卡片已发布但发送回执尚在途时，同聊天的有效 ask 点击保留为可重试事件，待远端 message ID 绑定到问题后再作答与 ACK；单题与整组卡都遵守该顺序。已结束发送且没有对应绑定的未知卡片仍按既有规则忽略，不能猜测绑定到另一道题。
回执到达并绑定后重新读取问题的持久状态：在发送途中已经通过文字作答或关闭的问题，单题卡与整组卡都补写当前状态；卡片展示与已记录答案一致，发送完成不会重新打开已结束的问题。

除 host tool 外，任务里的 Agent 还可以用本机 `octo-cli` 以本 bot 身份直接访问 Octo Bot API：宿主注册 Bot 后把该 bot 的 token 经 stdin 写入自己的 octo-cli 凭据目录（`~/.oco/octo-cli/<botUid>`，目录权限 0700，命令行与日志中不出现 token），并把 `OCTO_CONFIG_DIR`、`OCTO_API_BASE_URL`、`OCTO_BOT_ID` 注入 OMP worker 环境。一个 bot 一份目录，宿主服务多个 bot 时凭据互不共享。原始 token 不进入 worker 环境：OMP worker 继续按前缀剥离宿主继承的 `OCTO_*` 与 `OMP_CHANNEL_OCTO_*`，只有这三个名字允许进入子进程。凭据准备是 best-effort，octo-cli 缺失、登录失败或返回的 robot_id 与当前 bot 不一致时只记录一条有界日志并保持不注入，不影响启动与任务。因此 host tool "目标固定为当前聊天" 的承诺只约束 host tool 自身；经 octo-cli 的调用不受该绑定限制，其授权完全由服务端按本 bot 身份判定。`channel_control` 的说明同时告知 Agent 这条路径，并要求它先用 `octo-cli auth status` 自证身份，身份不是本 bot 时不使用。


### RPC 与输出

worker ready 后协商协议版本；本地实现保持 OMP v18.1.18 兼容的 RPC 解码，按请求 ID 匹配响应并正确处理 v2 分块；宿主独立管理 worker 生命周期。`agent_end.willContinue=true` 表示仍有后续生命周期或消息，必须继续等待，不提前收尾正文或 typing；prompt 接受不代表任务完成，以生命周期事件和异步错误判断结果；本地完成但未调用模型的 prompt 也必须结束状态。

按需启动 worker；同一持久会话只能被一个 worker 写入。新会话只通过 fresh RPC `new_session` 创建并立即落盘；对已有绑定，恢复前先按 session ID 与 `previousSessionFiles` breadcrumb 在 native roots 中寻找并验证唯一外移候选，找到后持久化重绑；扫描或验证失败则保留原绑定并报告失败，不能用“最近会话”替代精确身份。恢复 worker 时仅传入已经确认存在且准确的 session 文件和保存的目录。正常退出释放 worker。
OMP extension 在 worker 启动时由固定路径自动加载；sidecar 根路径通过宿主显式 allowlist 的非秘密 worker 输入传给 extension，sidecar 在真实 session ID 确认后、第一次 `prompt` 前原子发布，extension 在生命周期回调中按该 ID 精确读取并写入 `prepared` receipt。绑定 session 指针在该 turn 的第一次 `prompt` 前发布，并作为该作用域的当前 session 保留；worker 进程内由 OMP 打开的 subagent 或 eval 子会话因此不会被当作 channel turn，extension 不按 cwd、全局路径或模糊 session 猜测身份。宿主必须能观察 matching receipt 和 prompt acceptance，并以 attempt ID 做单调 CAS；worker 停止、重启、恢复和 compaction 不得绕过 `pending`/`committed` 判定。宿主不向 extension 暴露 Octo 认证凭证，extension 不得按 cwd、全局路径或模糊 session 查找 sidecar。

`WorkerEvent` 的正文事件为稳定的本地 `messageId`、累计正文快照和 `final` 标记；上游没有原生 ID 时由 adapter 生成。每个 assistant message 独立维护 stream，首次非空快照立即创建一条正文消息，后续累计快照只编辑同一个远端 message ID；不同 assistant message 不合并。`final=true` 是该消息的权威结束快照，允许比此前更短或为空；已有远端消息必须编辑到最终空文本，尚未创建且从未有非空正文的空最终事件不发送空白新消息。

正文增量可先于 `message_start` 到达；迟到或重复的开始事件复用当前尚未结束、上游身份兼容的 stream，保留累计正文和本地 message ID。消息结束后或出现明确不同的上游身份时才分配下一条消息 ID。

正文编辑以最新累计快照为准，首次创建不等待整轮结束；编辑最多每 1000ms 一次并按目标串行，最终快照优先完成，不得由旧快照覆盖新快照。正文按 3000 UTF-8 bytes 上限分段，每段在自己的窗口（该段起点起 3000 bytes）内取层级最高、同层最靠后的自然断点：段落/换行 > 句末标点（。！？；…! ? .）> 逗号/顿号（，、,;）> 空白；窗口内没有任何断点（如无分隔的长串、URL、代码）才在该窗口末尾硬切，ASCII 标点只在后面是空白或文本结尾时才算断点，避免小数、缩写与 URL 里的点被误判。断点字符归上一段，其后的空白留在下一段开头，不修剪也不吞并。每段的边界只由该段自己的窗口决定，因此已由满窗口定界的段在流式增量下逐字稳定、不重排，规模变化只发生在仍在累计的最后一段及其新增段；保留原始换行、空格和 inline 标记；分段 stream 使用稳定的 client message ID，分段数量变化时清理 stale tail。每次网络操作前持久化该分段的目标快照及 `desiredVersion`/`ackedVersion`；首次 create 在网络请求前 durable 标为 `unknown`，送达未知时不重跑 Agent，重连/重启沿用稳定 ID 绑定已创建消息并将最新 desired 快照补做 edit。

真实 `tool_start`/`tool_end`、`turn_start`/`turn_end`、`todo_update` 和 `run_end` 事件由单一 `ExecutionTracker` 累计阶段、工具、todo、终态和 elapsed；每一轮——任务开始的一轮，或追加消息开启的新一轮——各自在其第一份真实工具或 todo 进度出现时懒建一张可编辑卡，之后只编辑该轮的卡。追加消息被接受时，上一轮的卡片立即以一次终态编辑收尾（`completed`），新的一轮从自己的第一份真实进度起在会话底部另开一张卡，因此正在看的进度始终在最新消息下方，而不是停在任务最初那次工具调用处；该轮的卡沿用任务当前的 todo 清单，阶段、工具与耗时只统计本轮。运行中 elapsed 只在真实事件到达时随卡片刷新，事件编辑遵守 1000ms 合并窗口，无事件时不做周期重绘；卡片 edit 使用严格递增的单卡 sequence，终态为 `completed`、`cancelled` 或 `failed`。卡片采用“摘要头部—当前状态—任务清单—子代理—执行轨迹”的进度通知布局；任务清单按阶段→任务的树形层级渲染，使用分支连接线和嵌套区块表达父子关系；任务节点只显示状态图标、任务内容和 blocker，不重复渲染状态文字；富布局下阶段标题与任务分支使用结构化 ColumnSet 分列，避免依赖比例字体空格对齐；富布局能力下使用强调色 Container、状态/耗时摘要和带状态元数据的步骤面板，轨迹步骤使用 Web 端兼容的 ColumnSet，轨迹行使用固定 24px 等宽标记列和 stretch 正文列，状态摘要置于正文列并允许自然换行，避免窄屏下正文被状态列挤压；状态图标与步骤内容、状态摘要同处彩色背景 Container 内；子代理列表位于执行轨迹之前；当对应区块超过三个步骤且能力支持 `Action.ToggleVisibility` 时，在标题行右侧提供“展开”/“收起”控件，默认展示最近三个步骤，其余步骤通过“展开”查看；能力支持 `Action.ToggleVisibility` 时，卡片头部始终提供“收起”/“展开”整卡详情控件：运行中默认展开任务、子代理和执行轨迹详情，收起后只保留摘要头部、当前状态与告警；终态卡片默认收起这三类详情，保留状态摘要，并可通过头部的“展开”恢复；状态标记按语义统一：成功/已完成使用绿色 `✓`，等待、取消和阻塞使用中性灰色 `-`，失败和放弃使用红色 `×`，进行中使用蓝色/Accent `•`；取消任务内容在支持 `RichTextBlock` 时使用删除线；能力不足时保持信息完整的降级文本。内置 `hub`/IRC、`task`、`todo` 和 `ask` 工具使用操作级安全摘要，IRC 轨迹显示方向、目标或协作状态，不显示消息正文；命令类工具显示压成单行的有界命令文本摘要，便于在轨迹里直接看到所运行的命令。卡片只展示安全摘要，不转发工具参数/结果、原始 payload、模型思考或秘密。超出渲染预算且仍可展开时，轨迹与子代理都使用同一组紧凑行，并放进各自区块的灰色 emphasis 历史带：每个步骤一行文本，状态字形后用不换行空格连接 `·` 与摘要，仍按状态着色，不用 ColumnSet 分列，以便同样的节点预算容纳更多隐藏行；能力不支持展开时没有可隐藏的状态，这些紧凑行照常显示（历史带保持可见），隐藏计数同样照常给出。
富布局下子代理区块由 OMP 自身的 subagent 事件驱动，而不是从工具调用名推断：worker 订阅 `progress` 级别后，`subagent_lifecycle` 的 `started` 记下一个真实的子代理（取 payload 的 `id`、`agent` 与可选 `description`），`completed`/`failed`/`aborted` 才是它的终态，`subagent_progress` 提供进行中的 `status` 与可选 `lastIntent`；同一 id 的终态之后不再被进度帧复活，`aborted` 归一为“已取消”。卡片只关心子代理的整体状态：行内容是 agent 名称、用途摘要、生命周期状态，以及当前正在运行的工具与已用工具次数（`<n> 次调用`），不渲染每个子代理自己的 `HH:mm:ss` 或耗时，也不展示 `subagent_event` 之类的子事件；子代理自己的会话记录保留全部细节。仍在运行或等待的子代理作为默认丰富行；已完成、失败、取消或停止的子代理默认隐藏，能力支持 `Action.ToggleVisibility` 时随“展开”在子代理区块的灰色 emphasis 历史带（`subagent_omitted_steps`）里以紧凑行查看，每个子代理只渲染一次，能力不支持该动作时该带保持可见而不是被折叠藏起；卡片只渲染事件报告过的子代理，OMP 不提供该订阅时该区块整体不出现（worker 记一条日志并照常执行）。执行轨迹默认展示最近三个工具步骤的丰富行，其余步骤（丰富窗口裁掉的较旧行与被预算剪掉的步骤）统一渲染在轨迹区块的灰色 emphasis 历史带（`timeline_omitted_steps`）里，一条单行紧凑文本一个步骤；该带是步骤列表 `timeline_detail` 的兄弟节点而不是子节点，因为 Web 客户端的 agent-progress 层会把 `#timeline_detail` 直接子级里有填充的 Container 重绘成失败步骤红块，放在外面才保住灰色填充。丰富行在状态摘要行首显示该步骤的 `HH:mm:ss` 本地墙钟时间（取快照里持久化的 `startedAtMs`，重放补发的终态卡同样显示），紧凑行是单行文本、不带时间。当前 OMP worker 以通用 RPC `tool_execution_start`/`tool_execution_end` 形成安全工具事件：`bash` 的摘要是压成单行、截断到 72 字符的命令文本，路径类工具只取安全文件名组件，其余工具按操作语义派生；命令文本中的凭据形态字符串由卡片层统一脱敏，宿主始终不转发原始 args/result。OMP 另有可选的 `set_subagent_subscription` 生命周期/进度事件桥，但它不属于 `pi.on` 专用 hook，且尚未纳入本服务的 `WorkerEvent` 卡片契约。
任务清单是本次运行对用户的承诺，执行轨迹是可展开回看的过程记录，因此节点预算不足时先压执行轨迹、任务清单最后才挤：适配循环对“完整可见任务清单”从最多 32 个可见工具步骤起逐级下调，每一级内部先按 8/4/2 收缩可展开隐藏行的渲染行数，全部级别都放不下时才按 `32/24/16/12/8/6/4/2` 的梯级缩小可见任务带，最后一级只保留隐藏计数。被裁剪时保留隐藏任务摘要；支持 `Action.ToggleVisibility` 时，标题行显示“展开”/“收起”按钮，展开后按原阶段和原任务顺序把可展开的隐藏任务插回树形位置，并复用富布局任务行的状态标记、颜色、blocker 与层级连接。可见任务围绕交接带选取：先钉住所有 `in_progress` 与 `blocked` 任务，再从交接锚点（第一个进行中任务，其次第一个未完成任务，全部完成时取末尾）向两侧扩展、已完成侧优先，使“已完成 ↔ 未完成”的分界及其前后若干条始终连成一段；可展开的隐藏任务取距离交接带最近的那些（上限 `min(hiddenRowLimit, 6)`），展开即向外延伸该段，而不是跳到清单两端。只有既没有可见任务、也没有可展开隐藏任务的阶段不渲染，避免出现没有子节点的裸阶段标题。能力不支持该动作时只保留安全的隐藏计数。

发卡前必须通过能力 profile 门禁：profile 启用，包含 `octo/v1` 与 card version 1.5，且 card/display/reasoning 开关均启用；`TextBlock` 是唯一硬依赖，`Container` 等布局元素缺失时使用扁平 fallback；`Action.ToggleVisibility` 仅在能力声明支持时渲染。遵守服务端声明的 payload、node、depth 等 limits：适配搜索按实际 wire envelope（`card` 加外层帧字段）统计节点数、深度与字节数，与服务端口径一致，避免选中一个服务端必然拒收的候选；无法满足时不发卡且不阻断正文；同一轮最多一张卡。

每张卡各自一行，按 `(botUid, taskId, messageId)` 持久化：建卡成功即写入远端 message ID、sequence 1 与当时的快照，之后每次被服务端接受的 edit 覆盖为新的 sequence 与快照，终态 edit 成功后删除该行。同一任务的多张卡互不覆盖，追加消息收尾上一轮时它仍是自己那一行，因此每一张遗留的卡都能被独立补发。进程重启后仍遗留的行由新进程补发一次终态编辑：sequence 取持久值 +1，状态按任务的终态取 `completed`/`failed`，其余（含重启中断）取 `cancelled`，快照由持久载荷重放同一个 tracker 得到（子代理行也按生命周期帧重放，保留其 id、agent、起始时间与时长；重启时仍在跑的子代理随该次 `run_end` 落到 cancelled），因此轨迹、脱敏与终态规则与在线回合一致。补发失败时保留该行并记录有界原因，且把持久 sequence 一并加一，避免与可能已落地但响应丢失的上一次尝试撞车；同一行累计尝试达到上限后丢弃并记录，不无限重试。补发遵循与在线 edit 相同的 2 秒有界 deadline，失败或载荷不可解析都不阻断启动。

typing 由按聊天单例的租约环驱动：agent-attached 消息在权限门通过、判定交给 agent 后立即发出（普通消息在待回答问题判定之后、附件组装之前；未注册 `/xxx`、`/queue`、`/thread`、`/thread merge` 与 observing/intercepting 命令在各自交给 agent 前的同一点位），其后每 3 秒续期；同一聊天任一时刻至多一条续期环，owner 为 `msg:<messageId>` 与 `task:<id>` 租约——任务被持久接受时并入 task 租约、环不重启，同聊天排队与跨聊天同目录等待期间保持亮起，任务终态（完成/失败/取消/启动失败）释放，排队中 `/cancel` 等一切漏释放路径由每 tick 的任务行状态兜底回收，消息租约的释放由调用方 try/finally 硬保证（覆盖附件拒收、拒绝抛错、claim 去重早退等一切出口）；服务停止时切断新 acquire 并在 activity settle 后、store 关闭前释放全部租约；非 agent 命令、待回答问题答复、成员命令提示、不支持类型、权限拒绝与 Bot 回声一律不发送 typing。每个 typing/card 活动请求使用独立 2 秒 deadline，终态卡片使用独立短 signal。运行中卡片失败可按有界节流重试；终态 edit 失败只做一次 best-effort，随后 dispose 卡片活动，不无限重试，其遗留的持久记录由下一次启动补发。卡片正文被 Bot API 之前的部署边缘拒绝时——响应的状态码来自边缘本身、正文不是 Bot API 的错误信封，因而没有机器错误码——该轮改用不带工具与子代理步骤摘要的形态重试，并沿用至该轮的终态编辑：切换一次即成，状态、计数、任务清单与子代理行照旧，被拒事件与切换各记一条有界日志。卡片队列 promise 纳入服务生命周期并在停止时于任务结束后等待其有界收敛，不能拖延正文投递、取消 kill、目录解锁或正常业务。typing/card 失败不阻断正文或业务。

typing 的已排定 tick 在服务进入 stopping 后直接回收该租约环，不再读取任务状态或发起续期请求，避免停机等待期间继续增加后台活动。

### 持久化、调度与恢复

本地 SQLite 保存聊天绑定、动态允许集合（`allowed_chats`：运行中开通的聊天及其 `granted_by`/`granted_at`）、任务、入站去重键、问题、出站记录、进度卡记录和任务行上的派发回传登记（`tasks.relay_channel_type`/`relay_channel_id`/`relay_thread_name`：回传目标与子区名，空 = 不回传），OMP 自身保存对话。入站唯一键使用 Bot 身份、聊天类型、真实聊天 ID 和服务器消息 ID。没有可靠 ID 的任务拒绝执行。去重记录与接收状态事务写入成功后才确认接收；状态盘写入失败时不发送成功 ACK、不启动 Agent，并保留可重试的命令状态。每个聊天的追加模式（`steer`/`queue`）持久化在与绑定、任务同一套状态盘中，未写入行时按 `steer` 处理。作为 steering 消费的入站消息同样先 durable claim 再发送 RPC 帧：claim 成功而 OMP 拒绝该帧时释放 claim 并回退为普通排队任务，已 claim 未确认的消息在服务器重投时不会重复注入。
共享说明的持久 marker 与 sidecar 状态属于 SQLite 中的 session context ledger，至少记录 `botUid`、真实聊天目标、真实 OMP session ID、当前 server version、`pending`/`committed` 阶段和 injection attempt ID。marker 的提交必须是同 session/目标/version 的 CAS；同一 pending 在重放前沿用其 attempt ID，提交后不得再次接受旧 attempt。新 session 不能继承旧 session marker，外部移动若保持同一真实 session ID 则保留 marker，`/new`/`/reset` 产生新 session 时清空其 marker。sidecar 与 marker 发布、extension 注入确认和 `description-write` 的后续 version 发布均不得以占位 session ID 完成。

状态为 queued、started、completed、failed、cancelled、interrupted。启动 Agent 前持久化 started；跨此边界后永不自动重跑，即使崩溃发生在写入与实际 prompt 之间。每条 assistant 正文 stream 的每个分段独立持久化 outbox，任务终态只保存真实 assistant 正文（无正文则为空），并与终态状态写入 durable store。保存的不只是内存队列。正常运行按接受顺序调度，同规范化目录串行；不同目录不提供重叠树、硬链接或外部终端写入隔离保证。

服务重启将遗留 queued 和 started 标记 interrupted，清除自动执行资格，在重新连接后向原聊天报告需重新发送。历史和当前绑定可恢复不意味着任务继续执行。重启会使未完成问题等待失效；去重记录仍保留，服务器重投同一消息不能重新启动副作用；用户主动发送的新消息产生新的任务。

取消是控制路径，不在普通任务队列后等待：发送 abort，等待 worker 停止；超过 10 秒关闭该 worker 进程树。只有确认进程退出且 channel 管理的执行已停止后才释放目录锁；无法确认则保持该目录阻塞并报告未知状态。取消不回滚已发生的副作用，不保证已派生到外部系统的工作停止。服务启动恢复前核查自身管理的遗留 worker；不能确认停止时不运行冲突目录的新任务。迁移操作无法确认停止时同时保留 source/target 两目录 blocked，跨重启继续生效。

服务停止时先封闭新的入站处理并中止附件下载、语音转写和免@查询，等待已开始的入站清理完成后才关闭状态盘。尚未持久接受的入站以有界取消错误返回，使传输层保留重投资格；附件组装释放临时 claim、删除本次新建文件，重启后同一消息可重新接收。即使在途 I/O 恰好成功返回，也先检查停止状态，再决定是否进入后续处理。

Octo 断线不取消已经开始的 Agent；正文 outbox 与任务状态持久化，重连后按聊天顺序继续投递，不重跑任务。重连采用有上限退避（1s 起、翻倍、上限 30s，向下抖动）并重新认证；服务端主动 DISCONNECT（被踢，如同一 Bot 的另一次登录接管会话）与底层断线走同一条退避重连路径；只有注册或 CONNACK 认证失败才停止重连并给出本地明确错误。重复消息经持久去重。文字和文件 outbox 按聊天顺序发送，送达未知时沿用稳定 client message ID；投递失败按有上限退避重试（1s 起、翻倍、上限 30s、向下抖动），连续失败到 6 次或遇到永久失败（4xx，`err.server.bot_api.store_failed` 除外）就把该行标记 `dead`、在 `last_error` 与日志里保留真实失败原因，随即继续投递队尾——一条投不出去的消息不会把整个聊天永久静音；成功投递或内容更新会清零尝试计数。文件永久失败同样标记 dead 并报告，不阻塞后续文字回复。

会话文件按项目隔离存放在 `sessionsDir`（缺省 `~/.oco/sessions`，可配置）下：每个项目（任务绑定的 canonical cwd）一个 `<basename>-<路径摘要>` 子目录，worker 以该项目目录作为 `--session-dir` 启动——不同聊天、不同隔离子区工作区互不共享会话目录。改动前的 `<stateDir>/sessions` 扁平根保留在恢复候选里，已有绑定继续按记录的绝对 `session_file` 恢复。

外部移动恢复只接受精确 session ID 且通过 session 文件的 `previousSessionFiles` breadcrumb 证明身份；不按最近文件、不按时间、不按模糊 basename 选择。候选 roots 按 OMP native profile 与 `.env` 对当前有效 cwd 的解析结果取得，再加 channel 的会话根（该项目的 `sessionsDir` 子目录）与改动前的状态目录扁平 sessions 根。候选不唯一、无法读取或无法验证时保持原绑定，不自动猜测；唯一候选通过 session header 的身份与 cwd 校验后立即持久化重绑，不启动 worker。`refreshState` 仅用于原生 `/move` 与 fresh 命令的 worker state 校验。

## 验收标准

1. 实际 Octo 私聊发起文件操作，在选定目录观察结果并收到完成回复；全程没有工具审批。
2. owner 在允许群 @Bot 和允许的 CommunityTopic 线程（channelType=5）可执行：线程的允许关系继承父群，父群在允许列表里时该群下新建的线程无需额外配置即可对话，父群不在允许列表的线程一律拒绝；其他成员、未 @、伪造文本 @、Bot 回声均不启动 worker 或命令。
3. `/new`、`/reset` 省略目录时按目标默认目录解析的固定顺序取目录：已有已验证会话沿用绑定 cwd，线程尚无会话时取父群绑定 cwd，其余使用 `~/tmp`；显式目录（含空格）规范化为真实目录；`/move <目录>` 使用原生 OMP `/move`，同一 session ID 保留历史与附件，非法目录或校验失败不改变绑定。
4. 首次普通消息创建默认目录会话（DM/群为 `~/tmp`）；从其他目录再次 `/new` 或 `/reset` 仍沿用当前绑定目录并创建 fresh session。
5. 私聊与两个群/线程的上下文不串线；交错完成的结果各自返回原聊天；同一持久 session 在共享说明 version 不变时连续任务不重复注入，version 变化时只注入一次新的完整快照并给出变化说明；共享说明读取失败不启动 worker。
6. 私聊获得 `ask`、`octo_send_file` 与 `channel_control`；群/线程额外获得 `octo_management`，其 `description-read` 实时读取对应服务端 `GROUP.md` 或独立 `THREAD.md`（分别对应 `groups/{id}/md` 与 `groups/{parent}/threads/{short}/md`），`group-info`/`group-members`/`group-update`/`list-threads`/`create-thread`/`thread-info`/`thread-members`/`thread-join`/`thread-leave`/`thread-delete` 作用于当前群或当前线程，写操作依赖服务端授权；`thread-dispatch` 把一条任务派发给本群 thread，交付按该 thread 的追加模式处置（并入可接收 steering 的运行中回合，否则成为该 thread 的任务）、结果如实回到工具结果与发起群回执、向两个聊天各投递一条可见说明，派发深度为 1；新建和无可靠 marker 的恢复 session 首次注入共享说明，普通未变化 turn 不注入；工具不能改写目标聊天或 cwd。
7. 同规范化目录的两个聊天写入任务不重叠；`/new`、`/reset`、`/move` 在运行或排队时拒绝；`/move` 同时取得真实 source/target lease，未确认停止时两目录跨重启保持 blocked。
8. 长正文保留原始换行、空格和 inline 标记；每个 assistant message 独立 stream，首次非空累计快照立即 create，后续累计快照以同一 message ID 每 1000ms 最多一次串行 edit，最终更短或空快照权威生效；正文按 3000 UTF-8 bytes 上限分段：窗口内取 段落/换行 > 句末标点 > 逗号/顿号 > 空白 的最高层自然断点，无断点才硬切，已由满窗口定界的段不随流式增量重排，并清理 stale tail，异步 prompt 失败、本地完成和 worker 异常退出均正确结束任务状态，不生成通用完成文字。
9. 正文 outbox 在 create 前 durable 记录 `unknown`，保存 desired/acked 版本；断线、重启或送达未知恢复时沿用稳定 client ID、编辑最新快照且不重跑 Agent，不因失败重复创建；单条投递的失败有界收敛——退避重试到 6 次或遇到永久失败即标记 `dead` 并把队尾让给后续消息，重启恢复仍从队首排空 pending。
   失败归属实际发出的快照版本：在途旧版本失败时若已有新 desired 版本，不消耗新版本的重试预算，也不据旧错误将新版本标记 dead；未知送达后的修正请求按修正时实际读取的版本计数。服务停止导致的在途请求中止不消耗投递预算，保留持久行供下一进程恢复，不因停机耗尽最后一次重试而丢弃正文。
   普通文字、文件和送达未知提示也纳入同一停机取消与排空流程；中止后的持久状态和重试次数保持不变。文件检查或未知提示结束后若服务已停止，不再开始下一次发送，恢复后沿用原 client ID 投递。
10. 执行过程中取消能越过待执行队列；后续队列被清除，取消不被宣称为回滚。未确认停止时不启动同目录新任务。
11. `ask` 问题可跨消息持久等待；owner 或已开通群/子区内成员在同一聊天的下一条非命令文本被当作答案：单个待答问题时按该问题校验（编号选项按单选/多选校验，其他文本原样返回），一次 ask 的多个问题同时待答时同一条文本作为整组答案写入每个仍未作答的问题（逐题按各自规则解释）并使该 ask 立即返回；不同聊天、无待回答问题与重复投递的文本都不作为答案，其中无待回答问题时的文本按普通任务处理；取消不使用默认答案。等待超时可配置：`ask.timeoutMs` 默认 6 小时、允许 30 分钟到 7 天，越界或非整数在下一次启动即被配置校验拒绝（`config.example.json` 给出 21600000 的示例）。等待超过该超时不作为过期：问题行保持 pending、卡片保持可提交、不发任何提示，当前回合作像被取消的 tool call 一样停住（任务记为 interrupted，agent 不自行继续）；owner 或成员之后的文本回复或卡片提交照常记录答案（并记录提交人 uid：`answered_by`，随 `answeredBy` 进入 ask 工具返回、随「由 <uid> 回复」进入卡片改写与唤醒文本）并作为同一 session 的新回合输入唤醒 agent（运行中的回合按该聊天追加模式并入，否则成为 durable 任务），同一答案不重复作答，超时后的部分提交与普通提交规则一致（已答不重复、未答保持待答）。宣布交互档时问题以 `octo/v2` 卡片投递：单题卡为选项按钮、选择列表或自由输入，选项题另带「其他」自由输入（填写后以它为准、覆盖选择）；一次 ask 的多个问题共用一张卡、每题独立输入 id、整卡一个提交，一次提交按题各做一次 CAS（同一事务），未填的保持待答并以新 generation 重绘，全部作答后卡片改写为终态（每题显示已回复内容）；owner 的点击在任何聊天生效、成员的点击在已开通群/子区生效，并与文本回复争用同一个答案判定，重复投递不重复作答；整卡超出 limits 或发送失败时回退逐题投递（单题卡或纯文本），卡片不可用时退回纯文本；事件队列按持久游标消费、处理后才 ack，非 `card_action` 事件与无端点部署都不影响问答。
12. 在接收、started 落盘、执行、回复阶段分别终止服务再启动：绑定可恢复，历史可读，遗留任务报告中断，同消息重投不再执行副作用；外部移动只按精确 session ID 与 breadcrumb 唯一重绑，roots 依 native profile/`.env` 有效 cwd 解析，不选最近文件。
13. Octo 断开再连接不重跑任务；已持久化正文从 outbox 继续投递，送达未知明确呈现；真实 `ExecutionEvent` tracker 每轮用一张卡累计工具/turn/todo/run 终态与 elapsed，只在真实事件到达时随卡片刷新（编辑按 1000ms 合并窗口推进，无周期重绘），遵守 TextBlock/Container fallback、ToggleVisibility 能力和 payload/node/depth limits（按 wire envelope 计数），卡片 edit sequence 单调递增，预算不足时先压执行轨迹、任务清单最后压，裁剪后仍保留交接带（进行中任务、其相邻任务与已完成/未完成分界）、隐藏任务摘要与可展开的邻近隐藏行，不渲染没有子节点的裸阶段标题，丰富轨迹行在状态行首显示该步骤的 `HH:mm:ss` 本地时间，安全摘要不含原始 payload 与参数对象（命令类工具显示单行、截断到 72 字符并经凭据脱敏的命令文本）；typing 每 3 秒续期、活动请求 2 秒有界，终态卡片失败只做一次 best-effort，均不阻断正文；正文被 Bot API 之前的部署边缘拒绝的卡片（4xx 且响应不是 Bot API 的错误信封）改用不带工具与子代理步骤摘要的形态重试，该轮此后的运行中编辑与终态编辑沿用该形态，切换一次即成、其余字段照旧；每张卡的身份、sequence 与最近快照各占一行持久化，终态编辑成功后删除该行，进程重启后仍遗留的卡片（同一任务可能多张）由下一次启动逐张补发一次终态编辑（序号严格递增、状态取任务终态、失败按有界次数重试后丢弃），使客户端无需重新执行任务即可离开「进行中」。
14. 状态盘写入失败不启动新任务；同 Bot 第二实例不能启动（在重新注册 Bot 之前即报错退出）；App Bot 配置不能被验收为支持群聊。
15. `launchd install` 仅写入权限为 `0600` 的 plist，不调用 `launchctl`；实际启动、停止分别由 `launchctl bootstrap "gui/$(id -u)" "$HOME/Library/LaunchAgents/com.omp.channel-octo.plist"` 与 `launchctl bootout "gui/$(id -u)/com.omp.channel-octo"` 完成，`launchd uninstall` 只删除 plist。环境凭证会进入该私有 plist，runtime 复用 plist 中安装时解析出的 OMP 路径；退出交互终端后仍能从实际 Octo 收发，日志不包含 token。
16. 新建 session 的第一次 agent start 会注入目标的完整共享说明；恢复 session 只在没有可靠的同 session/目标/version committed marker，或 marker 仍处于 pending 时补注入；已 committed 的恢复不会因重新启动 worker 自动重复注入。
17. 同一 session 的共享说明 version 变化时，OMP 收到一次完整最新快照和明确的版本变化说明；删除也按带 server version 的变化处理并明确当前无说明；version 不变的普通 turn 的 OMP prompt 不包含共享说明正文，也不把共享说明并入群历史块。
18. OMP compaction 后，压缩上下文保留当前 turn immutable snapshot 的完整共享说明和 version 边界；即使 version 不变也只在该 compaction 生命周期中恢复性注入，下一次普通 turn 不重复注入；当前 turn 的 `octo_management` `description-write` 不改写这份 snapshot。
19. 共享说明 sidecar、持久 marker 和 extension 输入按 Bot、真实聊天目标与真实 OMP session 隔离，不包含 Bot token；extension 或 sidecar 目标不匹配、输入不完整或 session ID 未确认时在进入模型前拒绝共享上下文；同一 worker 进程内非绑定的 OMP 子会话（subagent、eval）既不被注入也不被拒绝，只有绑定 session 在 sidecar 缺失或校验失败时进入该失败路径，从未发布绑定 session 的作用域沿用原有严格行为；marker CAS 失败时保留 pending、不得标为 committed，并在下一任务重放。
20. OMP prompt acceptance 与 context marker 提交之间发生崩溃时，pending 状态可恢复并在下一任务重放，不能静默跳过；正常成功路径不重复注入同一 version，重放使用明确的 injection attempt ID。
21. `/restart` 只使用检测出的守护进程，未检测到守护进程时明确拒绝且不猜测重启机制；存在运行或排队任务时默认拒绝并提示 `/cancel` 或 `/restart now`；`now` 先持久化重启请求再执行重启，发起聊天收到“正在重启 channel”，进程恢复后在发起聊天与被打断会话投递重启完成通报，超过 10 分钟的旧通报不投递；守护进程未停止进程时 channel 继续运行并记录告警。真实 CLI 端到端覆盖检测、进程自行以 0 退出以及重启后的确认投递。重启中断在途任务时，该任务已发出的进度卡由重启后的进程补发一次终态编辑（sequence 取持久值 +1、状态 cancelled），不再停留在「进行中」。
22. CommunityTopic 线程在尚无已验证会话时，其默认目录取父群当前绑定 cwd；父群无绑定、真实 channel ID 不含合法父群段或父群目录不可用时回退 `~/tmp`，不拒绝任务。线程首次成功建立会话后 cwd 固定，父群随后 `/new`、`/reset`、`/move` 不改写该线程；已建绑定但从未成功建立会话的线程在下一个任务重新按父群解析并写回绑定；启动时不对存量绑定做一次性回填。线程继承期间仍使用自己的 session、自己的 `THREAD.md` 与独立 marker，任务按规范化目录与父群串行，不新增用户可见提示。

23. 追加模式按聊天目标持久化并在重启后保留，默认 `steer`：`steer` 模式下运行中收到的普通文本经持久 claim 后作为 OMP `steer` 注入当前回合，不新增任务或正文消息，并为该轮新开一张进度卡（上一轮的卡以 `completed` 收尾）；`/mode queue` 后同一文本走 durable acceptance 成为排队任务，独立正文与进度卡；`/queue <文本>` 在任何模式下都走排队任务（正文经同一附件组装点：随消息发来的附件落盘后以绝对路径进入排队任务正文）；没有运行中的回合、回合已结束或 OMP 拒绝该帧时该文本回退为排队任务而不丢失；同一 messageId 重投只注入一次。`/interrupt` 中止运行中回合并保留该回合已追加的消息及其后的排队任务，worker 进程不被终止；回合因中止结束且无后续真实事件时任务记为 interrupted、进度卡记为 cancelled，回合继续产出时正常结算。`/stop` 与 `/cancel` 等价，清除排队任务与未消费的追加消息。追加消息的消费可见：被消费的 steering 在并入回合上下文时、确实等待过的排队任务在开始执行时，各在该聊天补一行有界回执；仅投递成功而尚未消费、或被取消/重启丢弃的追加消息不发回执。

24. 群级免@：服务端 `mention_pref.effective` 为真时，owner 在该群及其线程发送的未 @Bot 文本正常启动任务；`effective` 为假、查询失败或响应不可解析时不启动任务、不回复也不落任何入站副作用；同一个群在 60 秒缓存窗口内只查询一次，带 mention 的消息不触发查询；非 owner、不在允许列表或 Bot 回声在任何情况下都不产生该查询。

25. 线程隔离：`octo_management` 的 `create-thread` 带 `worktree_name` 时，在调用方当前目录所属仓库旁建立独立 git worktree（本机有兼容 wt 时经宿主调用 `wt switch --create`，否则经部署的 OMP 可执行文件的 `omp worktree add`，clone-first 复制被忽略文件），工作区目录与分支即该名称（slug 截断 32 字符，被占用时退到 `<slug>-<short_id>`），并把新线程绑定固定到该目录（`chats.cwd_pinned`）；该线程下一个任务以工作区目录启动自己的 session，父群随后 `/new` 改目录不影响它；工作区目录被删除时线程按普通目录顺序回退父群目录而不是拒绝任务；显式 `/new <目录>`、`/move <目录>` 解除固定；名称不含 ASCII 字母或数字时在创建线程前以参数错误拒绝；worktree 创建失败时不改写已创建的线程，工具结果返回单行、≤200 字符的 `worktree_error`；省略 `worktree_name` 时线程照旧继承父群目录。

26. `/thread`：群聊中 owner 的 `/thread <任务>` 只把意图转成当前聊天的一个任务（正文含原始意图与交付说明：由助手自行确定子区名称与 `worktree_name`、`create-thread` 建区、`thread-dispatch` 派发；派发正文按 SDD 格式写——清晰到可直接生成 SDD 的需求直接写清、由子区立即生成 SDD 并开工，否则发起会话只做够派发的最少澄清、由子区把剩余需求按 SDD 格式澄清成 SDD 后再实现），命令本身不建子区、不建工作区、不发回执；随后助手按该说明建出子区与独立工作区（子区名与工作区名由助手决定，不再由任务文本机械派生）、子区绑定固定到工作区、任务以该目录启动自己的 session 并在子区显示派发说明、发起群收到一行如实描述这次交付（并入运行中回合或作为独立任务执行）的回执；任务文本为空回复用法；私聊与子区中的 `/thread <任务>` 调用明确拒绝且不产生任务（子区中的 `/thread merge` 是独立的合并入口，见 31）；正文按该聊天的追加模式处置：运行中的回合能接收 steering 时交付说明并入该回合（不新开任务），否则成为 durable 任务并在正忙时排队等待；随消息发来的附件（例如富文本里的截图）与普通任务走同一条组装点，落盘后的绝对路径写进原始意图，不再只剩 `[图片]` 占位。

27. Agent 的 Octo 身份：注册 Bot 后宿主把该 bot 的 token 经 stdin 写入 `~/.oco/octo-cli/<botUid>` 的 octo-cli profile（目录 0700，token 不出现在命令行、日志与工具结果中），并只把 `OCTO_CONFIG_DIR`、`OCTO_API_BASE_URL`、`OCTO_BOT_ID` 注入 OMP worker；宿主继承的 `OCTO_BOT_TOKEN` 与其他 `OCTO_*` 仍被剥离，不进入子进程；每个 bot 一份独立凭据目录，后注册的 bot 不会复用前一个的凭据；octo-cli 缺失、登录失败、响应非 JSON 或返回的 robot_id 与当前 bot 不一致时只记录一条 ≤200 字符且不含 token 的日志、保持不注入，channel 照常启动并继续处理任务；任务里的 Agent 可以 `octo-cli` 以本 bot 身份访问未被 host tool 包装的 Octo Bot API，该路径不受 host tool 的当前聊天绑定约束，授权由服务端判定。

28. `thread-delete` 的瞬时失败重试：首次响应为 `err.server.bot_api.store_failed`（线缆 HTTP 400、body 声明 `http_status: 500`）或任意 5xx 时，用同一 `short_id` 换新连接重试一次（第二次调用携带新连接标记，不复用连接池连接）；重试成功时工具返回「已删除线程 `<short_id>`」且线程从列表消失；重试仍失败时工具错误被压成单行、≤200 字符并保留机器码（`err.server.bot_api.store_failed`；多行与超长服务端正文都在压缩截断范围内），线程保持存在、不报告假成功；4xx 参数与权限拒绝只调用一次、不重试。删除成功后按 `force` 口径联动清理 `cwd_pinned` 工作区（见 31）：干净工作区被删除（经 wt 或 git 回退）并在回执写明，有未提交改动且未传 `force` 时保留并提示 `force=true`，`force=true` 时丢弃未提交改动；工作区已不存在时回执说明；清理失败只进入回执、不影响已生效的删除。

29. 未开通群/子区的 owner 自助开通：允许列表为配置 `allowedGroupIds` 与状态盘 `allowed_chats` 的并集（线程继承规则对两者一致）。owner 在未开通群或子区 @Bot 时恰好收到一条短通知（含固定口令，同一聊天 10 分钟内不重复提示），不启动任务、不落 `inbound`、不写 `tasks`；owner 仍以 @Bot + 剥离 mention 与首尾空白后恰好等于 `开通本群` 的文本回复时，该聊天写入 `allowed_chats` 并把 ID 追加进配置文件（原子写、保留权限与其余字段），下一条消息即正常执行、无需重启，重启后仍有效；配置写回失败只影响镜像并明确告知，不撤销开通。非 owner、未 @Bot、近似文本与 Bot 回声一律保持静默拒绝；子区开通只覆盖该子区，父群开通后其子区按继承生效；已开通群不受影响。
30. 进度卡的子代理区块只来自 OMP 的 subagent 事件：worker 启动时以 `set_subagent_subscription` 订阅 `progress` 级别（失败时只记一条日志，worker 照常可用），`subagent_lifecycle` 的 `started`/终态与 `subagent_progress` 的进行中状态被翻译为 `subagent_start`/`subagent_update`/`subagent_end`；卡片按事件的真实 `id`、`agent`、`status`、`lastIntent`、`currentTool` 与 `toolCount` 渲染运行中/已完成的子代理并计数，行内只有整体状态与工具活动（不渲染子事件、每个子代理的时钟或耗时），同一个 id 的终态不被后续进度复活，run 结束仍无终态的子代理按该回合终态收尾；子代理行不进入执行轨迹、不使用工具名推断；卡片持久载荷包含子代理行，重启补发时按同样规则重放；工具名（如 `task`）在轨迹里只作为普通工具行出现。

31. 子区工作区的 Worktrunk 生命周期：本机存在兼容 wt（稳定 v0.76.x，探测接受版本输出恰为 `v0.76.<n>` 的可执行文件）时，`create-thread` 的 `worktree_name` 由宿主经 `wt switch --create <branch> --no-cd --format json --config-set worktree-path=<候选路径>` 在调用方所属仓库旁创建同名目录与分支（hooks 按项目 `.config/wt.toml` 执行，宿主不传 `-y`/`--no-hooks`，120 秒上限、随工具取消信号中止）；wt 缺失或版本不受支持时创建走 OMP 回退、行为与 25 一致，wt 存在但创建失败或超时则按失败回报（不回退），仍按 25 的口径以 `worktree_error` 保持线程可用。子区中 `/thread merge`（channelType=5 且绑定 `cwd_pinned` 工作区、部署提供隔离能力、wt 可用）命令只注入一条合并指令 prompt——要求助手调用 `octo_management` 的 `thread-merge` 而不是自己运行 wt，默认走 wt 默认 pipeline（命令即 owner 对合并 + 清理的确认：除非有明确必要理由并向 owner 说明，否则按默认参数执行、合并成功后删除工作区与已合并分支，要保留工作区须说明理由并显式传 `remove:false`，工作区删除导致的本子区 cwd 失效是既定结果、owner 已知（不反复说明，也不作为保留理由））、附工作区路径，其余按追加模式交付——命令本身不执行 wt；主群、私聊、未绑定工作区的子区、未配置隔离能力的部署以及 wt 缺失或版本不符时只回复提示、不产生任务。`thread-merge` 由宿主以工作区为 cwd 运行 `wt merge --format json`（不传 `-y`，600 秒上限、随工具取消信号中止）：参数默认 target 取仓库默认分支、`squash`/`commit`/`rebase`/`remove`/`ff` 默认 true（false 映射 `--no-*`）、`stage` 默认 `all`；只接受当前子区且要求工作区目录存在并为 linked worktree，否则拒绝；成功返回 wt 的 JSON 结果（分支、目标、squash/rebase/commit/remove 状态），失败返回单行 ≤200 字符原因，rebase 冲突时工作区留在 rebase 现场、目标分支未改动。`thread-delete` 在服务端删除成功后按 `force` 清理 `cwd_pinned` 工作区：wt 可用时 `wt remove --foreground`（分支已合并即删除、未合并保留），否则 `git worktree remove`；干净工作区删除并在回执写明，dirty 且未传 `force` 时保留并提示 `force=true`，`force` 时丢弃未提交改动；工作区不存在时回执说明；清理失败只进入回执、不影响已生效的删除。
32. `/switch` 模型切换：无参数时回复本聊天当前模型（运行中的回合为该会话的模型并标注「运行中会话」，与本聊天指定值不同时并列；空闲时优先本聊天指定值并标注「本聊天指定」，否则为一次性 fresh worker 读到的 OMP 默认并标注「OMP 默认」）与按 provider 分组的可用模型列表（来自 OMP `get_available_models`，总模型数超过 80 时截断并说明总数），列表来源可解释为「OMP 已配置 provider 的可用模型」；带参数时把选择器交给 OMP 自己的 `/switch` 解析（`provider/id`、模型 id/子串、`@角色`、`:level`），成功即把解析后的 `provider/id:level` 写入按聊天目标隔离的 `chat_models` 并回执，失败回单行中文错误且状态不变，选择器含空白时直接按未找到处理；有运行中的回合时由该回合的活会话执行切换（不新建探测 worker，OMP 只改本会话、该回合继续运行），此后该聊天新建的 worker（任务路径与 `/new`、`/reset`、`/move`）都带 `--model <值>`（覆盖 resume 会话里记录的模型），服务重启后仍生效；`default`（不含 `/`）清除本聊天模型、之后跟随 OMP 默认，运行中的会话不被改动；探测 worker 是 fresh、不跑 agent 回合、独立临时会话目录的一次性进程（停止后从 worker ledger 清除、目录删除），不读写任何聊天会话；`/status` 增加 `model=` 行（未指定时为「未指定（OMP 默认）」），`/help` 与命令表包含该命令。

33. 派发回传：`thread-dispatch` 带 `notify=true` 的派发任务在其运行中终态（完成/失败/取消/中断）各向发起派发的聊天回传一条有界通知（消息 ID `notify:<子区任务 id>`，含子区身份、任务 id、状态与结果/失败原因/取消或中断说明；该聊天空闲时成为其一个任务，运行中且可接收 steering 时并入该回合），每个任务至多一条、重启后不重复；回传登记随任务行持久化，派发被并入运行中回合时不生效并在收据与工具结果中说明；未带 `notify` 的派发与一切非派发来源的子区任务不产生任何通知或额外回合；服务停止/重启导致的终态（`stopping` 期间的 `cancelled`、`markInterruptedOnStart` 的 `interrupted`）不产生回传。
34. 会话目录布局：OMP 会话文件按项目隔离存放在 `sessionsDir`（缺省 `~/.oco/sessions`，可配置、按既有 `~` 规则解析）下——每个项目（任务绑定的 canonical cwd）一个 `<basename>-<路径摘要>` 子目录（0700）；`/new`、`/move` 与该聊天下一个任务都以该项目目录作为 worker 的 `--session-dir`，同一个 cwd 稳定映射同一目录，同名但路径不同的项目互不混淆；外部移动恢复的候选 roots 为该项目的会话目录、改动前的 `<stateDir>/sessions` 扁平根与 OMP native roots；未配置 `sessionsDir` 的配置仍按 `<stateDir>/sessions` 工作，已有绑定记录的绝对 `session_file` 不受影响。
35. 成员参与：已开通群/子区内，成员（非 owner）以结构化 @Bot 发出的消息走与 owner 相同的入站路径（待答问题作答、附件组装、steering/排队、任务接受与失败分类），全部当前支持的内容类型都可用；成员未 @Bot 的消息、私聊非 owner、未开通群/子区的成员消息一律静默拒绝且零副作用（不落 `inbound`、不建任务、零 mention_pref 查询）；成员的 `/` 开头消息不执行、不交给 Agent，同一聊天 10 分钟内至多一条提示，owner 的命令行为不回归；ask 卡片在已开通群/子区内任何成员可点击/提交，答案记录提交人（`answered_by`）并进入 `ask` 工具返回值（`answeredBy`）与卡片改写（「已由 <名字> 回复」，查不到名字回退 uid），私聊与未开通聊天的点击仍被忽略且无副作用；文本与点击争用同一 compare-and-set；放开的只是「成员可驱动助手」，命令、配置与私聊面不放开。
36. 回答署名显示名：`ask` 已回复行的署名把 `answered_by` 的 uid 解析成显示名（`GET /v1/bot/user/info`；30 分钟 TTL、最多 200 条、单次查询 3 秒预算的有界缓存，同一 uid 的在途查询合并，失败不缓存）；查不到、超时或失败一律回退成 uid，解析失败绝不影响答案落盘、卡片改写与投递，`ask` 工具返回值里的 `answeredBy` 始终是 uid；卡片里署名以自带 `weight: "Bolder"` 的 `TextRun` 呈现，同帧 `plain` 文本回退（消息正文那一路）用 Markdown 加粗，两句同源；等待超时后的唤醒文本仍按 uid 标注提交人。
   显示名查询同步抛错与异步拒绝都只影响本次解析；清理在途记录后，下次查询同一 uid 必须能重新请求并取得恢复后的显示名。
37. 会话创建回执的模型提示：`/new` 与 `/reset` 共用同一会话创建路径，其成功回执在 session id 与 cwd 之后附该新会话实际生效的模型（`已创建会话 <id>，cwd=<目录>，模型=<provider/id[:level]>`）。模型在停止候选 worker 前取自创建该会话的候选 worker 自身——与 `/switch`、`/status` 相同的 `worker.models()` 只读状态查询，不发起生成回合：设定了聊天模型时，候选 worker 以 `--model` 启动，回执即该经 OMP 生效的存值（含 thinking level）；未设定时回执展示 OMP 实际默认模型，绝不把字面 `default` 当作模型名。模型查询失败或 OMP 未报告当前模型时，以不含模型的回执（`已创建会话 <id>，cwd=<目录>`）送达且不编造模型值，`/new`、`/reset` 的其余失败路径（目录无效、租约占用、会话校验或持久化失败等）的回执与行为不变；`/move` 迁移既有会话，不产生创建回执。
38. 群历史与「这个」关联、引用媒体的入站合同：带附件消息（含无 caption 媒体）在群/线程历史中存活为完整条目并渲染 `[文件 名称 (大小)]` 式标记（历史自身零下载，相对 preview 等不可用 URL 不保留）；受权消息本身无附件、无可用引用时按「同一发送者、10 分钟窗口、唯一候选」视同引用，经同一附件组装点下载（`maxBytes` 预检、8 条上限、单条 60 秒与整消息 120 秒预算、语音转写）并以绝对路径进入 prompt，`[系统提示]` 注明关联来源；歧义、跨发送者、超窗、未知 seq/时间、`groupHistory` 或 `attachments` 关闭时一律不关联，且歧义时明确请发送者引用具体消息、绝不虚构已收到或已读取；关联取回失败降级为纯文本 `[系统提示]` 而非拒收任务。显式引用文件（`reply.payload` 内联 type 8/9、绝对 http(s) URL）经同一张表成为可下载附件，被引用媒体无正文时以 `[引用 <发送者>]` 标题注明来源，相对 preview 路径整个引用不成立。
39. typing 即时反馈：agent-attached 消息（普通任务消息、未注册 `/xxx`、`/queue <文本>`、`/thread <任务>`、`/thread merge`、observing/intercepting 注册命令）在权限门通过、判定交给 agent 后立即发出 typing——普通消息在待回答问题判定之后、附件组装之前，各命令路径在各自交给 agent 前的同一点位；同一聊天任一时刻至多一条 3 秒续期环，owner 为 `msg:<messageId>`/`task:<id>` 租约：任务被持久接受时同聊天排队与跨聊天同目录等待期间保持亮起，任务终态（完成/失败/取消/启动失败）释放，排队中 `/cancel` 等漏释放路径由每 tick 的任务行状态兜底回收；消息租约的释放由调用方 try/finally 硬保证，steer 命中的消息租约立即释放且续期不中断；非 agent 命令、待回答问题答复、成员命令提示、不支持类型、权限拒绝与 Bot 回声一律不发送 typing；服务停止时切断新 acquire 并在 activity settle 后、store 关闭前释放全部租约。
