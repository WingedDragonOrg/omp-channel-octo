# 本地文件链接解析器设计

日期：2026-11-11

## 用户原始需求

1. 「能想办法制作一个插件吗？负责识别，然后提供抽象，支持多种实现，比如：zed, 可以替换成 zed 可识别链接(注意可能是远程需要 zed ssh 的)，比如: octo, 可以把部分文件上传到 octo, 并替换为上传后可访问地址，具体由实现自己 isMatch」「只服务 omp-channel-octo, 且注意 zed 应该支持配置，比如当前channel ssh 信息是: hostname: my-mini」。
2. 「先只支持 Zed」：首期范围收敛为 Zed，实现公共扩展接口，不实现 Octo 上传。
3. 「没事了， 继续，就按照当前实现就行，但是 octo buddy 本身好像不支持 zed:// ，有其他办法迂回吗？ 没有办法的话先这样，我找其它方式，相对路径的话，需要结合工作空间/子区的绑定地址来转换」。
4. 「不要这样按照子区，是 channel 整体的配置，给出 .envrc 中需要配置的配置项，我配置好」：配置范围调整为 channel 实例，使用环境变量。

## 范围和配置

仅处理助手普通正文中的 Markdown 本地文件链接。识别器识别完整链接和代码上下文；有序 resolver 各自判断 `isMatch`，首个匹配者转换，未匹配保持原文。普通 URL、代码块、行内代码不变。默认关闭，通过服务环境配置 Zed 本地或 SSH 模式，配置适用于该 channel 的所有聊天。相对路径使用任务启动时实际绑定的工作目录，不使用父群当前目录或进程 cwd；绝对路径保留其含义。Zed SSH 使用 `zed://ssh/[user@]host[:port]/absolute/path`，本地使用 `zed://file/absolute/path`；对路径进行 URL 编码。Zed 链接指向实时文件。

在 channel 服务启动时加载的 `.envrc` 中配置：

```sh
export OMP_CHANNEL_OCTO_ZED_MODE=ssh
export OMP_CHANNEL_OCTO_ZED_HOSTNAME=my-mini
```

`HOSTNAME` 是接收方 SSH 配置中可解析的名称。需要覆盖 SSH 默认用户名或端口时，可分别设置 `OMP_CHANNEL_OCTO_ZED_USERNAME` 和 `OMP_CHANNEL_OCTO_ZED_PORT`。本地模式设置 `OMP_CHANNEL_OCTO_ZED_MODE=local`，无需 SSH 参数；不设置 `MODE` 时关闭转换。`.envrc` 必须由服务启动环境加载，修改后重启服务才会生效。

任务首次开始投递前，将实际 cwd 与 channel 的 resolver 配置一起持久化为任务级解析上下文；同一任务恢复时复用该快照，不重新读取变化后的聊天绑定或配置。新任务使用新配置。已持久化的 outbox 文本按原样恢复投递。

扩展接口允许 resolver 异步完成；相同消息的快照按版本排序，较旧结果不得覆盖较新或 final 结果，任务收尾须等待已接受的 final 投影落盘。Zed 转换无需异步网络操作；未来有副作用的 resolver 仍须单独设计幂等及恢复。

## 投递与失败

基于累计文本快照转换，完整链接出现后替换，再进入 mention 处理和 UTF-8 分段；不改变原始会话输出。保留原消息 ID、final 权威快照、既有 outbox 持久化与重启恢复。转换不引入网络请求和上传。识别失败或没有匹配项保留原文，不声称链接已打开；普通正文继续投递。不得将链接拆成跨消息的半截链接：可放入 3000 字节消息的链接按完整单元分段，超过上限的链接保留原文并遵循既有分段。

非 final 快照末尾可能是未完成的 Markdown 链接时，暂不投递该候选尾部；补全后按完整链接转换和分段，final 仍不完整则按原文交付。较新快照或 final 对先前分段的修正复用 outbox 现有版本、在途创建和稳定 client ID 机制，不能让旧结果覆盖新结果。

已检查本机 OctoBuddy Test 2026.1029.41749 的消息渲染和外链实现：Markdown 的协议白名单及桌面外链入口均不允许 `zed:`，后者只放行 HTTP(S)。用户截图表明 Zed 已进入远程连接流程，但不能证明此版本 OctoBuddy 能直接打开 Zed 链接或文件已打开。可考虑由浏览器访问 HTTPS 页面后再打开 Zed，但浏览器协议交接尚未验证，且中转会暴露路径和主机信息；本实现不提供中转服务。

## 验收

- 本地与 SSH 的相对、绝对路径按任务实际 cwd 及 channel 配置解析，不同聊天使用各自的实际 cwd；普通 HTTPS、代码、未完成链接与失败路径不受影响。
- 真实流式消息的多次快照、final 修正、分段、mention 和重启恢复保持既有身份与顺序；至少验证跨段链接及相对路径绑定。
- 核对实际 Zed 客户端链接处理与 OctoBuddy 点击行为；无可用真实客户端或点击受限时明确报告，不虚称可点击。OctoBuddy 的 HTTPS 方式仅在真实支持且权限和安全边界明确时采用，不设置未验证的跳转服务。
- 不自动上传任何文件。未来 Octo resolver 须另行确认文件选择、访问权限、上传快照、失败及恢复语义。
