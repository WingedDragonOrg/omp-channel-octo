# OctoBuddy 本地增强器设计

日期：2026-11-10

## 用户原始需求

按对话顺序保留；后续条目补充前面的需求。

1. 「现在有一个 OctoBuddy App，应该是 electron 构建的，我可以往里面注入插件或者自己的自定义能力吗？并且不影响后续更新等，比如注入：点击超链接，使用本地 zed 打开这种」
2. 「我要能注入到里面去实现，甚至添加 功能、UI 等，有办法吗」
3. 「eletron 本身没有 extension 机制吗？像 chrome 一样」；「需要确认下有没有入口，没有的话是否可以注入?」
4. 「可是这样方便打开吗？一个全新的入口？OctoBuddy 增强版？还是每次都要启动两个？」
5. 「验证并形成初步方案，在当前项目中 创建独立的 packages/xxxx」
6. 关于范围，用户选择：「本地自定义增强，且最好看下有没有什么现成的 插件注入/增强框架/抽象，避免完全自己从头实现一套」。
7. 「所以到底使用什么框架呢？或者还有其他的吗？我理解这个需求并不小众才对」；「为什额么 electron-webext 不合适？除了默认热更新可能刷新页面 还有啥缺点？不要只看缺点不看优点，如果使用了 webext，它可以带来什么？」
8. 「ok, 看起来 electron-webext 更合适，它提供了我们不想碰的基础框架能力，除非硬伤否则不考虑其它」。
9. 用户确认整体设计：独立 macOS 启动入口、本地可信插件、electron-webext 优先、Zed 示例、原应用和资料保持不变、隔离验证与安全边界。

## 目标与范围

在 `packages/octobuddy-enhancer` 建立独立增强器：一次点击启动已安装的 OctoBuddy 并注入本地插件，为现有页面添加 UI 和交互；第一个插件在可识别的本地文件路径上提供「用 Zed 打开」，支持行号。当前仓库现有 channel 服务、命令和运行状态不受影响。对照需求 1、2、4–6、8–9。

本设计不修改、重签 OctoBuddy 安装包，不改写应用更新机制，不创建或复制另一份账号资料。不承诺兼容任意 Chrome 扩展、不提供插件市场、不支持 macOS 以外平台。插件能力与应用更新兼容性以实际验收为准，不承诺任意未来版本永久兼容。

## 已验证事实与前置验证

- 本机 OctoBuddy `2026.1106.44225` 是 Electron 应用，`app.asar` 带完整性声明。已检查的主进程与 preload 代码未发现 `loadExtension` 或 `--load-extension` 入口；此结论不扩展到其他版本。
- 用隔离临时用户目录和测试模式启动该版本，CDP 发现 `Octo Communication` 与 `OctoBuddy` 页面；在其中一个页面创建、读取并移除 DOM 元素成功。未对已登录生产实例注入。
- 该测试不证明正常生产资料、electron-webext 插件、目标聊天消息、Zed 或更新行为可用。实现前须以临时资料完成目标页面、插件、窗口重建、Zed 链路验证；真实资料与登录保持只在用户授权下验证，不复制或改写登录数据。
- [electron-webext](https://github.com/boweiliu/electron-webext) 提供 CDP 宿主、manifest、内容脚本、isolated world、部分 `chrome.*` shim 与管理界面。其当前源码不严格执行内容脚本匹配、默认可刷新页面、存在内存存储及不完整 API；必须针对所选固定版本核实，不能当作完整 Chrome 扩展运行时。

## 关键决策

1. **优先 electron-webext**。先在隔离实例上验证并评估采用固定版本依赖、上游贡献或维护小范围 fork。必须补齐本设计的目标隔离与生命周期合同。仅在验证发现无法接受且无法合理修正的硬伤时停止并向用户报告，再讨论替代方案；不得静默切换框架。对照需求 6–8。
2. **一个用户入口**。增强器以独立 macOS `.app` 入口启动原版 OctoBuddy 和后台宿主；用户只需打开该入口，进程可以不止一个。保持 OctoBuddy 实际资料和原有更新路径，不改变应用包。对照需求 1、4–5、9。
3. **可信本地插件**。只加载用户明确安装或项目内明确启用的插件，按插件允许的目标页面注入；不自动加载 electron-webext 示例插件或 Discord 桥接。isolated world 不构成权限沙箱；插件可访问匹配页面的数据。对照需求 2、6、9。
4. **本机调试风险透明**。CDP 仅绑定回环地址并使用随机端口；本机其他进程仍可能连接并读取或控制登录界面，随机端口不是认证。首次启用 CDP 前展示风险并取得用户确认；拒绝时不启用 CDP。对照需求 1、9。

## 设计与行为

### 启动与退出

增强入口启动已安装的 OctoBuddy，并给其受控启动实例启用本地 CDP；不改变默认应用的数据目录。宿主附着确认属于该次启动的目标实例，只对明确允许的 OctoBuddy 页面注入。不能验证目标身份或不能建立连接时提示增强不可用，不连接其他进程、不伪报成功。
连接前将本次启动的进程身份、启动代际和 CDP 端口监听进程关联验证，重连及目标重新发现时再次核验；只凭端口、标题或 URL 不足以证明身份。入口使用原子单实例控制；端口被占用、监听者变化或身份无法确认时拒绝附着。这些检查不构成本机 CDP 的访问认证。

普通 OctoBuddy 已运行且不能安全附着时，提示用户自行退出后重开增强入口；不得自动终止现有进程、改变其启动参数或启动另一份资料。重复打开增强入口不得产生冲突的增强宿主。OctoBuddy 退出时宿主释放连接并退出；宿主异常退出或增强失败时，不关闭原应用，须有可观察提示。CDP 由 OctoBuddy 进程持有，宿主退出并不保证端口关闭：应用仍运行时须明确提示调试端口仍可访问，端口随该应用实例退出关闭。
由独立于插件宿主的监护者或等效机制观察宿主和 OctoBuddy：宿主异常退出且应用仍存活时，提示增强已停止且调试端口可能仍开放，不终止应用。监护机制不可用时不得静默承诺异常退出提示；在启用增强前报告失败。正常退出和更新后无法重新附着也须有对应状态。

更新由 OctoBuddy 既有流程完成，增强器不拦截、替换或重新签名更新包。页面结构改变或目标匹配失效时应明确报告对应插件不可用，不把失败称为增强已生效。更新期间实例重启按普通窗口/连接生命周期重新发现；若无法重新附着则提示用户重新从增强入口启动。

### 插件宿主

基于 electron-webext 的 manifest、内容脚本、isolated world 和管理界面；受控的插件集合及严格目标匹配由增强器负责。每次文档创建前，按插件、具体 `content_scripts` 条目及实际目标和 frame 的地址重新匹配，无法确认的 frame 默认拒绝；不能依赖当前框架中忽略 `content_scripts.matches` 的实现。不得向无关目标、身份未确认的窗口或不允许的页面注入；插件的页面访问范围不得扩大为全部目标。

插件在目标页面首次可用、页面重载和窗口重建时生效；同一页面不得累积重复的 UI 或点击处理。默认关闭 electron-webext 自动页面刷新。启用、禁用和重载应反映实际状态：禁用时移除插件自身已创建的 UI、事件监听及可撤销效果；不能清理的效果须明确提示，不得报告已完全卸载。插件失败不妨碍其他插件或 OctoBuddy 本身，并可观察到失败。
插件管理界面由 `⌘⌥⇧P` 快捷键打开或关闭，在主渲染页面和嵌入的消息页面均可使用。
禁用立即在宿主撤销该插件尚未执行的本地能力调用，并清理可撤销效果；已经发生或无法清理的效果如实报告。构建、注入和运行错误逐插件隔离，不能因一个插件读取或执行失败阻止其他插件。

框架现有扩展 API 仅承诺经验收实际支持的子集，不以存在名称替代真实实现。持久化需求不得依赖其当前进程内存存储冒充持久存储。无关示例插件和 Discord 专用宿主桥接不得随增强器默认启用。

### Zed 插件与本地能力

只为能够明确识别的本地文件路径提供「用 Zed 打开」操作，支持路径和行号；其他链接保留 OctoBuddy 原行为。具体可识别消息形态以隔离实例对目标界面的观察和可重复测试确定，不把远程链接或不明确的文本猜成受支持的本地文件。宿主先把文件解析为规范绝对路径，再作为独立参数传给 Zed，绝不拼接成 shell 命令；不存在、不可识别或 Zed 不可用时向用户报告失败，不宣称成功。
用户点击群聊或子区消息中的 `zed://ssh/` 文件链接时，增强器查询当前聊天绑定 cwd，并在链接的 SSH 主机上规范化 cwd 和文件后交给 Zed CLI；具体合同和版本要求见 `2026-11-12-zed-chat-workspace-design.md`。其他 `zed://` 链接按原样交给 Zed。合成点击不得触发本地能力。
对于 OctoBuddy 将目标清空的 Markdown 链接，在真实点击时按该链接节点的源文位置从消息原文恢复 `zed://` URL；无法明确恢复时提示失败，不根据相邻文本猜测目标。该恢复依赖当前 OctoBuddy 渲染器提供的 React 消息元数据。

宿主只暴露 Zed 插件所需的明确本地能力；网页内容或普通聊天文本不是插件安装、任意进程执行或本地权限授权。插件本身是用户信任的代码，不承诺防御恶意插件；任何用于页面到宿主的桥接须限制目标与操作，不能将普通网页输入直接解释为任意命令。
桥接调用方由宿主记录的目标、执行上下文及已启用插件身份确定，不信任请求自报的插件 ID；按调用方、操作和目的目标授权。插件管理操作只接受可信管理入口的真实用户操作；Zed 操作只接受插件处理的真实用户点击。页面脚本直接调用、伪造插件身份、跨目标调用或合成点击不得触发本地能力或管理操作。

## 验收标准

1. **独立入口与更新**（需求 1、4、5、9）：一次打开增强入口即可启动原版 OctoBuddy 和插件宿主，现有资料保持；原版已运行时提示人工处理，不杀进程、不复制资料。原 App 安装包和现有 channel 服务不变。
2. **框架与插件**（需求 2、6–8）：隔离实例加载本地可信插件，展示新增 UI；目标外页面不注入；重载、新窗口和重建后按允许范围恢复，重复触发不产生重复 UI 或事件。允许页面导航到不允许页面、未授权子 frame 及同插件不同匹配规则的脚本均须验证未执行。禁用后定时器和延迟调用不能再执行本地能力；一个插件构建或运行失败时另一个仍正常工作。
3. **Zed**（需求 1、9）：隔离测试对带空格的本地路径和行号验证宿主传给 Zed 的参数；普通链接维持原行为，识别失败及 Zed 不可用时可观察。实际消息页面的目标形态须有可重复验证。
4. **安全与失败**（需求 1、9）：只使用所启动且身份已确认实例的本机 CDP；覆盖端口预占、退出后端口复用和并发入口，不得附着错误实例。页面直接调用、身份伪造、跨目标调用和合成点击不得触发管理或本地能力；未知页面与插件不自动加载，不执行聊天文本作为 shell。启用前确认调试风险；杀死插件宿主后原应用保持运行，独立监护机制提示端口可能仍开放。正常退出及更新后无法重新附着状态如实呈现。
5. **真实框架验证**（需求 5–8）：对固定版本 electron-webext 执行隔离端到端验证，包括管理 UI、严格插件匹配、无自动刷新、窗口生命周期及加载/禁用；明确列出验证过的 API 和其余不承诺的能力。硬伤不能合理修正时停止并汇报，不换框架冒充完成。
6. **生产与更新验证**（需求 1、4、9）：使用临时资料验证生产启动方式及更新后再次注入；真实登录保持仅在用户授权下验证。不复制、改写真实账号资料或重启常驻 channel 服务。无法进行真实登录验证时明确记录未验证，不推断已通过。

- README「安装与启动」和「验证」中的命令已从文档抽出并回放。`bun install` 无依赖变化；`bun run scripts/build-app.ts` 写出 `dist/OctoBuddy Enhancer.app`，其 `Contents/MacOS/OctoBuddyEnhancer` 可执行。
- `bun run test`：26 pass、0 fail、119 次 expect，覆盖启动器、宿主和 Zed 三组验收。`bun run typecheck` 通过。
- 当前 `bun run test:integration`：1 pass、25 次 expect。使用已安装的 OctoBuddy `2026.1109.44980`、临时用户目录和临时 Zed 记录器。隔离世界加载 Zed 插件；在页面中插入的带空格 `file:` URL 与绝对路径按规范绝对路径和行号传给记录器；普通链接保持原样；页面重载后按钮恢复；宿主停止后按钮消失，OctoBuddy 进程保持原启动身份。
