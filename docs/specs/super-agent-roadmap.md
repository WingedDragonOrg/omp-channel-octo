# Super-agent 路线图

## 用户原始需求

1. 「结合 @docs/specs/super-agent-roadmap.md 和 https://github.com/deepseek-ai/dsh-superagent-prototype (deepseek 刚发布的 super agent 构想/原型) 看下roadmap 有哪些需要调整的？以及对于我们有哪些启示、路线指引」
2. 「将以上的信息、建议、方向、待做事项、最新进度，等等都更新到 roadmap 中」：将前述分析和建议纳入本路线图，不构成各阶段实施授权。


## 1. 定位与目标

面向 `omp-channel-octo`：以 Octo 群聊作为协调入口、子区作为任务协作空间、Git worktree 作为代码隔离环境、OMP 作为执行引擎，逐步形成低打扰、可追踪、可并行的长期助手。

核心目标：**父会话掌握意图、决策和交付，子区承载执行过程；完整状态可查询，只有值得关注的事件才主动进入父会话。**

进一步的产品方向：围绕任务全生命周期管理人的注意力，分别回答工作为何获授权、后续信息归谁、执行进行到哪里，以及何时需要人处理。依据必须可追溯；不能仅凭模型摘要推断。

本文是阶段路线图，不是一次性实施授权。已经确认的监听策略沿用现有规格；新增能力按阶段收敛实施规格后开发。阶段按依赖推进，不承诺日期，不把规划能力标成已上线。

### 典型使用场景

- 用户在群里提出多项需求，助手创建隔离子区并派发，父会话继续响应。
- 用户直接进入子区讨论设计、补充信息、回答问题并验收。
- 子区完成实现后，通过宿主合并流程交付；父会话只收到所监听的关键结果。
- 用户问“这些任务现在怎样”，助手按需查询，而不是依赖父会话是否记住所有过程。
- 后续 PR 评审、CI 等事件能够找到原任务，避免重新开工或混入另一项需求。

| 已有基础 | 路线图如何使用 |
| --- | --- |
| 每聊天独立会话、任务持久化、排队与 steering | 保持响应与执行隔离，复用任务身份及调度路径 |

| ask、权限门禁、入站去重、恢复与 outbox | 保留用户授权、答案归属、事件与输出交付边界 |
| 原生 goal 控制 | 长任务持续执行沿用 OMP 能力，不再发明第二套执行循环 |
| Loop workspace 任务感知与路由 | 规格记载已实现并通过隔离验收、未部署：有当前路由的 task 直达子区，无路由时仅符合 owner/Bot Octo UID 指派条件的任务进入主群；快照不是完整事件日志 |
| PR/MR 子区引用 | 规格记载已实现并经离线验收；可从 `thread-info.references` 查询本地关联，但不验证远端对象存在，不提供 webhook、评论或 CI 订阅 |
| 语义 watch | 规格记载已实现并经离线验收；用户显式请求后有界观察，命中进入所属聊天的独立队列；不等同于自动诊断运行中任务 |
| 子区向创建方显式输入 | 规格记录了实现和离线验证；`thread-send-parent` 独立于 listen，来源不是用户答案或新增授权，接受不等于处理完成 |

## 3. 架构立场

```text
用户消息 / 经授权的外部事件
          ↓
确定性准入、去重、归属判断
          ├─ 归属已明确 → 对应子区 / OMP 会话
          └─ 需要协调   → 父会话理解、澄清、派发
                                ↓
                     子区执行与本地协作
                                ↓
                 任务、交付、来源等持久记录
                      ├─ 用户或 agent 按需查询
                      └─ 命中 listen → 有界通知到创建方
```

### 职责划分

- **父会话**：理解需求、确定任务归属、派发、跨任务协调、向用户报告交付。角色是使用约定，不是新增一个拥有全局权限的 agent；不强制剥夺其工具或禁止局部直接操作。
- **子区 agent**：在明确范围内调查、设计、实现、验证和修复。继续支持直接与用户交互，其内部 subagent 对父会话透明。
- **宿主**：负责权限、任务身份、持久化、租约、命令执行、恢复、事件交付和通知策略。程序可判定的事实不交给模型猜测。
- **OMP**：负责模型执行、会话与原生持续目标。channel 不复制其推理循环。

“Router”是逻辑协调职责，不预设跨所有群共享一个上下文。现有聊天与授权隔离保持有效。

### 身份与证据

- **子区**是协作空间，可包含多个执行轮次，也可关联多个 Loop task；不是天然的一项业务任务。
- **channel task** 是一次持久受理的执行工作；**Loop task** 是外部业务任务，两者身份不可混用。OMP session 保存执行上下文，不等于交付状态。
- PR/MR 引用、提交、合并和归档是不同对象或证据；本地引用不证明远端对象存在、交付已完成或事件订阅已授权。
- 查询入口从一开始标明每条记录的对象类型、稳定身份和来源。先组合已有对象；只有实际需求证明无法表达跨轮次业务工作时，才另行设计业务任务实体。
- 外部对象关联决定上下文归属，订阅决定信息去向，执行授权决定允许做什么；三者不可相互推导。

### 不变量

1. 状态可查与主动通知分离；静默不代表任务记录丢失。
2. 子区报告和外部事件不是用户答案、确认或新增授权。
3. agent 判断语义相关性，宿主保证权限、隔离及副作用边界。
4. 已接受任务的恢复沿既有同会话机制执行，不重放原始需求创建新工作。
5. 模型声称“完成”不是已验证、已提交或已合并的证明。
6. 任何摘要或详情读取都受原资源访问权限约束；知道对象 ID 不等于可以读取。
7. 消息被接收、持久受理、送达 worker、被 session 消费和处理完成是不同事实；未知接受不能靠重复派发消除。
8. 展示“需要人处理”必须有结构化证据；模型声明 ready 不能单独证明等待 review 或业务完成。

## 4. 分阶段路线图

| 阶段 | 用户可见收益 | 前置依赖 | 结束条件 |
| --- | --- | --- | --- |
| P0 可靠响应与低打扰交付 | 慢操作期间仍可受理其他聊天，父会话只收到需要的结果 | 已有监听与合并契约；完成非阻塞入站既有规格及验收 | 集成场景验证跨聊天响应、取消、实际合并与通知一致 |
| P1 按需待办与任务总览 | 优先知道哪些事项需要人、哪些正在运行 | P0 的可靠受理、来源与状态基础 | 有依据、可追溯的只读查询，不触发执行 |
| P2 身份、分层详情与交付证据 | 知道工作跨轮次的关系、结果和真实交付 | P1 明确对象类型及身份 | 从摘要读到证据，区分业务工作、执行与交付 |
| P3 外部事件归属与直达 | 获授权的 PR/CI 等后续事件回到原任务 | P2 对象关联及权限 | 一个选定来源完成可靠路由闭环 |
| P4 受控进展监督 | 长任务异常可被发现和处理 | P1/P2 证据；真实需求 | 监督有范围、成本约束及停止边界 |

### P0：巩固可靠响应与低打扰交付

**范围**：验收既有能力的集成；按现有规格完成非阻塞入站，不重新设计监听系统。

- 默认 merge：只在宿主确认实际合并成功后通知创建方。
- off：不自动回传。task：额外报告独立派发任务的终态。
- 合并失败及修复失败在所有级别下均留在子区。
- shared 不支持合并；默认静默，需要派发结果时显式 task。
- 清理与归档按真实状态表述；“已排定”不能显示为“已完成”。
- 慢命令、合并或其他长操作期间，其他聊天的消息和控制命令可继续受理；区分 handler 返回、持久受理与执行开始。

**验收门槛**：使用隔离 Git、数据库和 transport 场景验证成功、冲突、修复失败、重启、改档；默认普通任务终态不向父会话增加任务或 steering，真实合并成功不重复通知。既有规格中的接受状态不明处理保持不变，不能为了补通知而重新合并。

同时依据非阻塞入站规格，在隔离的真实 CLI、transport 和进程场景验证慢操作期间跨聊天的新输入、状态查询及取消可受理，保持授权、ACK、聊天/session 顺序与恢复边界；不以 handler 返回冒充持久受理。该规格仍实施中，不将其分项结果当作整体验收完成。

**交付物**：集成验收证据与必要的契约修正；完成非阻塞入站的既有实施与验收。前提满足后进入 P1。

### P1：按需待办与任务总览

**用户问题**：“这个群派出去的任务有哪些？哪个在等我？哪个失败了？”

**范围**：提供一个只读查询入口，由宿主根据当前聊天与权限返回关联子区和任务，优先回答需要人处理的事项，再展示运行、排队和已结束工作；不启动新的 OMP 执行任务，不扫描所有会话正文。

每项至少包含：来源子区、对象类型与稳定任务标识、简短目标、持久执行状态、最后记录时间，以及已有证据支持的待决事项和详情入口。任务目标摘要是展示信息，不是重新执行的指令。可分别展示明确待答问题、执行中或排队、已结束及已有交付证据；状态无法确认或查询不完整时如实标明，不把缺失数据视为正常。

**约束**：
- 按当前聊天创建关系和现有访问规则限定可见范围，不把同一 owner 的全部群信息自动汇总。
- “等待回答”来自待答问题，“失败”来自任务记录；没有证据时不推断进展或完成比例。
- 等待 review、人工验收或其他人为阻塞只在有对应结构化证据时展示；P1 不为填满分类而建立推测状态。
- 读取本身不唤醒子区、不补发旧通知、不恢复任务、不改变监听档位。
- 子区名称变化不影响稳定身份；历史记录与当前工作区可用性分别展示。

**验收门槛**：构造多个子区，包括运行、排队、待答、失败及已结束任务；需要人处理的事项有可定位的证据，对象身份和查询状态与持久记录一致，缺失或不完整数据如实显示，权限范围外结果不可见。结果过多可分页，详情可按标识继续读取，且查询前后任务及通知状态不变。

**阶段设计要明确**：在现有 host tool 上扩展还是独立只读工具、返回字段与分页契约。只建立一个权威查询入口。

### P2：身份、分层详情与交付证据

**用户问题**：“它为什么失败？改动在哪里？代码是否真的合入？”

**范围**：将 P1 的摘要连接到可按需读取的详情；厘清子区、Loop task、多个 channel task 和 session 的关联，把执行状态与交付证据分开表达。

- 摘要只内联任务身份、状态、必要结论和详情引用。
- 详情分层展开：任务 → 子区与结果 → 可验证产物，如提交、合并事件、测试报告。
- 详情有大小边界及续读入口，不把截断当成完整结果。
- 执行结束由任务状态表达；提交、合并、归档分别引用真实证据及时间。
- 文档、调查等非代码任务使用各自的交付物及验收依据，不要求 Git merge。

**约束**：复用现有记录建立引用，不建设通用知识图谱，不复制所有会话形成第二个事实库。结果来自 agent 时标明来源；宿主事实与模型总结分开。

一个 Loop task 可以跨多次执行，一个子区也可关联多个 Loop task；关联缺失时展示未知，不凭共享 cwd、名称或相似文本猜测。先复用现有持久记录与领域归属，不预设引入新的 Ticket 或 Assignment 状态机。

**验收门槛**：从总览可以定位一个具体任务的结果及产物；任务 completed 但未合并时，查询明确显示未有合并证据；产物不存在、访问无权或引用失效时如实说明，不能替换成相近任务。读取长报告不会自动将全文注入父会话。

**阶段设计要明确**：详情引用生命周期、结果脱敏、读取权限，以及非代码任务的最小交付契约。具体协议在该阶段确认，不在路线图中承诺统一完成状态机。

### P3：外部事件归属与直达

**用户问题**：“这个 PR 的新评论和 CI 失败能不能直接由原来的子区继续处理？”

**范围**：先选择一个真实高频来源完成闭环，例如 GitHub PR 评论与 CI；不一次接入所有平台。

**现有基础**：Loop 具备按路由或成员指派门槛交付任务快照变化的既有路径；PR/MR 已有本地引用绑定，但尚不等于已验证远端对象或订阅事件。语义 watch 是显式的一次性条件观察，不替代来源事件流。

- 显式关联外部对象与任务/子区，使用提供方稳定对象 ID，而非标题文本匹配。
- 通过来源验证、权限与订阅规则的已归属事件直达对应任务。
- 未归属或归属不唯一的事件进入授权范围内的协调路径，不广播给所有子区。
- 外部事件是上下文输入；是否允许触发执行由该订阅的明确授权决定，不绕过现有命令权限。
- 区分任务直接工作对象与仅供参考对象；对象关联不自动建立订阅，也不授予执行权限。先明确事件仅记录、作为上下文送达还是可触发执行。
- 明确归属的后续信息按原任务范围处理；超出范围或归属不明时走受授权的协调路径。来源正文、评论和 CI 输出不得扩大原授权。
- 持久记录事件来源、去向及受理/消费事实；实际消费与仅投递分开，接受状态不明时不新建第二次执行。
- 父会话仍按 listen 接收关键结果，不接收每条评论或 CI 日志。

**验收门槛**：在一个真实协议的隔离 fixture 中，初始请求与后续事件关联同一任务；重复事件不重复执行，乱序事件不覆盖较新事实。取消、解绑、归档后到达的事件不自行重新开工；权限变化和跨群隔离可验证。

**进入实施前必须确认**：首个来源、工作对象与参考对象的关系、订阅由谁建立、允许的自动执行范围、后续输入归属及过期事件处置。该阶段需独立审查授权、取消与恢复设计；不因原型允许人类消息恢复已结束工作而改变本项目的停止和归档边界。

### P4：受控进展监督

**用户问题**：“这个长期任务是不是卡住了？现在需要我做什么？”

**范围**：先依赖确定性事实识别等待、进程异常、外部依赖不可用；只有需要判断方向或实质进展时才考虑模型监督。与已有进程 watchdog 区分，不替换其进程安全职责。

现有 watch 只覆盖用户显式请求的有界条件观察与命中唤醒，不证明任务是否卡住，也不构成本阶段的主动监督。

**默认立场**：监督先提供按需诊断，不自动重试、修改任务目标、增加权限或恢复用户已停止的任务。主动监督作为显式开启的独立能力，不能通过 task/merge 监听级别暗中启用。

**验收门槛**：能够区分等待用户、合法长操作、外部依赖阻塞和异常停止；诊断附证据，不把“很久没消息”直接当失败。停止意图始终优先，不产生无限重试或重复副作用。

**进入实施前必须确认**：监督对象、成本预算、触发频率、告警接收方、允许的干预动作。没有实际长任务需求与收益证据时停在 P3。

## 5. 工程落点与阶段边界

| 能力 | 现有主要落点 | 责任边界 |
| --- | --- | --- |
| 监听与结果通知 | `src/threads/thread-notify.ts`、`src/service.ts`、store | 宿主事实与通知策略，不承担语义相关性分类 |
| 任务总览、详情 | store、`src/host-tools.ts`、任务契约 | 只读组合既有数据；不借查询入口执行任务 |
| 事件路由 | transport、inbound、任务调度层 | 来源规范化与授权后才进入调度；不把平台逻辑散落进模型提示词 |
| 交付证据 | 合并、归档、任务记录 | 各领域拥有自己的事实，查询层负责关联展示 |
| 进展监督 | 既有任务与 worker 生命周期接口 | 读取事实与受授权控制，不直接接管 worker 所有权 |

每阶段先设计明确的窄接口，再按实际代码决定拆分；上述是职责归属，不是要求立即新增模块。

## 6. 评估方式

先用固定隔离场景建立基线，再比较阶段前后；不凭主观感觉承诺提速比例。

| 观察项 | 判断方式 |
| --- | --- |
| 父会话干扰 | 固定任务序列中，普通任务终态、合并失败造成的父会话新输入数；默认应为零 |
| 查询准确性 | 查询状态、来源与证据是否对应同一个持久任务 |
| 上下文占用 | 同一组任务总览及详情读取的实际字节量，核查是否被动携带全文 |
| 交互响应 | 后台任务执行时，父会话能否接收独立的新需求，不等待子区完成 |
| 归属正确性 | 新事件是否送到明确授权的原任务，是否误投或重复执行 |
| 人工负担 | 完成固定多任务流程需要用户手动查找、复制结果和重复解释的次数 |
| 人工注意力 | 待人处理分类是否有证据，漏报和误报各多少；无证据时是否显示未知 |
| 输入生命周期 | 固定故障与重启场景中，收到、受理、送达、消费和结果是否可区分，未知状态是否避免重复执行 |
| 健康与交付 | 投递失败、权限变化、失效引用是否可查，是否被误报为完成或正常 |

P0 使用现有行为测试与真实 Git/进程 smoke；P1/P2 重点验证只读路径、证据和访问边界；P3 验证提供方协议、重复/乱序及撤销；P4 验证停止边界和真实进展判断。新增持久化或生命周期变化必须按项目规范补充迁移与恢复验收。

## 7. 暂缓方向

- 云端计算与本地环境分离：当前仍是常驻本机 Bun 服务加 OMP 子进程；多机访问和离线持续执行有明确需求后再设计。
- 全群无提及主动修复、后台投机执行：需要独立授权、成本与副作用政策。若出现真实需求，可先设计仅记录“原本会做什么”的观察模式，再评估授权自动执行；观察记录本身不触发工作。
- 全局单一 Router、Router 分片、通用事件总线、知识图谱、通用 Source 框架和独立 Web 面板：没有实际需求与测得收益前不引入；可在现有查询界面借鉴“先显示待人处理、再显示健康与历史”的原则。
- 强制 Worker 不与用户交互：保留用户直接进入子区工作的方式。

这些方向不构成 P0–P3 的前置条件，也不作为本轮实施内容。

## 8. 下一步决策与交付标准

推荐顺序：**完成非阻塞入站既有验收并核验 P0 → 设计并实施 P1 → 按查询需求推进 P2 → 从实际高频的 Loop 或 PR/MR 跟进中选定一个来源完成 P3 → 有证据再决定 P4。** P1 与 P2 可分步交付，但 P1 起即区分对象类型与稳定身份。

下一份可实施规格应聚焦 P1，只回答“当前聊天关联的哪些事项需要人处理，以及任务状态如何只读查询”。使用现有 ask、任务、创建关系、Loop 路由和引用中可获得的证据；字段与可用性须在设计时核验。不同时捆绑外部事件接入或监督系统。

本路线图的完成标准：已有契约与规划能力明确区分；每阶段具有用户问题、范围、依赖、可观察验收和进入实施前的决策门槛。路线图自检不代替后续涉及迁移、权限、外部协议及跨重启行为的独立设计审查。

### 近期待办

1. 对照各现有规格与当前代码核验能力和部署状态，完成非阻塞入站规格的剩余实施及隔离验收；不得把历史分项测试视为本轮通过。
2. 核验 P0 的合并、失败、监听和通知链路及慢操作期间的跨聊天受理。
3. 为 P1 明确现有记录能证明哪些待答、执行状态和来源，设计只读查询、分页、权限和未知状态。
4. 为 P2 梳理跨轮次身份关系与可验证交付证据；不足以关联时明确缺口。
5. 根据真实使用频率选择 P3 首个来源，在实施前确认订阅、授权、停止、解绑和恢复边界；P4 留待真实需求与收益证据。

### 原型的启示与适用边界

DeepSeek 原型将 Source/Trigger、授权依据、Ticket、Assignment 和 Subscription 分开，并强调“先看是否需要人”。可借鉴其授权与上下文分离、输入实际消费追踪、以证据呈现待人处理，以及主动接单先观察再授权的思路。

本项目保留现有宿主事实、合并与精确 session 恢复合同，不照搬单仓库 Ticket 状态机、提示词式合并安全边界或原型的重试与已结束任务恢复规则。原型本身自述为研究代码、非生产产品，且不完全等同于文章中的内部实现；其文档是设计参考，不是本项目实现或性能证据。
